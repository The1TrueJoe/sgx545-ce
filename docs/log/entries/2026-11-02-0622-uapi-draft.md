# First draft of the DRM uAPI

M2 step 1 (AGENTS.md section 5), ahead of M0 and M1 finishing. Nothing goes upstream or
into Mesa from this. No hardware was touched.

## What was done

- `docs/UAPI.md`: the ioctl set, client streams field by field, how every word of the TA
  command, render details and transfer command gets produced, heap constraints, the threat
  model, how hardware recovery reaches userspace, ten decisions for Joseph and 25 doc gaps.
- `docs/uapi/sgx_drm_draft.h`: the draft header with kerneldoc. `sgx545` in every name is
  a placeholder.
- `docs/uapi/check.sh`: compiles the header with `zig cc` for `x86-linux-gnu` and
  `x86_64-linux-gnu`, against zig's copy of `drm/drm.h`, with `-Wpadded -Werror` and
  static asserts on literal offsets and sizes from `layout.inc`, plus ioctl numbers. A
  negative control has to fail on both targets. All of it passes.

The shape follows `pvr_drm.h` with three differences:

- the kernel allocates and hides the parameter buffer and RT dataset;
- a render job is a whole scene with an array of TA kicks;
- streams are plain extensible structs.

Each is a decision for Joseph, not a settled choice.

## The finding that matters

Isolation rests on four hardware properties `docs/` doesn't establish (UAPI.md section 7.2):

- a client's USSE task can't reach `EUR_CR_*` through `ldr`/`str`;
- it can't reach kernel memory, which depends on BIF banks and on `EDM_PROTECT`;
- a client's PDS program can't enter the microkernel through DOUTU base 15 or b27;
- the microkernel takes nothing from secondary attributes a client can write.

Each has a proposed experiment, none run. If one of the first three fails, the choices
are kernel validation of all shader code or a firmware change, and M2's exit test can't
pass as written (decision D9).

## What's solid

- The layouts: identical on i386 and x86_64, proven by the compile.
- Heap bases, the 5 MiB and 2 MiB USSE reach, PDS address formats, 1 MiB request bases, the
  16-bit free-list index, all from captures and hardware runs.
- Each stream field was poked or diffed; the table in UAPI.md section 3 has the tag per row.

## What's a guess

- Heap sizes other than USSE: the next base is used as an upper bound.
- Whether the stream fields are enough for Mesa: unknown until M3.
- Kernel-written constants for unnamed words: right for the captured frames, not known
  right for all GL state.
- Scenes of more than two kicks: there is no documented flags value for a middle kick.
- More than one parameter buffer in a VM, and any concurrent contexts.
- The ZLS offset limit.
- Hardware recovery as userspace sees it: a design on a path only run offline.

## Doc inconsistencies found

- STATE.md section 1 refers to a TA-flags bit table that isn't there, and has `0x71`/`0x62`
  where DRIVER-UPSTREAM.md has `0x63`/`0x10`.
- STATE.md 6's tail-pointer formula gives 0x100 at 720×480, against its stated 0x1000.
- Transfer word 11 is a code size in TEX.md and a flag in UKERNEL.md.
- Register 0x408 is region headers on a render and the depth/stencil block on a transfer.
- GEN.md lists `+0x104` under render details, STATE.md under the TA command.
