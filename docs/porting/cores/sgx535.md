# SGX535 (Intel Poulsbo, GMA 500)

The fact sheet for the SGX535 in Intel's Poulsbo (GMA 500, Atom Z5xx). Mainline gma500
lists the same core in Moorestown and Oaktrail (GMA 600, Atom Z6xx and E6xx). It collects
what public sources say, compares the core with the SGX545 we know from hardware and with
the SGX530 ([sgx530.md](sgx530.md)), and lists what a hardware test must confirm. Nothing
here has been read from an SGX535 yet.

The tags are [sgx530.md](sgx530.md)'s:

| Tag | Meaning |
|---|---|
| **L** | Mainline Linux 7.3.3: gma500. The text is in the tree. |
| **K** | The GPL kernel side of an SGX DDK: its register, feature, errata and MMU headers. They describe what that DDK programs, not the silicon itself. |
| **P** | Our own gma500 patches in `drm/gma500/`. |
| **D** | Derived from L, K or P facts, often with an SGX545 result we confirmed on hardware. |
| **C** | Confirmed on SGX535 hardware. None yet. |
| **G** | A guess. |
| **U** | Unknown. |

## Sources

- **L:** `drivers/gpu/drm/gma500/`: `psb_drv.c` and `psb_drv.h` (the chip list, the BAR
  layout, the SGX setup at load), `psb_reg.h` (the SGX registers gma500 uses),
  `psb_device.c` (Poulsbo's `psb_chip_ops`), `psb_irq.c`, `mmu.c`, `gtt.c`, `power.c`.
- **K:** the GPL kernel drop the SGX545 work started from: `sgx535defs.h`,
  `sgxfeaturedefs.h`, `sgxerrata.h`, `sgxmmu.h`. The SGX530 comparisons use the headers
  [sgx530.md](sgx530.md) cites.
- **P:** `drm/gma500/0001-drm-gma500-Publish-the-Cedarview-SGX-as-an-auxiliary.patch`.
- No closed userspace, firmware or non-GPL vendor file was used.

As for the SGX530, the K headers list only the registers the host kernel touches. The TA,
3D, DPM, ISP, TSP, PBE and PDS state registers are **U** for the SGX535.

## Summary

The SGX535 is a mix of the two cores we've written up:
- **Its low registers and unit layout are the SGX530's:** the clock-gating, reset, ID and
  event registers sit where they do on the SGX530, with the same fields, and it has a 2D
  unit.
- **Its BIF is the SGX545's:** 16 directory lists, the same per-requestor bank registers,
  and a 32-bit device address space.
- **It has one kick register**, like the SGX530.

So it does **not** need the single-context mode in
[single-context.md](../single-context.md): one memory context per job, 32-bit heaps and the
SGX545's bank scheme all apply. It needs only that note's single-kick part (the init kick
on `EVENT_KICK`, `regs.event_kick2 = 0`), and the core check has to accept a core that has
`MULTIPLE_MEM_CONTEXTS` but not `MULTI_EVENT_KICK` (D).

## Register map

### Where it matches the SGX530 and not the SGX545

| Register | SGX535, SGX530 | SGX545 | Tag |
|---|---|---|---|
| `CLKGATESTATUS` | 0x0004 | 0x0008 | K, L |
| `CLKGATECTLOVR` | 0x0008 | 0x000c | K |
| `CORE_ID` | 0x0010 | 0x001c | K, L |
| `CORE_REVISION` | 0x0014 | 0x0020 | K, L |
| `DESIGNER_REV_FIELD1`, `FIELD2` | 0x0018, 0x001c | 0x0024, 0x002c | K, L |
| `PDS_INV2` | 0x0ad8 | absent | K |
| `PDS_INV3` | 0x0adc | 0x0ad8 | K |
| `PDS_PC_BASE` | 0x0b2c | absent | K |
| `BIF_TWOD_REQ_BASE` | 0x0c88 | absent | K, L |
| `2D_BLIT_STATUS` | 0x0e04 | absent | K, L |
| `2D_VIRTUAL_FIFO_0`, `_1` | 0x0e10, 0x0e14 | absent | K |

The field layouts match the SGX530's too (K; L for the ones `psb_reg.h` names):
- `CLKGATECTL`: 2D b0-1, ISP b4-5, TSP b8-9, TA b12-13, DPM b16-17, USE b20-21, auto/manual
  b24. gma500 names the 2-bit values 0 enabled, 1 disabled, 2 automatic (L).
- `CLKGATESTATUS`: 2D b0, ISP b4, TSP b8, TA b12, DPM b16, USE b20.
- `SOFT_RESET`: BIF b0, 2D b1, DPM b2, TA b3, USE b4, ISP b5, TSP b6 (L agrees).
- `EVENT_STATUS`: every bit as on the SGX530, including 2D complete b27, OTPM loaded b21
  and ISP halt b17.

### Where it matches the SGX545 and not the SGX530

| Register | SGX535 | Tag |
|---|---|---|
| `BIF_DIR_LIST_BASE1` to `15` | 0x0c38 to 0x0c70; `BASE0` stays at 0x0c84 | K; L for `BASE1` |
| `BIF_BANK_SET` | 0x0c74 | K |
| `BIF_BANK0`, `BIF_BANK1` | 0x0c78, 0x0c7c | K, L |
| `BIF_BANK_STATUS` | 0x0cb4: 3D current bank b0, TA current bank b1 | K |
| `BIF_TILE0` to `9` | 0x0c0c to 0x0c30 | K |
| Device address space | 32 bits: `BIF_FAULT` b12-31, the requestor bases and `PDS_EXEC_BASE` b20-31, `EVENT_KICKER` b4-31 | K |
| `USE_CODE_BASE(n)` | 0x0a0c + 4n; address b0-24, data master b25-26 | K |

The bank registers' fields are the SGX545's exactly: `BIF_BANK0`/`1` carry a 4-bit
directory-list index per requestor, EDM b0-3, TA b4-7, host b8-11, 3D b12-15, 2D b16-19
(K). The scheme in [UKERNEL.md](../../UKERNEL.md) ("Point the BIF at a context") carries
over. The SGX545's `BIF_BANK_SET` has named per-requestor select bits; the SGX535's
header gives only one 10-bit select field (b0-9), so its meaning is **U**.

### Absent from the SGX535 header

`CLKGATECTL2`, `TIMER`, `EVENT_KICK1` to `3`, `BIF_36BIT_ADDRESSING`, the
`BIF_TILE*_ADDR_EXT` registers, `BIF_CTRL_RDATA`, and the SGX530's `PDS` (0x0abc). All K.
As on the SGX530, a register missing from the header isn't touched.

### Other field differences

| Field | SGX535 | SGX530 | SGX545 | Tag |
|---|---|---|---|---|
| `BIF_CTRL` bypass bits | the SGX530's (2D b11, PBE b12, TSPP b13, ISP b14, USE b15) plus host b16 | no host bit | no 2D bit; PBE b11 to host b15 | K; L: gma500 clears b8-16 (`_PSB_MMU_ER_MASK` 0x0001ff00) |
| `BIF_INT_STAT` | fault b0-13, page fault read/write b14, flush complete b15 | the same without flush complete | fault requestor b0-15, type b16-18, flush complete b19 | K |
| `BIF_DIR_LIST_BASE0` address | b12-31 | b12-31 | b8-31, for 36-bit addresses | K |
| `EVENT_STATUS2` | the DPM TA/3D free-load events b0-1, host and "dhost" free load b2-3, BIF requester fault b4, the TA, 3D and display-list triggers b5-7 | b0-1 only | b0-3 and b5-7 like the SGX535, no requester fault, more events above | K |
| `PDS_DOUT_TIMEOUT_DISABLE` (in `PDS`) | absent | b6 | absent | K |

gma500 enables the BIF requester fault (`EVENT_HOST_ENABLE2` b4) and the 2D complete
event (`EVENT_HOST_ENABLE` b27) when it installs its interrupt (L), which matches the K
bits.

## The BIF and the MMU

| Fact | Value | Tag |
|---|---|---|
| Device address space | 32 bits | K |
| Memory contexts | multiple: `SGX_FEATURE_MULTIPLE_MEM_CONTEXTS`, 16 directory lists | K |
| Requestor banks | `BIF_BANK0`/`1`, the SGX545's layout | K |
| Physical addresses | 32 bits: PDE and PTE address b12-31. No 36-bit MMU. | K, L |
| PTE flags | valid b0, write-only b1, read-only b2, cache-consistent b3 | K, L (`PSB_PTE_*`) |
| Pages | 4 KiB. The PDE's page-size field reads 0 for 4 KiB in the K header. Whether larger pages work is U. | K |
| Errata touching the MMU | none known; no BRN_28889 | K |

gma500 already programs this MMU on Poulsbo (L, `psb_drv.c`, `mmu.c`, `gtt.c`):
- It writes 0 to `BIF_BANK0` and `BIF_BANK1`, so every requestor uses list 0, and clears
  the bypass bits so that every access goes through the MMU.
- It loads list 0 with its own directory, which maps the stolen memory at the GATT's
  address, and points `BIF_TWOD_REQ_BASE` at the GATT. It places its MMU's GATT window at
  0xe0000000 (`mmu_gatt_start`, 256 MiB aligned), because of a video-MMU erratum at
  0xd0000000, per its comment.
- It writes a second directory with `hw_context` 1 to `DIR_LIST_BASE1 + 1 * 4` = 0x0c3c,
  which `sgx535defs.h` calls `DIR_LIST_BASE2` (D). With both banks 0, nothing reads it.
- It sets `PDS_EXEC_BASE` to 0x20000000 and `BIF_3D_REQ_BASE` to 0x30000000.
- It flushes with `BIF_CTRL`'s `INVALDC` and `FLUSH` bits.
- It submits no 2D or 3D work: no file in gma500 uses the 2D command definitions in
  `psb_reg.h`.

So on Poulsbo gma500 uses the SGX only for its MMU setup, as on Cedarview, and our driver
redoes all of it when it takes the core (D).

## Events and kicks

- **One kick register.** The SGX535's feature block doesn't set
  `SGX_FEATURE_MULTI_EVENT_KICK`, and `FIX_HW_BRN_22934` would remove it on every listed
  revision anyway (K). Only `EVENT_KICK` at 0x0ac8 (`NOW` b0) exists. gma500 names the same
  `EVENT_KICKER` 0x0ac4 and `EVENT_KICK` 0x0ac8 (L).
- `EVENT_STATUS` 0x012c, `EVENT_HOST_ENABLE` 0x0130, `EVENT_HOST_CLEAR` 0x0134 and the
  `*2` registers at 0x0110 to 0x0118 are where they are on both other cores (K, L).

## The USSE

- The SGX535 runs the USSE, the instruction-set family of the SGX545 and SGX530 (D, from
  [the porting README](../README.md)).
- **2 USE pipes**, as on the SGX530; the SGX545 has 4 (K).
- The SGX545-only features `USE_NO_INSTRUCTION_PAIRING` and `USE_UNLIMITED_PHASES` aren't
  set (K), as on the SGX530.
- F16, C10 and `efo` support is **U**, as on the SGX530.

## The 2D unit

The SGX535 has `SGX_FEATURE_2D_HARDWARE` (K), unlike the SGX530 whose register header has a
2D block but whose feature block doesn't set it.
- Registers: `BIF_TWOD_REQ_BASE` 0x0c88, `2D_BLIT_STATUS` 0x0e04, `2D_VIRTUAL_FIFO_0`/`1`
  0x0e10/0x0e14, `2D_SOCIF` 0x0e18 (free space b0-7), `2D_ALPHA` 0x0e1c (K, L).
- gma500 defines a 2D slave port at 0x4000 (`PSB_SGX_2D_SLAVE_PORT`, L). That it's an
  offset in the 32 KiB SGX window, where commands are written, is a guess (G).
- The command format is in `psb_reg.h` (L): 16 block headers in b28-31 (clip, pattern,
  control, offsets, fence, blit, source, destination and pattern surfaces, palettes,
  flush), 12-bit coordinates and sizes, a 15-bit stride, 28-bit surface addresses, raster
  ops, alpha blend ops, and rotation by 90, 180 and 270 degrees.
- gma500 holds its clock on: `psb_init_pm` sets the 2D field of `CLKGATECTL` to 1,
  disabled gating (L).
- gma500 doesn't use the unit (above). Whether our stack does is a later decision.

## Other features

From `sgxfeaturedefs.h` (K). Set for the SGX535: the 32-bit address space, multiple memory
contexts with 16 lists, 2D hardware, 2 USE pipes, automatic clock gating, the full-range
vertex PDS address in the EDM. Set for the SGX545 and not for the SGX535: volume textures,
the texture-stride extension, host allocation from the DPM, `PDS_DATA_INTERLEAVE_2DWORDS`
and 2 PDS pipes, the monolithic microkernel, external Z, native backward blits, 512 TA
render targets, secondary programs requiring a USE kick, the write-back DCU,
`BIF_WIDE_TILING_AND_4K_ADDRESS`, and multiple event kicks.

### Publishing it

Our patch 0001 gives each chip's `psb_ops` an `sgx` pointer to a `struct gma_sgx_info`
(`core`: the SGX core number), and publishes `gma500_gfx.sgx` only for chips that set it.
Only Cedarview sets it (`.core = 545`); Poulsbo and Oaktrail stay NULL "until an SGX driver
has run on them" (P). For the SGX535 the change is:
- `psb_device.c`: a `psb_sgx_info` with `.core = 535`, and `.sgx = &psb_sgx_info` in
  `psb_chip_ops`. `sgx_aux.c` maps the window from `ops->sgx_offset`, so Poulsbo's 0x40000
  needs no new code (D).
- Oaktrail would be a second entry in `oaktrail_device.c`, at 0x80000, once its own core
  and revision are read.

While an SGX driver is bound, patch 0001 stops gma500's runtime SGX writes: the interrupt
enables at (re)install, and the MMU's directory and flush writes. gma500's load-time setup
(`psb_do_init`, `psb_spank`, `psb_init_pm`: the banks, the reset, the 2D request base, the
directory lists, the 2D clock) runs before the aux device exists (D, P). The SGX driver's
own reset has to replace all of it, and gma500's 2D clock setting is overwritten when the
driver programs `CLKGATECTL`.

## What this means for the stack

- **The core table:** a family with `MULTIPLE_MEM_CONTEXTS`, 16 lists and 32 bits, but no
  `MULTI_EVENT_KICK`. Today's check refuses it for the missing kick. The usable check in
  [single-context.md](../single-context.md) section 1 has to allow "multi-context, single
  kick" as its own case.
- **The kick:** the init kick on `EVENT_KICK` (`regs.event_kick2 = 0`), the single-kick
  part of single-context.md section 4, with the same microkernel question: how the image
  tells the init kick from a CCB kick.
- **The VM, heaps and banks:** as on the SGX545. No shared firmware heaps, no list
  switching by the microkernel, no BRN_28889 split.
- **The register table:** the SGX530's low offsets and field layouts (clock gating, reset,
  ID, event status), the SGX545's BIF and `USE_CODE_BASE` fields, `BIF_CTRL`'s bypass bits
  with the host bit at b16, and `BIF_INT_STAT`'s fields. No `CLKGATECTL2`, no `TIMER`, no
  36-bit register.
- **The platform:** a third gma500 chip entry (above), the shared legacy interrupt, and
  no island to manage.

### Parked

- **gma500's second directory write.** `psb_mmu_set_pd_context()` computes a list
  `hw_context` > 0 as `PSB_CR_BIF_DIR_LIST_BASE1 + hw_context * 4`, so `hw_context` 1
  lands on 0x0c3c, `DIR_LIST_BASE2` in `sgx535defs.h`, not `BASE1`. `psb_mmu_free_pagedir()`
  clears `DIR_LIST_BASE0 + hw_context * 4` = 0x0c88, which is `BIF_TWOD_REQ_BASE` (D,
  from L and K). Both banks are 0, so no requestor reads either list. The clear runs
  at unload (`psb_driver_unload()` frees `pf_pd`) and zeroes the 2D request base, which
  nothing uses by then. On Cedarview the same code writes 0x0c3c and clears 0x0c88, an
  offset the SGX545 header doesn't name; patch 0001 skips the clear while an SGX driver is
  bound (D, P). Worth a short note to the gma500 maintainer someday, once the 535 work has
  hardware behind it. Nothing has been sent.
