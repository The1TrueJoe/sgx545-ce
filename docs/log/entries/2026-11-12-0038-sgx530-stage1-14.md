# SGX530 stage 1, fourteenth attempt: a branch loop doesn't hold the PDS, and 0x0a68 is row-aligned

**Board:** our OMAP3630 test board, openHC on the SD (7.3.3, the 02:16 build). 75 °C
before, 73.5 °C after.

**What ran:** powervr_sgx from sgx530 eedab6be (CI: omap3630 43161799195, powervr-sgx
43161792558 and upstream 43161795584, all green), `allow_unisolated=1 code_base_pads=1
stage1_sweep=1`, with the landing-pad image `sgx530_bases` (f7de7b95…). The normal start is
back to 0x0a6c = 1. The event program is at 0x01404aa0 above `PDS_EXEC_BASE`, so
`PDS_PC_BASE` reads 0x5012a8 for its row 0, 0x5012ac for row 1, 0x5012b0 for row 2 and
0x5012b4 for row 3.

The variants replace the event program with minimal row-aligned programs, built with
docs/PDS.md's SGX545 encodings (BRA = 0x97000000 | target, cc 7; HALT = 0xaf000000):

| # | Variant | Program | If the PDS executes it |
|---|---|---|---|
| 0 | baseline | data row, then MOVS (DOUTU) + HALT | PC on row 1, then idle |
| 1 | program A | data row; row 1: BRA 8, HALTs; row 2: HALTs; row 3: BRA 8 (to itself) | PC leaves row 1 for row 3 (or row 2) and never goes idle |
| 2 | program C | data row; row 1: BRA 4, HALTs; row 2: HALTs | PC leaves row 1 for row 2, then idle |
| 3 | program D, 0x0a6c = 0 | no data; row 0: BRA 8; row 2: BRA 8 (to itself) | PC leaves row 0 for row 2 and stays |
| 4-6 | program A, 0x0a68 low bits 0x1, 0x4, 0xf | as 1 | as 1 |

Then the fault check.

**Results:**

| # | `PDS_PC_BASE`, every 10 ms | 0x0a68 written → read |
|---|---|---|
| 0 | 5012ac 5012ac 5012ac 0 0 5012ac 0 5012ac 0 5012ac | 0x01404aa0 → 0x01404aa0 |
| 1 | f33c 0 0 0 0 0 f33c 5012ac 0 5012ac | same |
| 2 | f33c 0 0 0 0 0 0 0 0 0 (5012ac in the status line after) | same |
| 3 | f33c 0 0 0 5012a8 f33c 5012a8 f33c 0 0 | same |
| 4 | 0 f33c 0 0 0 5012ac f33c 0 5012ac 0 | 0x01404aa1 → 0x01404aa0 |
| 5 | 0 0 0 0 0 f33c f33c 5012ac 5012ac 0 | 0x01404aa4 → 0x01404aa0 |
| 6 | 0 0 5012ac 0 f33c f33c f33c 0 0 f33c | 0x01404aaf → 0x01404aa0 |

- `EVENT_TIMER` stayed 0 throughout. No "not independent" warning.
- The fault check: `BIF_INT_STAT` 0x4004, `BIF_FAULT` 0x0e800000, then "recovered, BIF int
  0x0".
- -ETIMEDOUT, all five modules unloaded, the parent (5000fe00.target-module)
  runtime-suspended.

**Facts (C):**
- **No program's PC ever reached its branch target.** Programs A, C and D only show the row
  they start on (row 1, or row 0 for D), 0xf33c and 0. Rows 2 and 3 (0x5012b0, 0x5012b4)
  never appear.
- **A branch to itself doesn't keep the PDS busy.** With programs A and D, `PDS_PC_BASE`
  goes back to 0 and to 0xf33c between samples, as it does for the baseline's MOVS + HALT.
- **0x0a68's bits 0-3 don't latch.** 0x1, 0x4 and 0xf all read back as 0: the event program
  address is 16-byte aligned, a row. It makes no difference to the PC pattern.
- **Every `PDS_PC_BASE` value seen in attempts 9-14 is a multiple of 4 dwords** (one row),
  0xf33c/0xf35c/0xf75c included.

**What it suggests (G):**
- **The PDS reaches the first code row of the event program and doesn't execute its
  instructions the way the SGX545 would.** Either the SGX530 decodes BRA (and so likely MOVS
  and HALT) differently from PDS.md's SGX545 encoding, or something ends the program at its
  first row before any instruction takes effect.
- **`PDS_PC_BASE` may hold the row the PDS fetched or started at, not a per-instruction PC.**
  Its row-only values fit that. Then attempts 12-14 locate where the PDS starts, and say
  little about how far it gets. Even so, a branch to itself that ran would have kept it
  from going back to 0.
- **The 0xf33c activity is still unchanged by everything we vary.** U.

**Next:** for the microkernel session to design. Candidates: the SGX530's PDS encoding (a
program whose only effect, a DOUT to a register we can read, needs no branch), and a check
of whether `PDS_PC_BASE` ever shows a row past the first one.
