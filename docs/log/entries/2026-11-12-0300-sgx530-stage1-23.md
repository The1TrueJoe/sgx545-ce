# SGX530 stage 1, twenty-third attempt: code base 15 moves the EDM's fetch

**Board:** our OMAP3630 test board, openHC on the SD (7.3.3, the 02:16 build), up 1 min
after the owner's Wi-Fi test, with the owner-confirmed host key. the board lock was held for
the run. 77 °C before, 75 °C after. No hang, no plug cycle.

**What ran:** powervr_sgx from e6fa6cea, built on wip/sgx530-a23 (CI: omap3630 43175024078,
powervr-sgx 43175017937 and upstream 43175020981, all green; modver-check 0 differ), so as
not to cancel attempt 22's CI on sgx530. `allow_unisolated=1 code_base_pads=1
stage1_sweep=1`, with the landing-pad image `sgx530_bases` (f7de7b95…). Part 2 writes 0xa74
= 0x208200. No alias.

**The question:** the DDK runs the SGX530 with kernel code at `PDS_EXEC_BASE` + 0x01400000
(0x0ec00000), but no DOUTU word-0 bit tried reaches it (attempts 21-22). Is there a word-0
segment encoding, or does the EDM use code base 15?

| # | Variant | `BIF_FAULT` |
|---|---|---|
| 0 | baseline: normal word 0, code base 15's address field 0x1d8000 (0x0ec00000 >> 7) | 0x0d800000 |
| 1 | word 0 = temps \| 0x100008 | 0x0d808000 |
| 2 | word 0 = temps \| 0x7 | 0x0d808000 |
| 3 | word 0 = temps \| 0xf80000 | 0x0d808000 |
| 4 | normal word 0, code base 15's address field 0 | **0x00000000** |
| 5 | normal word 0, code base 15's address field 0x100000 (0x08000000 >> 7) | **0x00000000** |

- Every variant faulted with `BIF_INT_STAT` 0x4004 (requestor b2) and recovered. The DM
  field of code base 15 kept its usual value.
- No variant ran the ladder or reached a pad. The fault check: 0x4004 at 0x0e800000,
  recovered. -ETIMEDOUT, all five modules unloaded, the parent runtime-suspended.

**Facts (C):**
- **Code base 15's value changes where the EDM's task faults.** With its address field
  0x1d8000 it faults at 0x0d800000. With 0 or with 0x100000 it faults at 0x00000000.
- **The three word-0 segment guesses behave like every other word with b0-3 ≠ 0xf:**
  `PDS_EXEC_BASE` + 0x8000.
- **With the address field at 0x100000, the fault isn't at 0x08000000,** the address that
  field gives as an absolute << 7.

**What it suggests (G):**
- **The EDM's code address goes through code base 15, but not as `field << 7` on its own.**
  The baseline's field 0x1d8000 would give 0x0ec00000, yet the fault is at 0x0d800000, and
  0x100000 gives 0, not 0x08000000. The field's width, shift or relation to
  `PDS_EXEC_BASE` differs from the SGX545's, or its DM bits change how it's read.
- **A fault at 0 for two different values suggests some values aren't taken at all.** That
  could be a field out of range, or a DM that doesn't match.

**Next:** for the microkernel session. Candidates are code base 15's DM field (0, 1, 2) and
more address-field values, each read by its fault page.
