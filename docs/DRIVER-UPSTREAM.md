# The gallium driver and winsys: upstream readiness (audit, 2026-11-01)

This checks `mesa/src/gallium/drivers/sgx545` (the driver, 4.0k lines) and
`mesa/src/gallium/winsys/sgx545/drm` (the winsys, 3.6k lines) against
`docs/CLEANROOM.md` and AGENTS.md §3.5-§3.7, the way `docs/COMPILER-UPSTREAM.md`
checks the compiler. It covers `um-re` at the commit that adds this file.

For each piece of hardware knowledge the code uses, it says:

- which `docs/` section describes it;
- how that section knows it, using CLEANROOM's tags: `static` (read from a
  decompile or the DDK's data), `capture` (DDK captures and diffs),
  `hardware` (our own frames or pokes on an EA), `oracle`;
- how the code was written: **doc** (from the doc section, which already said
  everything the code uses) or **static** (from the decompile, with the doc
  written alongside or after it, or not at all);
- what has to happen before upstream.

## 0. Who wrote this code

Every line of the driver and winsys was written by sessions that also read
the DDK decompiles: libGLESv2, libsrv_um, libusc and libsrv_init.

- **sgxgen (`tools/gen`).** The frame-from-scratch session wrote it
  (88dfc68, 2026-10-28), and the winsys is its C core. That session wrote
  STATE.md and PDS.md from decompiles and captures in the days before, and
  wrote the generator from them.
- **The driver.** This session (the Mesa driver session) wrote it, and it
  read decompiles while doing so.

None of this code is clean-room implementation in CLEANROOM's sense. The
plan for each piece is the question:

- **Rewrite from the doc as it stands.** The doc already holds every fact
  the code uses, with capture or hardware evidence. A clean session can write
  the code from it, and the black-box suites validate the result.
- **Doc fix first.** The code knows something the doc lacks, or the doc's
  only source is static. The spec side fixes the doc (with an experiment where
  the fact is static only). Then a clean session rewrites the code from it.
- **Doesn't go upstream.** This covers DDK compatibility and the
  services/microkernel interface. That part is replaced by the new kernel
  driver and uAPI (M2/M3), or it disappears.

## 1. Licensing (§3.5)

- **Driver: clean.** It sees the winsys only through `sgxws.h`: GL-level
  state, the hardware's words as `docs/` describes them, and opaque handles.
  Its meson dependency (`idep_sgx545_ws`) carries no kernel include path and no
  kernel defines.
- **Winsys: not upstreamable as it is.** `sgx545_frame.c`/`.h` include
  libpvr's `pvr.h`, whose `abi/` is generated from the GPL kernel headers. It
  also lays out microkernel structures by their GPL-header offsets:
  `SGXMKIF_CMDTA`, `PVRSRV_SYNC_DATA`, `SGXMKIF_HWDEVICE_SYNC_LIST`. That is
  correct for the overlay and wrong for Mesa. M3 replaces this layer (§5).
- **Generated code with a forbidden input.** `sgx545_usse_progs.h` is
  regenerated by `mesa/build.sh` from `tools/gen/mkusse.py`, which assembles
  through `tools/isa/hw.py`. `hw.py` was typed while reading libusc
  (COMPILER-UPSTREAM §2.1). The Mesa build therefore depends on a table the
  implementation side may not read (§3.4).
- **Headers.** Every file now carries `Copyright © 2026 Joseph Telaak` and
  `SPDX-License-Identifier: MIT`. `mkusse.py` writes them into the generated
  header.
- **Decompile addresses removed.** `FUN_…` names, libGLESv2/libsrv_um addresses
  and "the DDK's 0x1e970 layout" comments are removed from `mesa/`. The
  comments now cite `docs/` sections. The addresses still live in `docs/`,
  where provenance belongs.

## 2. The driver (`drivers/sgx545`)

Most of the driver is Mesa plumbing with no hardware knowledge in it:

- screen and caps;
- resources and transfers;
- CPU vertex gathering and the vertex cache;
- index handling;
- the CPU blit path;
- fences;
- the debug-option table.

## 4. The winsys: services and microkernel interface (doesn't go upstream)

This is what `pvrsrvkm` and its microkernel expect from a client. A DRM
driver with an open microkernel (M2) owns this, or does it differently. None
of it moves to Mesa as written. The kernel and microkernel sessions write
their equivalents on the implementation side from STATE.md §1/§6 and
UKERNEL.md.

| piece | where | docs/ | doc's evidence | note |

## 5. What to do before upstream

In order:

1. **Doc fixes the spec side owes.** This session can do them, being on the
   spec side.
   - The pixel-event inputs (§3), so the program can be written new rather
     than transcribed.
   - `emitpix` in ISA.md.
   - The TA terminate, from a hardware test of what it needs.
   - The VDM state info word's rotation, from a hardware test.
   - The background block's fields.
   - DOUTD's 16-dword limit and b22-24 rule.
   - Projected samples and DOUTI source 0x22.
   - The discard's sa3/sa4 table.
   - The prologue: is it needed?
   - The fixed programs' source text and purpose.
   - Minimum alignments.

   Each fact gets its tag. A static-only one gets an experiment.
2. **Move every hand-encoded USSE word into the compiler.** The winsys
   writes instruction words in raw hex in five places: the blend, the
   colour mask, discard's `pcoeff`/`atst8`/`phas`, the EOT's
   `limm`/`emitpix` and the vertex wrapper. Once the compiler's encoder is
   the clean isaspec one (COMPILER-UPSTREAM §2.4/§4), these become compiler
   output. The fixed programs become assembly text assembled at build time.
   `sgx545_usse_progs.h` and `mesa/build.sh`'s call into `tools/` go away.
3. **Drop the USP path from the driver.** Take `struct sgx_shader` from the
   compiler (COMPILER-UPSTREAM §3). Dependent samples come out of the
   compiler finished.
4. **Clean rewrite.** A session that never read the decompiles writes the
   M3 driver from the docs. That covers the command-word layer of §3 and the
   driver facts of §2 marked "rewrite from doc". It sits on the new uAPI
   rather than `sgxws.h`'s services implementation. `sgxws.h`'s shape
   (GL-level state in, words out) is a reasonable starting interface, and it
   contains no services material.
5. **Validation.** Done black-box, as CLEANROOM says:
   - the A/B suites (`mesa/tests`, pixel-exact against the DDK);
   - the gl4es/Minecraft bench;
   - dEQP-GLES2 under deqp-runner with the `ci/` expectation files (M0);
   - `tools/gen/cmpcap.py`-style structure diffs of a frame against a DDK
     capture.

   Mismatches go back to the spec side as doc fixes.

## 6. Not covered

- `src/egl/drivers/dri2/platform_fbdev.c` is EGL plumbing with no hardware
  knowledge. Mesa has no fbdev platform, so it stays openHC's.
- The tests (`mesa/tests`) and the dEQP rig hold no proprietary material.
  `run-deqp.sh ddk` runs the DDK as an oracle, which CLEANROOM allows; no
  shipping test depends on it.
