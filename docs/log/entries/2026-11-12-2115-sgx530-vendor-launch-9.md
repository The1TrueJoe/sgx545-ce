# SGX530 vendor-launch (vendor-setup §9): the task launches, and the write gates move

**Board:** our OMAP3630 test board, up 12 h 33 min (the same boot as attempts 40-47, T1 and
T2), the owner-reread pinned host key (SSH connected on the pinned ED25519;
`SHA256:7a+D6jQmYwIIrhROaddwQ9OTMcvirgL2pY/59X4ba9M`, the owner's on-board reading, after my
scratchpad was lost), the board lock held 21:15:40-21:17:26 UTC. 75-77 °C. No hang, no plug
cycle.

**What ran:** powervr_sgx from claude/sgx530-gap19-tests f5f00ec6 (CI: omap3630 43306518522,
green), all four loads with `allow_unisolated=1 stage1_vlaunch=1`. The modver reference tree
was lost with the scratchpad; the board SD image is unchanged (owner: a36033a), the omap3630
CI builds against that exact config and compiler, and the kernel has `CONFIG_MODVERSIONS`, so
`insmod` enforces the symbol versions and would reject a mismatch without touching the GPU.
Every image's SHA-256 matches the microkernel session's list.

`stage1_vlaunch` applied: the event PDS base read back the §9 address, and the event control
words read `0xa6c` = 3, `0xa70` = 0x00013d01 (the vendor values, §5/§7). The event DOUTU is the
three fixed words (0x0020000f, 0x04000000, 1) in the 8-word data interleave (word 2 at memory
word 8), §2/§3. The kernel data arena is mapped **with** EDMPROTECT (§6).

- In every load the USE went busy (0x00110000) after the kick and stayed busy through 500 ms:
  **the task runs.**
- **No load faulted at code base 0 (0x0f400000).** Every pre-§9 DOUTA-layout attempt (46, 47)
  started the task at code base 0; §9's 8-word interleave and launch words do not.
- -ETIMEDOUT for each load; all modules unloaded and the parent runtime-suspended.

**Facts (C):**
- **§9's launch starts the task.** The 8-word interleave with DOUTU words
  (0x0020000f, 0x04000000, 1) launches the task at the microkernel's code, not code base 0.
  This closes the pre-§9 launch failure (the DOUTU-after-layout gate).
- **The faulting address changed from the pre-§9 leftovers.** `aluwr` faults at 0x0fa93000,
  neither the old r5 leftover (0x0c004000) nor the expected OR result (0x0fd7d000). Both
  `aluwr` and `aluwr_pa0w` fault at the same 0x0fa93000.
- **The store faults under EDMPROTECT.** `stout` gives `BIF_INT_STAT` 0x4004 and
  `BIF_FAULT` 0x02d3b000, and neither value reaches either arena (0 scan hits). Before §9
  (arena mapped without EDMPROTECT) the store didn't fault but didn't commit; with EDMPROTECT
  back on it faults.

**What it suggests (G):**
- The write-retire decode is the microkernel session's: whether 0x0fa93000 is a new register
  leftover under §9's launch or a retired write to a different value is theirs to settle from
  the register-leftover map. The bisect (word 2 → word 1 → word-0 bit 21 → `0xa70`) runs from
  here if a write retired.
- That the task launches at all under §9, where the open-microkernel launch words started it at
  code base 0, is the §9 result that matters most: the 8-word interleave and the vendor DOUTU
  words are what the 530 needs to launch an EDM task.
