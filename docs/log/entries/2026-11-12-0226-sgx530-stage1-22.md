# SGX530 stage 1, twenty-second attempt: the + 0x8000 comes from DOUTU b0-3 ≠ 0xf

**Board:** our OMAP3630 test board, openHC on the SD (7.3.3, the 02:16 build), up 19 min,
the owner-confirmed host key, `hc250.lock` held. 77 °C before, 75 °C after. No hang, no
plug cycle.

**What ran:** powervr_sgx from sgx530 b49aaf7c (CI: omap3630 43174455569, powervr-sgx
43174448939 and upstream 43174452177, all green; modver-check 0 differ),
`allow_unisolated=1 code_base_pads=1 stage1_sweep=1`, with the landing-pad image
`sgx530_bases` (f7de7b95…). Part 2 writes 0xa74 = 0x208200.

**The question:** in the twenty-first attempt, the temporaries plus any one of b0-b3 or
b19-b23 put the DOUTU's fetch at `PDS_EXEC_BASE` + 0x8000, but the normal word 0 put it at
+ 0. The normal word sets b0-3 = 0xf and b27. Which of those takes the 0x8000 away?

**Results:** every variant faulted with `BIF_INT_STAT` 0x4004 (requestor b2) and recovered.
No variant ran the ladder or reached a pad.

| Word 0 (with the temporaries, 6 << 24) | `BIF_FAULT` − `PDS_EXEC_BASE` |
|---|---|
| normal (b0-3 = 0xf, b27) | 0 |
| nothing else | 0x8000 |
| b0-3 = 0xf | **0** |
| b27 | 0x8000 |
| b0-3 = 0xf, b27 | **0** |
| b0-3 = 1, 2, 4 or 8 | 0x8000 |
| b19, b20, b21, b22 or b23 | 0x8000 |

The fault check: 0x4004 at 0x0e800000, recovered. -ETIMEDOUT, all five modules unloaded, the
parent runtime-suspended.

**Facts (C):**
- **b0-3 = 0xf puts the fetch at `PDS_EXEC_BASE` + 0. b0-3 = 0, 1, 2, 4 or 8 puts it at
  + 0x8000.** This repeats the twenty-first attempt's values for 1, 2, 4 and 8.
- **b27 and b19-b23 don't move the fetch,** alone or with b0-3 = 0xf.
- **So the twenty-first attempt's + 0x8000 came from b0-3 ≠ 0xf, not from the bit it set.**
  Its offsets for b4-b7 and b16-b18 were measured with b0-3 = 0. Over + 0x8000 they still
  give b16-b18 = 0x1000-0x4000 and b4-b7 = 0x8000-0x40000.

**What it suggests (G):**
- **b0-3 is not a linear address field:** 1, 2, 4 and 8 land on the same page. It reads like
  a selector where 0xf picks a base at `PDS_EXEC_BASE` + 0 and the values tried pick another
  0x8000 above it. The code bases we program (0-14 at the pads, 15 at the kernel code heap)
  don't match either.
- **No bit tried so far reaches the kernel code heap.** Attempt 23 tests segment encodings
  and code base 15's value directly.
