# SGX530 stage 1, eighteenth attempt: 0x0a74 = 0x208200 makes the PDS execute

**Board:** our OMAP3630 test board, openHC on the SD (7.3.3, the 02:16 build), up 18 min,
the host key the owner confirmed on the board. 75 °C before, 73.5 °C after. No hang, no plug
cycle.

**What ran:** powervr_sgx from sgx530 453ee1da (CI: omap3630 43170158591, powervr-sgx
43170151244 and upstream 43170155024, all green; modver-check 0 differ),
`allow_unisolated=1 code_base_pads=1 stage1_sweep=1 stage1_vendor=1`, with the landing-pad
image `sgx530_bases` (f7de7b95…). The coordinator approved the writes to unnamed SGX530
offsets under the standing go: exactly 0xabc, 0xa00, 0xa74, 0xa78, 0xaac, then 0xa7c and
0xa80, at the SGX545's values. Each is read before the write and put back after its variant.
The recovery reset comes first, and the sweep stops at the first hang.

**Why:** the seventeenth attempt showed the PDS forms the start address and stops before any
fetch. The candidate was the SGX545 vendor's part-2 writes in the PDS and event block, which
the SGX530's part 2 skips.

**The variants**, each alone and with F1 (the sixteenth attempt's DOUTD from 0x0e840000):
0xabc = 0xe; then 0xa00 = 0x7c000, 0xa74 = 0x208200, 0xa78 = 0x2c and 0xaac = 0x45, one at a
time; then those four together. 0xa7c = 0 and 0xa80 = 0 were to run last, each alone, only
if nothing before them faulted.

**Results:**

| # | Variant | Write: before → wrote → after | Fault |
|---|---|---|---|
| 0 | baseline | none | none |
| 1, 2 | 0xabc, alone / F1 | 0 → 0xe → 0xe | none |
| 3, 4 | 0xa00, alone / F1 | 0 → 0x7c000 → 0x7c000 | none |
| 5 | **0xa74, alone** | 0 → 0x208200 → 0x208200 | **`BIF_INT_STAT` 0x4004, `BIF_FAULT` 0x0d800000** |
| 6 | **0xa74, F1** | same | **`BIF_INT_STAT` 0x4002, `BIF_FAULT` 0x0e840000** |
| 7, 8 | 0xa78, alone / F1 | 0 → 0x2c → 0x2c | none |
| 9, 10 | 0xaac, alone / F1 | 0 → 0x45 → **0** | none |
| 11 | the four, alone | as above | 0x4004 at 0x0d800000 |
| 12 | the four, F1 | as above | 0x4002 at 0x0e840000 |

- Every fault recovered with the reset ("recovered, BIF int 0x0").
- 0xa7c and 0xa80 were skipped by the rule: earlier variants had faulted.
- With 0xa74 set, `PDS_PC_BASE` read 0 at every sample. Without it, the usual start row
  0x5012ac and a third value, 0x93e700 here (0x136500 on the same boot in the seventeenth
  attempt).
- `EVENT_TIMER` stayed 0: no task ran the ladder.
- The fault check: 0x4004 at 0x0e800000, recovered. -ETIMEDOUT, all five modules unloaded,
  the parent runtime-suspended.

**Facts (C):**
- **Without 0x0a74 = 0x208200 the SGX530's PDS doesn't fetch the event program. With it, it
  does, and it executes F1's DOUTD:** the fault is at exactly F1's source, 0x0e840000.
- **So the SGX545's MOVS-to-DOUTD encoding (docs/PDS.md) works on the SGX530,** at least for
  DOUTD with the sources, interleave and control word F1 uses.
- **The DOUTD's read uses BIF requestor b1** (0x4002). The kicker read and the fault at
  0x0d800000 use b2 (0x4004).
- **With 0xa74 set, the normal entry program (MOVS DOUTU + HALT) faults at 0x0d800000,
  `PDS_EXEC_BASE` + 0,** with requestor b2. Nothing is mapped at the PDS pixel heap's base.
- **0xabc, 0xa00, 0xa78 and 0xa74 latch the SGX545's values. 0xaac reads back 0.** All read
  0 before the write.
- **0xabc, 0xa00, 0xa78 and 0xaac alone change nothing visible.**

**What it suggests (G):**
- **0x0a74 is a PDS or event setup the dispatch waits on,** maybe a data-store or
  thread allocation. It's what attempts 1-17 lacked.
- **The fault at `PDS_EXEC_BASE` + 0 with the entry program fits the DOUTU's task start
  going wrong:** a USSE or event-side fetch at an address formed from 0, with the same
  requestor as the event kicker read. Which address the DOUTU word was meant to give is the
  next question.

**Next:** for the microkernel session. Part 2 of the SGX530's init should write 0xa74 =
0x208200; that's a driver change once the design is agreed.
