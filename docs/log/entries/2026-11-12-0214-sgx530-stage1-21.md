# SGX530 stage 1, twenty-first attempt: DOUTU word 0's bits by the fault page

**Board:** our OMAP3630 test board, our kernel on the SD (7.3.3, the 02:16 build), up 7 min after
the owner's Wi-Fi test, with the owner-confirmed host key. the board lock was held for the
run. 75 °C before and after. No hang, no plug cycle.

**What ran:** powervr_sgx from sgx530 2bf15841 (CI: omap3630 43173008667, powervr-sgx
43173001914 and upstream 43173005068, all green; modver-check 0 differ),
`allow_unisolated=1 code_base_pads=1 stage1_sweep=1`, with the landing-pad image
`sgx530_bases` (f7de7b95…). Part 2 writes 0xa74 = 0x208200. Attempt 20 (the page-0 alias)
didn't run: its CI was cancelled when this build was pushed.

**The question:** the DOUTU's task fetches its code from `PDS_EXEC_BASE` + an address
(nineteenth attempt). Which bits of DOUTU word 0 move that address, and by how much?
- **Baseline:** the normal word 0.
- **Then:** word 0 = the temporaries field (6 << 24) | one bit b, for b = 0-23, low bits
  first.
- **After each variant:** `BIF_INT_STAT` and `BIF_FAULT` are logged, then the recovery reset
  runs.

**Results:** every variant faulted with `BIF_INT_STAT` 0x4004 (requestor b2) and recovered.
No variant ran the ladder or reached a pad (`EVENT_TIMER` 0).

| Word 0 | `BIF_FAULT` | − `PDS_EXEC_BASE` |
|---|---|---|
| normal (baseline) | 0x0d800000 | 0 |
| temps \| b0, b1, b2 or b3 | 0x0d808000 | 0x8000 |
| temps \| b4 | 0x0d810000 | 0x10000 |
| temps \| b5 | 0x0d818000 | 0x18000 |
| temps \| b6 | 0x0d828000 | 0x28000 |
| temps \| b7 | 0x0d848000 | 0x48000 |
| temps \| b8-b15 (each) | 0x0d808000 | 0x8000 |
| temps \| b16 | 0x0d809000 | 0x9000 |
| temps \| b17 | 0x0d80a000 | 0xa000 |
| temps \| b18 | 0x0d80c000 | 0xc000 |
| temps \| b19-b23 (each) | 0x0d808000 | 0x8000 |

The fault check: 0x4004 at 0x0e800000, recovered. -ETIMEDOUT, all five modules unloaded, the
parent runtime-suspended.

**Facts (C):**
- **With the temporaries and any one of b0-b3, b8-b15 or b19-b23, the fetch faults at
  `PDS_EXEC_BASE` + 0x8000.** The normal word 0 faults at + 0.
- **Over that + 0x8000, b4-b7 add 0x8000, 0x10000, 0x20000 and 0x40000,** and b16-b18 add
  0x1000, 0x2000 and 0x4000.
- **No single bit reached the kernel code heap** (+ 0x01400000) or started the image.
- **Every fault came from requestor b2 and cleared with the recovery reset.**

**What it suggests (G):**
- **b16-b18 and b4-b7 carry address bits:** bits 12-14 and 15-18 of the offset. Bits below
  4 KiB can't be seen at page resolution.
- **The + 0x8000 against the normal word's + 0 means a bit the normal word sets** (b27, or
  the code-base field b0-3 = 0xf) **takes 0x8000 away, or the field is read differently**
  when those are set. Which one is the next question.
- **No bit above b7 moved the fetch past + 0x48000,** so the offset field may top out near
  512 KiB from `PDS_EXEC_BASE`. The kernel code heap at + 0x01400000 would then be out of
  reach, and the heap layout, not the DOUTU, would have to move.
