# powervr_sgx runs transfer jobs: blits pixel-exact on the first boot

M2 item 3. CE5310 board RAM boot of 5c6fd45, 2026-11-03 ~04:03 UTC, DDK microkernel, nothing
flashed, no power-cycle.

## What the driver does

A transfer context gets a kernel-built firmware half:
- the 0xb4-byte HW transfer context `{1, 0, PD, ring, ring control, ..., PID at 0x2a}`, as
  `SGXCreateTransferContext` builds it (TEX.md 10);
- a 0x104c8-byte command ring and its control;
- a completion sync.

A transfer job's `CMD_TRANSFER` stream goes through the stream decoder and the
cross-field check, and must be mapped in the VM. The kernel writes the 0x1c0-byte
command from it (UAPI.md 3.5):
- words 0-16, with word 15 = the PDS pixel heap base, never the client's;
- +0xa4 = 0x1c0;
- +0xa8 = 8 for `DST_TWIDDLED`;
- +0x194 = 0x07c00000.

In `SGXMKIF_TRANSFERCMD_SHARED` it names one destination sync, its own. Then it sends a
kernel-CCB `TRANSFER` command (data[1] = the HW transfer context). The job is done when
the microkernel sets that sync's write-ops-complete to the pending value plus one.

The shared command's layout comes from the GPL kernel's `sgx_mkif_km.h`
(`SGX_MAX_SRC_SYNCS` 8, `SGX_MAX_DST_SYNCS` 1):

| offset | field |
|---|---|
| +0xac | the shared command, starting with `ui32NumSrcSyncs` |
| +0x130 | `ui32NumDstSyncs` |
| +0x134 | `asDstSyncs[0]` |
| +0x164 | `ui32NumStatusVals` |
| +0x168 | `sCtlStatusInfo[0]` |

So UKERNEL.md's "destination sync at 0x168/0x16c" is really the status word. The doc
is corrected, and the open microkernel has to set the destination sync as well
(UKERNEL.md 10).

## The test

`drm/tests/powervr_sgx_blit.c` uses `tools/tex`'s blit builder (`sgxtex`, proven on the
CE5300 board through the DDK, TEX.md 10). It writes the client side into BOs mapped in the VM:
- the background block;
- the background pixel program;
- the end-of-tile program;
- the context's secondary and pixel-event programs and its shaders.

Every blit is then a `SUBMIT_JOBS` transfer job. The source is a 64x64 BGRA8888 pattern
the CPU writes; every destination pixel is checked against what it must be:

```
copy  done, 4096/4096 pixels right     strided -> strided
down  done, 4096/4096 pixels right     strided -> twiddled (upload), twiddled -> linear: the pattern again
mipl  done, 1024/1024 pixels right     twiddled -> 32x32, LINEAR: the box filter, bit for bit
firmware running: 1 lost: 0 resets: 0 irqs: 4      (one SW_EVENT per blit)
```

Then:

| run | result |
|---|---|
| 50 rounds (200 blits) | all right |
| 40 rounds (160 blits), concurrent with another process rendering 40 frames on two render contexts | all right; 40/40 frames |
| the uAPI suite, now 28 tests with `submit-transfer-invalid` (every `CMD_TRANSFER` rejection, plus transfer/render context mismatches) | 28/28 |
| two forced TA-fault hangs (`SGXGEN_FAULT=1`), each followed by 5 rounds of blits | both restarted in place, every blit right |

No resets, apart from the two forced hangs.
