# SGX530 stage 1, sixteenth attempt: no fault from a DOUTD or a far branch

**Board:** our OMAP3630 test board, our kernel on the SD (7.3.3, the 02:16 build), freshly
rebooted. 75 °C before and after.

**What ran:** powervr_sgx from sgx530 e102d15a (CI: omap3630 43164878925, powervr-sgx
43164872927 and upstream 43164875911, all green; modver-check 0 differ),
`allow_unisolated=1 code_base_pads=1 stage1_sweep=1`, with the landing-pad image
`sgx530_bases` (f7de7b95…).

**Why:** every `PDS_PC_BASE` value so far is a program's start row, 0, or the drifting
0xf3xx/0xf7xx value. That fits "the start address of the last program dispatched" (G), not a
running PC. If so, attempts 14 and 15 couldn't have shown a branch target even if the branch
ran. This attempt detects execution with the fault path instead: it is calibrated (tenth
attempt), and a fault at an address only our instruction touches would prove the
instruction ran.

**The programs:** a data row, then row 1 (0x0a6c = 1), in docs/PDS.md's SGX545 encodings.
- **F1, a DOUTD read.** The data row is [0x0e840000, 0, 0, 0]: the address, and control 0
  (one dword) under either interleave. 0x0e840000 is in the hole past the PDS vertex heap,
  unmapped, and isn't the fault check's 0x0e800000. Row 1: MOVS dest 3 (DOUTD) with ds0[0],
  ds1[1], ds0[1], ds0[0], then HALT. The expected `BIF_FAULT` page is 0x0e840000.
- **F2, a branch.** Row 1: `97004000` (bra #0x4000), then three HALTs. The target is the
  first code word + 0x10000 = 0x0ec14ab0, past the code arena (+0xe000) and the PD table
  (+0xf000-0x10000). The expected `BIF_FAULT` page is 0x0ec14000.
- **Each under 0x0a70 = 6 and 16.** After each variant the driver checks `BIF_INT_STAT`. If
  it shows a fault, the driver logs `BIF_FAULT` and runs the recovery reset before the next
  variant. The event data words are now read back.
- **The fault check last.**

**Results:**

| # | Variant | 0x0a6c, 0x0a70 read | `PDS_PC_BASE`, every 10 ms | BIF int at 100 ms |
|---|---|---|---|---|
| 0 | baseline | 0x1, 0x6 | 0 f75c 5012ac 0 0 f75c 0 0 0 5012ac | 0 |
| 1 | F1, 6 | 0x1, 0x6 | 0 0 0 0 f75c 5012ac 0 0 0 f75c | 0 |
| 2 | F1, 16 | 0x1, 0x10 | 0 f75c 5012ac 0 5012ac f75c 0 5012ac 0 0 | 0 (req 0x2) |
| 3 | F2, 6 | 0x1, 0x6 | 5012ac f75c 0 0 0 5012ac 0 f75c 0 0 | 0 (req 0x2) |
| 4 | F2, 16 | 0x1, 0x10 | f75c 0 0 0 5012ac f75c 0 0 0 5012ac | 0 |

- No variant logged a fault, so no recovery ran between variants.
- `EVENT_TIMER` stayed 0. No "not independent" warning.
- The fault check: `BIF_INT_STAT` 0x4004 at every sample, `BIF_FAULT` 0x0e800000, then
  "recovered, BIF int 0x0".
- -ETIMEDOUT. All five modules unloaded, the parent runtime-suspended.

**Facts (C):**
- **0x0a70 latches what's written** (6 and 0x10 read back), and so does 0x0a6c (1).
- **Neither F1's DOUTD nor F2's branch faulted**, under either 0x0a70. An unmapped access
  faults on this core and the fault stays until the reset: the fault check shows 0x4004 at
  every sample over 100 ms. So no access reached 0x0e840000 or 0x0ec14000.
- **`PDS_PC_BASE` showed the start row (0x5012ac) for F1 and F2,** as for every program
  before. The third value is 0xf75c this time.

**What it suggests (G):**
- **The PDS doesn't execute our first code row as the SGX545 would:** neither a MOVS to DOUTD
  nor a BRA takes effect. With the start row seen in `PDS_PC_BASE`, it either never executes
  the instruction or decodes it as something else.
- **One reading isn't ruled out:** a BRA whose target field is narrower on the SGX530.
  0x4000 might then wrap to an address inside the mapped arena, with no fault. F1 doesn't
  have this problem.
- **`BIF_MEM_REQ_STAT` 0x2 at the end of variants 2 and 3** (also seen in the fourteenth
  attempt): an outstanding request of some kind. U.
