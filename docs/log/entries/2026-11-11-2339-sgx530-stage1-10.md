# SGX530 stage 1, tenth attempt: no task through any code base, and the fault path works

**Board:** our OMAP3630 test board, openHC on the SD (7.3.3, the 02:16 build). 75 °C
before, 73.5 °C after.

**What ran:** powervr_sgx from sgx530 51eb8ef1 (CI: omap3630 43155365069, powervr-sgx and
upstream green), `allow_unisolated=1 code_base_pads=1 stage1_sweep=1`, with the landing-pad
image `sgx530_bases` (f7de7b95…, event program at code offset 0x4aa0).
- **The pads.** Code bases 0-14 point at pads at kernel code + 0x4380 + 0x80·n. Pad n writes
  `EVENT_TIMER` = 0xc00 + n. Data masters as usual for variants 0-12; all 3 for 13-17.
- **The variants.** The ninth attempt's 13, plus five with the pads at DM 3: alone, with
  data 2, with word 1 = 0, with base-15 DM 2, and with data 2 + word 1 = 0.
- **The fault check last.** `EVENT_KICKER` at 0x0e800000 (the layout's hole below the kernel
  code heap), a kick, BIF registers every 10 ms, then the recovery reset.

**Results:**
- **No variant runs any of our code.** `EVENT_TIMER` stayed 0 in all 18: no 0xa5a and no
  0xc0n. No "not independent" warning.
- **`PDS_PC_BASE` cycles as in the ninth attempt.** It reads 0x5012ac/0x5012b0 (× 4 =
  0x014044b0, the event program's offset 0x01404aa0 + 0x10, and the next instruction),
  0xf33c, and 0.
- **The fault check:**

  ```
  fault check, EVENT_KICKER 0x0e800000: BIF int 4004 (at every sample)
  fault check: BIF fault e800000 (at every sample), req 0
  fault check: recovered, BIF int 0x0
  ```

- The probe then failed with -ETIMEDOUT. All five modules unloaded and the ti-sysc parent
  runtime-suspended.

**Facts (C):**
- **The SGX530 reports BIF faults.** An unmapped `EVENT_KICKER` gives `BIF_INT_STAT` 0x4004
  (fault field b0-13 = 0x4, plus b14) and `BIF_FAULT` = the address. So "no fault" in
  attempts 1-10 means no access went to an unmapped address, which supports what attempts
  2-9 inferred from it.
- **A kick makes the GPU read the event-kicker word** at `EVENT_KICKER`'s address. That fits
  the kicker increment's effect in attempt 8.
- **The recovery reset clears such a fault.** BIF int was 0 after it, with no page-fault
  rounds logged.
- **No task runs through code bases 0-14 either, with either data master.** With attempts 4
  and 9, no USSE task starts anywhere we can see: not at base 15, not at the code-base unit
  aliases, not through the other bases.
- **The third `PDS_PC_BASE` value moves with the image:** 0xf75c (diag), 0xf35c (probe),
  0xf33c (bases). U.

**What's left (G):** the PDS runs the event program and doesn't start a task the USSE
runs, under every DOUTU and code-base change tried. The microkernel session's next
suspect is the MOVS itself: which data words reach the DOUTU. Its proposal is a program
that sends the same DOUTU word in all four MOVS slots.
