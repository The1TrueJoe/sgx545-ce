# SGX530 stage 1, sixth attempt: the event program as an offset from PDS_EXEC_BASE

**Board:** our OMAP3630 test board, the same SD boot as the fifth attempt (7.3.3, the
02:16 build). 75.0 °C before, 73.5 °C after, thermal zone enabled.

**What ran:** one attempt.
- powervr_sgx from sgx530 0f8a6211, built by `powervr-sgx-omap3630` run 43143700491.
  powervr-sgx and upstream were green on the same head. `modver-check.py`: 0 differing
  CRCs.
- **The one change from the fifth attempt:** 0x0a68 takes the event program's offset from
  `PDS_EXEC_BASE`, not its address: 0x0ec04340 − 0x0d800000 = 0x01404340.
- Carried over: TI's heap layout, the 24-temporary entry DOUTU, and the diagnostic image
  (845463a3…), with `allow_unisolated=1` and no probes.

All five modules unloaded and the ti-sysc parent runtime-suspended.

**Result: the ladder's "all 0" row again.** The offset was taken (it read back). Even so,
none of the microkernel's code ran: `EVENT_TIMER` stayed 0.

**Facts (C):**
- `PDS_PC_BASE` and `PDS` stay 0 before and after the kick.
- After the kick, the USE clocks are on and the BIF reads come and go (2, 0, 1, 2, 2).
  There's no fault and no event bit, as in attempts 2-4.

**What it rules out, with attempts 1-5:**
- Attempts 1-4 wrote 0x0a68 as an absolute address below 2^26, with kernel code below
  `PDS_EXEC_BASE`.
- Attempt 6 wrote an offset, with kernel code above it, as the DDKs lay it out.
- Neither started the microkernel. So the event-program address isn't the only block, in
  either reading.

**What's left** (all G, none named in any GPL source): the runbook's order.
1. 0x0a6c/0x0a70, the event program's two data words (1, 6).
2. DOUTU word 1 (2).
3. The MOVS selects.
4. The event-program enable value at 0x0a58 (0x2204b00f, the SGX545's). It's also a guess
   for the SGX530, including which of its bits, if any, admits the kick's event.
