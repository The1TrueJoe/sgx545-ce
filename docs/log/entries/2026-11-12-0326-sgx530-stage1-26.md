# SGX530 stage 1, twenty-sixth attempt: the real image faults on a data read, the phas-first probe on a fetch

**Board:** our OMAP3630 test board, openHC on the SD (7.3.3, the 02:16 build), up 27 min,
the owner-confirmed host key, the board lock held for both loads. 77 °C before, 75 °C after.
No hang, no plug cycle.

**What ran:** powervr_sgx from sgx530 fd97aabe (the >> 8 code-base unit; modver-check 0
differ), `allow_unisolated=1` only, loaded twice. The images were built from the microkernel
session's branch (a0861f83) with `ukernel/build.py` and packaged by `drm/tools/mkukfw.py`.
- **Part 1, the real SGX530 microkernel** (`cores/sgx530.py`): 17088 bytes, sha256 2d79b7f2…,
  packaged 34aa17c4… (crc 0x77f96757, patches 0x8 ← the TA/3D control block, 0x10 ← the PD
  table). Its event entry starts with `phas.i`.
- **Part 2, the phas-first probe** (`cores/sgx530_usse_phas.py`): 112 bytes, sha256
  51fd3545…, packaged 084bd775… (crc 0x26a72325), both matching the microkernel session's.
  - `phas.i`;
  - `st.a.d`: control block 0x28 = 0xbeef1;
  - `str`: `EVENT_TIMER` = 0xa5a;
  - `st.a.d`: control block 0x18 = 0xc0de2;
  - a branch to itself.

**Why:** the twenty-fifth attempt's probe and the diagnostic ladder both did work before
`phas.i`. The SGX530 lacks `USE_UNLIMITED_PHASES`, so it may need `phas.i` first (G).

**Results:**

| Load | Event program (0x0a68) | `BIF_INT_STAT` | `BIF_FAULT` | Status words |
|---|---|---|---|---|
| Part 1, real image | 0x014042c0 | **0x4002** | **0x0fd79000** | init 0, version 0, wait 0, heartbeat 0 |
| Part 2, phas probe | 0x01400070 | 0x4004 | 0x010b9000 | init 0, version 0, wait 0 |

- In both loads the fault held from 100 ms to 500 ms, the clocks stayed busy and
  `EVENT_TIMER` stayed 0.
- -ETIMEDOUT each time. The failed-start path held the cores in reset, then all five
  modules unloaded and the parent runtime-suspended.

**Facts (C):**
- **The real image doesn't initialise.** It faults on a data read (requestor b1) at
  0x0fd79000. That's the address and requestor of the twenty-fourth attempt's code base
  15 = 0xec001 variant, which started the bases image 0x100 bytes in.
- **With `phas.i` first, the probe still stores nothing,** and its fetch faults at
  0x010b9000 (b2). The twenty-fifth attempt's probe without `phas.i` faulted at 0x09039000.

**What it suggests (G):**
- **The real image gets further than the probes:** a b1 fault is a data access, so at least
  one instruction issued a load or store, at a wrong address. 0x0fd79000 is in the USSE
  vertex heap, nowhere near the control block (0x0f003000).
- **`phas.i` first isn't enough on its own** for the probe's stores to land.
- **The same 0x0fd79000 from two different starts** (the real image at 0, the bases image at
  0x100) points at a common address computation, maybe a patched or immediate value the
  SGX530 reads differently.
