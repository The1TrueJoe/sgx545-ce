# SGX530 stage 1, thirty-third attempt: limm then str runs without a fault, but EVENT_TIMER stays 0

**Board:** our OMAP3630 test board, openHC on the SD (7.3.3, the 02:16 build), up 10 min,
the owner-confirmed host key, the board lock held. 77 °C before, 75 °C after. No hang, no
plug cycle.

**What ran:** powervr_sgx from sgx530 fd97aabe (the >> 8 code-base unit; modver-check 0
differ), `allow_unisolated=1` only, loaded three times.
- **The images:** the microkernel session's `cores/sgx530_limmwr_r<k>.py` for k = 5, 17
  and 0 (its branch, 559adece), built with `ukernel/build.py` and packaged by
  `drm/tools/mkukfw.py`. All six hashes match the microkernel session's list.
- **What each does:** `phas.i`; `limm rK, #0xa5a`; `str rK` to `EVENT_TIMER`; a branch to
  itself. There's no load, so nothing should fault before the `str`.

**Results:** the same in all three runs.
- The event program sat at 0x01400030 (read back).
- From 100 ms to 500 ms after the kick:
  - `BIF_INT_STAT` 0 and `BIF_FAULT` 0;
  - the clock status 0x00110000 (the USE busy; it was 0x00010000 before the kick);
  - `EVENT_TIMER` 0.
- INIT_STATUS, version and heartbeat 0.
- -ETIMEDOUT each time. The failed-start path held the cores in reset, then all five
  modules unloaded and the parent runtime-suspended.

**Facts (C):**
- **The task runs without a fault and stays busy for 500 ms,** with no load in it.
- **`EVENT_TIMER` never changes from 0:** not 0xa5a, and not r5's, r17's or r0's leftover
  values (attempts 31 and 32).

**What it suggests (G):**
- **`str` to `EVENT_TIMER` isn't shown to work on the SGX530.** No attempt has read back a
  value it wrote. So this attempt can't tell whether `limm` wrote rK.
- **The busy clocks fit the task sitting in its loop,** or stalling before it, at `phas.i`
  or `limm`.
- **A readout that needs neither `str` nor a register write** would separate the two. For
  example, a branch on a `limm`'d value could lead to a load through r5 (fault 0x0c004000)
  on one side and through r17 (0x0fd79000) on the other.
