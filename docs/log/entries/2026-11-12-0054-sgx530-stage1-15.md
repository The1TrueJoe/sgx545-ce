# SGX530 stage 1, fifteenth attempt: 0x0a70 doesn't let a branch run

**Board:** our OMAP3630 test board, our kernel on the SD (7.3.3, the 02:16 build). 75 °C
before, 73.5 °C after unloading.

**What ran:** powervr_sgx from sgx530 edd692f4 (CI: omap3630 43163496739, powervr-sgx
43163490240 and upstream 43163493468, all green; modver-check 0 differ),
`allow_unisolated=1 code_base_pads=1 stage1_sweep=1`, with the landing-pad image
`sgx530_bases` (f7de7b95…). The microkernel session's question: is 0x0a70 the event
program's length? The normal 6 would have cut the fourteenth attempt's programs off before
their branches.
- **The variants:** the baseline, then programs A, C and D (fourteenth attempt) each under
  0x0a70 ∈ {1, 2, 3, 4, 6, 8, 12, 16, 20, 32, 64}, smallest first. 0x0a6c = 1, or 0 for D.
- **Stop on a hold:** if the last five `PDS_PC_BASE` samples sit on one row past the start
  row, the loop executes. The sweep would then stop and check that the reset stops the PDS.
- **The fault check last.**

**Results:**
- **No variant held the PDS, and none reached a branch target row.** Programs A and C showed
  only 0x5012ac (their start row), 0xf7dc and 0. D showed only 0x5012a8, 0xf7dc and 0. Rows
  2 and 3 (0x5012b0, 0x5012b4) never appeared, at any length. The teardown check didn't run.
- `EVENT_TIMER` stayed 0 throughout. No "not independent" warning.
- 0x0a68 read back 0x01404aa0 in every variant.
- **The third value is 0xf7dc** this time, with the same image that gave 0xf33c in the
  fourteenth attempt.
- The fault check: `BIF_INT_STAT` 0x4004, `BIF_FAULT` 0x0e800000, then "recovered, BIF int
  0x0".
- -ETIMEDOUT, all five modules unloaded, the parent runtime-suspended.

**Facts (C):**
- **No 0x0a70 value from 1 to 64 lets program A, C or D's branch move `PDS_PC_BASE` off its
  start row, or hold the PDS in a loop.**
- **The pattern (start row, 0xf7dc-family value, 0) is the same at every length**, and the
  same as the baseline's MOVS + HALT.
- **The third value moved again with the image unchanged** (0xf33c → 0xf7dc), as in the
  eleventh attempt. It doesn't follow our image.

**Unknown (U):**
- **This sweep didn't read 0x0a70 back.** We don't know that it latched each value. If it
  holds only a few bits, some lengths aliased.

**What it suggests (G):**
- **0x0a70 isn't a length that cuts the program off before its branches,** or not one in
  this range. Under the microkernel session's reading, a length of 12 or more would have let
  A's self-loop hold.
- **What's left from the runbook:** whether row 1's content changes the trace at all (all
  zeros, all HALTs, or a self-loop on row 1 itself), and the SGX530's PDS encoding.

**Next:** the microkernel session designs attempt 16. The sweep should read 0x0a70 back.
