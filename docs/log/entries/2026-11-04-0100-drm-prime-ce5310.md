# PRIME with simpledrm, both ways: the SGX doesn't snoop, so listed imports are flushed

M2, PRIME. CE5310 board RAM boot of 697182a (ce5310-v1), 2026-11-04 ~01:05 UTC, DDK microkernel,
nothing flashed, no power-cycle.

## The test

The test kernel drives the framebuffer CEFDK leaves running with simpledrm instead
of simplefb. simpledrm only writes that memory and never touches the VDC. It came up
as card0 (720x480), and powervr_sgx as card1 and renderD128. The firmware loader
fell back to the DDK image under its own name, as it should with no open image
present.

`powervr_sgx_prime` renders the frame test's triangle at 720x480 (stride 736) and
puts it on the display. Before every frame the CPU fills the buffer with
0xdeadbeef. After the frame the test checks every pixel, both in the buffer the
GPU wrote and in the scanout memory, which it reads through /dev/mem. Frames take
turns:
- **explicit**: wait for the job, then DIRTYFB;
- **implicit**: the buffer in the job's BO list as written, DIRTYFB at once;
- **control**: no list, DIRTYFB at once.

| path | explicit, implicit | control |
|---|---|---|
| b) a powervr_sgx object (write-combined CPU mapping), exported to simpledrm as the fb | 4/4 right in the buffer and on the scanout | scanout stale (12960 pixels) |
| a) a simpledrm dumb buffer (cached pages), imported into powervr_sgx | 1792 to 45776 pixels per frame still 0xdeadbeef, in the buffer and on the scanout | all stale |

Path b shows that export, the fb import into simpledrm and implicit sync all work:
- simpledrm's commit waited for the render's fence, which it found in the
  reservation object the two drivers share;
- the control frames show that the check catches a commit that didn't wait.

## Coherence

Path a's stale pixels are exactly the CPU's fill word, and different ones every
frame. The SGX's writes don't snoop the CPU caches. The fill sat in dirty cache
lines; some of them reached memory after the GPU's pixels and covered them, and
others were read back from the cache. This answers G19 for writes. Our own objects
were never affected, because their CPU mappings are write-combined.

The fix:
- before a job, the kernel clflushes every imported object the job lists;
- it does so again once the job is done, before its fence signals;
- an import that isn't listed is not flushed, so userspace must list every import
  it renders to or samples (UAPI.md).

## Outcome

4405ed7 added the flushes, but the run looked the same: a job never kept its BO list
(`job->bos` was never set), so nothing was flushed. c95e32d keeps the list on the
job and drops it in `free_job`. On c95e32d:

| path | explicit, implicit | control (import not listed, no flush) |
|---|---|---|
| a) simpledrm dumb buffer imported | 6/6 right in the buffer and on the scanout | 48-80 stale words in the buffer, scanout not yet updated |
| b) powervr_sgx object exported | 6/6 right | scanout not yet updated |

The control frames of path a are the evidence that the flush does the work: the
same frame without a listed import still shows the CPU's words. The uAPI suite
(39/39), frames on two contexts, blits and forced-hang recovery all passed on the
same boot.
