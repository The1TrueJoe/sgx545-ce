# powervr_sgx's first TA kicks: the DDK microkernel runs under the job's directory

The first real render jobs through the new driver: kernel-built render context (HW render
context, CCB, PB, free list, PB descriptor), RT dataset (render details, RT data, region
headers, tail pointers, background block), TA command from the client's `CMD_RENDER` and
`CMD_TA_KICK` streams, and a client frame from `tools/gen`'s frame builder on the DRM uAPI
(`drm/tests/powervr_sgx_frame.c`: a clear and one triangle, pixels checked). EA1, two
RAM-boot slots, 2026-11-03 ~01:20 and ~01:45 UTC; DDK microkernel; nothing flashed.

## What works

- **uAPI tests: 27 of 27**, now including RT datasets and every render-stream negative case
  (`drm/tests/powervr_sgx_test.c`); render contexts with real parameter buffers are
  created and destroyed throughout.
- **The kernel-built TA command is taken by the microkernel** (`ccb ... consumed`).
- **The driver's own recovery works:** each failed job timed out after 2 s, the driver
  reset the core and restarted the microkernel ("job timed out ... resetting", then
  "microkernel started again", `GETMISCINFO` check passing), and the next test ran. Once the
  in-place restart failed ("device lost"); a module reload brought the GPU back. The box
  never wedged and needed no power-cycle.

## Finding 1: the DDK microkernel handles a TA kick under the job's page directory

First slot, kernel heaps not mapped in client directories (the P2/P3 design):

```
BIF_BANK0           0x00000011      (EDM and TA on directory list 1)
BIF_DIR_LIST_BASE1  0x0d4e1000      (the job VM's directory: HW render context word 2)
BIF_FAULT           0x3000b021      (microkernel code, kernel code heap +0xb000)
```

On the kick the DDK microkernel moves the EDM's own `BIF_BANK0` index onto list 1, loads list
1 with the context's directory, and fetches its own code through it. With the kernel heaps
absent from the client directory, it faults. The same happens with list 0 on the idle or the
kernel directory. So **under the DDK microkernel every client directory must map the kernel
heaps**, and P2/P3 cannot be closed; only the open microkernel, which keeps the EDM on list
15, can deliver the isolation the uAPI promises (`docs/UAPI.md` 7.2 and D8 updated). The
driver now shares the firmware directory's page tables for the three kernel heaps into every
VM when the DDK microkernel is loaded (`share_kernel_heaps`, warned at load).

## Finding 2: with the heaps shared, the TA faults in the 3D-params range

Second slot, kernel heaps shared:

```
BIF_BANK0           0x0000001f      (EDM back on list 15, TA on list 1)
EVENT_STATUS2       0x00000480      (TA triggered, not finished)
BIF_FAULT           0x16045041      run 1 (PB high in the range after the uAPI suite)
BIF_FAULT           0x13045041      run 2 (fresh driver, PB at 0x10000000)
```

The microkernel now gets through the kick and starts the TA, which faults in the 3D-params
range (fault request bit 2). The address moves with the 3D request base: base + 0x3045000 in
both runs, an address nothing is mapped at. Not yet explained. Candidates: a free-list or
PB-descriptor word the DPM reads differently from how the kernel writes it, or a field the
DDK's client path sets that the kernel-built command does not.
