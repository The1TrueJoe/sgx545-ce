# powervr_sgx: the second-context hang was the PB's address; one 3D-params heap per VM fixes it

A second render context rendered two frames and hung on its third, process after process
(`2026-11-03-0310-drm-second-context`, `2026-11-03-0300-drm-cleanup`). It was the parameter
buffer's address. EA1, three RAM boots and one normal-boot DDK run, 2026-11-03
~03:18-03:38 UTC; nothing flashed, no power-cycle.

## What the dumps showed

debugfs `render` now also prints the scratch block, the RT-data entry words and the TA3D
control block, and `powervr_sgx_frame -D` prints it after every frame. The same view of
the DDK came from `tools/gen/frame -R 4` with `SGXGEN_DUMP_AFTER=1`: two processes of four
frames each, all rendered.

- **What a frame leaves behind is the same on the DDK and here.** The PB descriptor
  after a 720x480 frame reads 0x14 = 0x19, 0x18 = `04210019`, 0x20 = 0x19, 0x24 = 1 on
  both paths. The earlier guess that this "accounting" kept the first context busy was
  wrong.
- **Rendering the DDK path's way did not help.** `single_entry=1` uses one RT-data entry
  and one region array with the frame counter at 0, as `tools/gen` does. Still 10/10,
  2/10, 0/10.
- **The second process's PB was not at the heap base:**

  ```
  process 1  pbdesc +0x08 04210000   (pages 0x000..0x421, free list 0x10422000)
  process 2  pbdesc +0x08 08850464   (pages 0x464..0x885, free list 0x10886000)
  ```

  Kernel objects had device-wide addresses, and the first process's PB stays allocated
  until a firmware restart. So the second PB landed at page 0x464, with `pb_base`
  0x10400000. The free list numbers pages from the heap base. On the DDK the 3D-params
  heap belongs to each context, so every process's PB starts at 0x10000000.

## The fix and the result

eba829c gives every VM its own 3D-params allocator, starting at the heap base. The PB,
free list, scratch block and background blocks come from it and are mapped only in that
VM's directory. On the EA1:

```
== process 1..5   10/10 frames right   (720x480, each)
== 256x256 -r     10/10 frames right   (a new RT dataset every frame)
27/27 passed      (uAPI suite)
== 2 more         10/10 frames right   (720x480, each)
firmware running: 1 lost: 0 resets: 0 irqs: 240
```

That is 80 frames over eight processes and the full suite, with no timeout and no reset.

## Still open

- **Two render contexts in one VM** each get a PB, and the second one sits above the
  heap base, so the same hazard is expected. The DDK shares one PB per process; the
  driver should share one per VM (UAPI.md G15).
- **The DDK microkernel's cleanup commands** still don't complete (UKERNEL.md 3). That
  is unrelated to this hang.
- **In-place restart** after a hang is unreliable (`2026-11-03-0300-drm-cleanup`). No
  hang happened here to exercise it.
