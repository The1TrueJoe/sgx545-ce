# SGX530 stage 1, attempts 1-40: the record so far

This sums up what stage 1 has established on our OMAP3630 test board, with each fact's log.
The tags are those of the fact sheet ([cores/sgx530.md](../../porting/cores/sgx530.md)).
Attempt 20 didn't run, because its CI was cancelled. Stage 1 hasn't passed: the open
microkernel doesn't reach INIT_STATUS 1.

## What works now (C)

**The event path, from kick to task:**
- **The kick.** The SGX530 has one `EVENT_KICK`. A kick needs the event-kicker word
  incremented first (attempt 8).
- **The PDS fetches the event program only with 0x0a74 = 0x208200,** the SGX545's value.
  Part 2 writes it now (log 2026-11-12-0151, 43831efb).
- **The event program's registers:**
  - 0x0a68 is the program's offset from `PDS_EXEC_BASE`, in 16-byte rows; bits 0-3 don't
    latch (attempts 12 and 14).
  - 0x0a6c is the code's start within the program, in rows, 12 bits at most (attempts 12
    and 17).
  - 0x0a70 latches (attempt 16).
- **`PDS_PC_BASE` is the computed start address of the last dispatch, not a running PC.** A
  program in unmapped memory shows its start and nothing faults until something fetches
  (attempt 17).
- **The PDS executes the SGX545's MOVS → DOUTD encoding** (attempt 18).

**Starting the USSE task:**
- **Code bases count 256-byte units on the SGX530** (128 on the SGX545). The EDM task
  fetches at code base 15's field << 8, masked to 28 bits. Four cells measured it
  (attempts 23-24). The driver keeps the unit per core (4089fd7f).
- **DOUTU word 0:**
  - b0-3 select the base: 0xf for code base 15, other values 0x8000 higher (attempt 22).
  - b4-7 and b16-18 are code-offset bits 15-18 and 12-14 (attempts 21-22); b8-15 are
    offset bits below 4 KiB (attempt 35).
  - b19-23 and b27 don't move the fetch.
- **With all of that, the task runs from the kernel code heap and executes `phas.i`, `limm`
  and loads** (attempts 24-27).

**Inside the task:**
- **Each register holds a stable leftover value at task start, and a load reads the
  register it names** (attempts 29-32 and 39). The leftovers are the same across reboots:
  r0 0x0055d000, r5 0x0c004000, r17 0x0fd79000, PA0 0x0f2d9000, and others (log 31).
- **No register write from the task is seen afterwards:**
  - `limm` (attempts 29, 30 and 32);
  - an ALU `or`, into r0-r3 or r5 (attempts 34 and 39);
  - with up to 8 `nop`s between the write and the read, or 23 instructions (attempts 32
    and 38).
- **`str` to `EVENT_TIMER` shows nothing** (attempt 33).

## What's been ruled out as the cause of the dropped writes (C)

- **The DOUTU temporaries field:** at 8 (32 temporaries, b27 set), and every free bit group
  set (attempt 35).
- **`phas.i`'s temporaries field:** at 6, 8 or 63 (attempt 36).
- **The rest of the SGX545's part 2:** thirteen writes, together and in subsets (attempt
  37). 0x800, 0x810, 0x814, 0x818, 0x4e8 and 0xaac don't even latch on the SGX530.
- **An instruction-pairing hazard of up to 8 instructions** (attempt 38).
- **`[moe]` addressing** (attempt 28).

## Readings that were wrong, and corrected

- **0x0a6c counts dwords** (attempt 12's first reading): it counts rows (attempt 13 void).
- **The load's base comes through with bits 24-25 lost, so `limm` is wrong** (attempt 29):
  the fault followed the register named, not its value (attempt 30).

## Still open

- **Why no register write lands.** Candidates (G): the destination operand's encoding on
  the SGX530; a setup the SGX530 needs before writes commit; or writes going to a bank
  later reads don't see.
- **Whether a primary attribute the PDS writes is visible to the task.** Attempt 40 didn't
  test it: its two-row event program's DOUTU took a zero word, with 0x0a70 left at 6. The
  same probe with 0x0a70 = 8 would.
- **A capture of TI's working SGX530 setup** would show directly how its EDM task gets a
  register file it can write. That's waiting on Joseph's answer about a capture board.

## The driver changes that came out of it

All three are in the SGX530's core table:
- 0xa74 = 0x208200 in part 2 (43831efb);
- code bases in 256-byte units (4089fd7f);
- the TI heap layout (attempt 5).

The rest of stage 1 is sweep code behind `stage1_sweep` / `stage1_vendor`, off by default.
