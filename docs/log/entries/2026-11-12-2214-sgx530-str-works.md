# SGX530: str works under §9 — the EDM task can program registers

**Board:** our OMAP3630 test board, up 13 h 30 min (the same boot as the whole §9 series), the
owner-reread pinned ED25519 host key, the board lock held 22:13:59-22:15:08 UTC. 77 °C. No
hang, no plug cycle.

**What ran:** powervr_sgx from claude/sgx530-gap19-tests (omap3630 CI green), two loads,
`allow_unisolated=1 stage1_vlaunch=1`. Image `sgx530_limmwr_r5` (matching the microkernel
session's hashes, img dbec9d41…, pkg 4a6c94ae…): `limm r5, #0xa5a; str r5 -> EVENT_TIMER
(0xacc); loop`. The driver's after-kick diagnostic already reads EVENT_TIMER (the `timer`
field), so no driver change was needed. A second load ran `sgx530_xorr5` as a §9 sanity.

**Result: `EVENT_TIMER` reads 0x00000a5a**, stable from 100 ms to 500 ms after the kick.

| Load | EVENT_TIMER (the `timer` field) |
|---|---|
| `limmwr_r5` (`limm r5,#0xa5a; str r5->EVENT_TIMER`) | **0x00000a5a** |
| `xorr5` (no EVENT_TIMER write) | 0x00000a5a (see note) |

**Facts (C):**
- **`limm` works under §9.** The task loaded the constant 0xa5a into r5.
- **`str` works under §9.** The task wrote r5 to EVENT_TIMER, and the register holds exactly
  0xa5a — the task programmed a core register.

**What this settles:**
- **The EDM task can drive the SGX530 hardware under §9.** It computes (temporaries retire,
  log 2026-11-12-2149), loads constants (`limm`), and programs registers (`str`: BIF, DPM, the
  TA/3D kicks). The one thing it can't do — commit a memory store (`st.a.d`, log
  2026-11-12-2201) — is survivable: the kernel owns every firmware-visible structure and
  signals fences from the host interrupt (UAPI threat model), and the microkernel writes
  PA0-PA2 via attribute DMA (DOUTA), not ALU.
- **So §9 + host-owned memory is a viable open-microkernel path on the SGX530.** The open
  microkernel can run on the 530 with the §9 launch words (minimal: DOUTU word 2 = 1 and
  word-0 bit 21; word 1 free). Host-kick (pvrsgx_host.c) returns to being the fallback it was
  meant to be.

**Note (not the headline):** the second load (`xorr5`, which does not write EVENT_TIMER) also
read 0x00000a5a at 100 ms, though its clocks-on read was 0. EVENT_TIMER is likely not cleared
by the reset between module loads, or this is a read quirk; the microkernel session decodes it.
The `limmwr_r5` result is unambiguous — 0xa5a is its own constant.

**Next:** fold the §9 launch words into the SGX530's real init (not only `stage1_vlaunch`) so
the open microkernel starts on the 530; the microkernel session brings up the full microkernel.
