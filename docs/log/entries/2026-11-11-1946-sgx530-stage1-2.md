# SGX530 stage 1, second attempt: the kick wakes the USE, the heartbeat never lands

**Board:** our OMAP3630 test board, mainline 7.3.3 plus the OMAP3 GPTIMER12 clocksource fix
(upstream 0d3a67b1954a), RAM-booted. The CPU thermal zone was disabled for this boot by the
board owner (unrelated power-offs). It read 80 °C before the load and 77 °C after.

**What ran:** one attempt, per [sgx530-stage1.md](../../porting/cores/sgx530-stage1.md).
- powervr_sgx from sgx530 25da19f6, built by `powervr-sgx-omap3630` run 43124322265
  (7.3.3). powervr-sgx and upstream were green on the same head. `modver-check.py`: 0
  differing CRCs against the board image's modules.
- The same microkernel as the first attempt: file 34aa17c4…, crc 0x77f96757.
- New in this build:
  - a runtime-PM reference held on a single-context core, so `power/control` wasn't touched;
  - bring-up logs from named registers: `CLKGATESTATUS`, `EVENT_STATUS`,
    `BIF_MEM_REQ_STAT`, `BIF_INT_STAT`, and the OCP wrapper's four (TI's GPL `ocpdefs.h`);
  - the microkernel's status words logged on the failed start.

All five modules unloaded, the ti-sysc parent runtime-suspended, and the board kept answering.

**Facts (C):**
- **The OCP wrapper is as mainline sets it.**
  - Revision 0x40000000, so ti-sysc's SGX quirk matches.
  - `sysc` 0x28: smart idle and smart standby.
  - `OCP_DEBUG_CONFIG` 0x80000000: `THALIA_INT_BYPASS` set.
- **`OCP_DEBUG_STATUS` is 0x023c0707 throughout, before and after the kick.**
  - Initiator: MConnect0 3, SConnect0 1, MWait 0, MStandby 0, MDiscReq/Ack 0.
  - No response error or FIFO-full bit.
  - The target fields (command out 7, register 17) are presumably the host's own register
    accesses.
- **The kick turns the USE clocks on** (`CLKGATESTATUS` b20, `USE_CLKS` in the SGX530's K
  header; b16 is the DPM's, which the driver keeps on). They stay on for the whole 500 ms.
- **The memory reads complete.** `BIF_MEM_REQ_STAT.READS` is 2, then 0 at 200 ms, then 2
  again, so reads come and go: they aren't stuck. No BIF fault, and no `EVENT_STATUS` bit.
- **The heartbeat (ctlblk word 0x2a) is still 0, and so is the version word (0x18).** By
  the image's layout the heartbeat is the event's first write, at instruction 6.

**What it rules out and what's left:**
- **Ruled out: a stuck interconnect.** That was hypothesis 1 of the first attempt's log. The
  wrapper is configured, the initiator is connected and not in standby, and reads complete.
- **The event reaches the USE.** The last attempt's hypothesis 2 (reads stuck in the table
  walk) is out too.
- **Still possible: the USE runs, but not the microkernel's first six instructions as
  written, or the store doesn't reach the memory the CPU reads.** Candidates, all G:
  - the PDS entry program's data under the SGX530's layout, or the DOUTU's code
    address: what it means against `USE_CODE_BASE_15`, whose 24-bit address field's unit
    is U;
  - `phas.i` (instruction 0) or the patched `limm` pair encoding differently on the
    SGX530 (ISA.md's SGX530 delta rates `phas.i` the highest risk);
  - the heartbeat store's address, from the `ctlblk` limm patch, landing elsewhere.
- **A caveat:** the SGX530's `CLKGATECTL` has no PDS field, so "USE clocks on" may be the PDS
  running in the USE's clock domain, not a USSE task. Which one is U.

**Next** (for the microkernel session and the owner): an entry that writes a constant to the
heartbeat as its very first instruction, with no `phas.i` before it, would split "the USSE
runs our code" from "something else runs". Any change to the image or the entry program is
a new attempt, agreed with the board owner.
