# The shader validator: client code only from validated read-only code objects

M2, D9 option 1. CE5300 board (ce5300-v2) RAM boot of b6d98a3 (tests from cd78c67), 2026-11-03
~07:30 UTC, DDK microkernel, nothing flashed, no power-cycle.

## What it is

A client's USSE task can read the core's registers with `ldr` (P1), and no page
directory can stop that, so the kernel must make sure no client instruction that
reaches the hardware is an `ldr` or `str` (D9 option 1, as `vc4` does upstream).

- **Code objects.** `CREATE_BO` takes `DRM_POWERVR_SGX_BO_CODE`. Such an object has no
  CPU mapping and no PRIME export. It is the only kind the USSE heaps accept, it maps
  nowhere else, and it is mapped with the PTE `READONLY` bit.
- **`UPLOAD_CODE`** (ioctl 0x0d) copies instructions into a code object after scanning
  every one. It refuses:
  - a word that matches no known form;
  - `ldr`/`str`;
  - `setl`/`savl`;
  - a `br` whose target is outside the object.

  On a refusal nothing is copied, and the offset of the first bad instruction comes
  back. While the object is mapped, uploads only append.
- **The form table** is generated from the clean-room isaspec description,
  `mesa/src/sgx545/isa/sgx545.xml`. Each of the 109 leaf forms gives one (mask, match)
  pair: the bits its patterns and its ancestors' fix. The generator refuses any two
  forms that could match the same word. Nothing comes from the DDK or the hardware
  oracle tools.

The uAPI is in UAPI.md (section 2, `UPLOAD_CODE`), with D12 recording what it closes
for Joseph: the winsys must upload shaders instead of writing a mapped buffer.

## Checked offline

The isaspec encoder's own test lists (`gles2.txt`, `int.txt`, 246 instructions, run
through `tests/standalone.sh`) all match exactly one form of the table: 239 plain, 5
`br`, 1 `setl`, 1 `savl`. Encoded `ldr`/`str` words classify as `ldr`/`str`. An `ldr`
with one stray bit (h3), and an all-ones word, match nothing.

## E1, second half: the PBE and a read-only page

`powervr_sgx_hang -E` uploads 16384 words of valid instructions into a 64 KiB code
object. It then renders a frame whose end-of-tile program points the PBE at the code
object (`SGXGEN_PBE_ADDR`), and copies the object out with a transfer, which reads
through the same VM.

```
PBE at code object 0x37021000: wait 0, context state 1, resets 2 -> 3
code object afterwards: 0 of 16384 words changed, 0 look like the frame's pixels
devcoredump: BIF_FAULT 0x37021002, BIF_INT_STAT 0x00080020
```

The PBE's write faulted at the object's first page and the job was reset; nothing
landed. The copy reproduced the pattern exactly, so the read path worked. The fault
word's low bits (0x002) differ from a vertex-fetch fault's (0x032, log 0600), which
fits a different requestor. With E1's first half (a task's `st`, 0115), the read-only
bit holds against both writers a client controls, so code objects need no further
protection.

## Still open

- E2 (which requestor fetches USSE instructions) and E3 (other encodings that reach the
  register file) matter less now: anything outside the 109 forms is refused.
- Whether a mapped object's append is seen without a USSE instruction-cache invalidate.
  Every test appends while mapped and renders right, but the driver sends no
  instruction-cache flush.
- Under the DDK microkernel the kernel heaps are in every client PD, so P2 and P3 stay
  open whatever the validator does. Isolation needs the open microkernel (M1).
