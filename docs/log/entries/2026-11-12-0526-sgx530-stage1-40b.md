# SGX530 stage 1, fortieth attempt rerun: PA0 keeps what the PDS wrote, and the task reads it

**Board:** our OMAP3630 test board, openHC on the SD (7.3.3, the 02:16 build), up 1 h 41 min
(the same boot as the first fortieth-attempt run at 10:17 UTC), the owner-confirmed host
key, `hc250.lock` held. 77 °C before. No hang, no plug cycle.

**What ran:** powervr_sgx from sgx530 84a3c5a0 (CI: omap3630 43199302472, powervr-sgx
43199292265 and upstream 43199297391, all green; modver-check 0 differ), `allow_unisolated=1
stage1_sweep=1`, with the microkernel session's `sgx530_pa0` (packaged f59ce697…):
`phas.i`; `ld.a.d r3, pa0, #0`; a loop.
- **The variants:**
  - the normal event program (no DOUTA);
  - the fortieth attempt's two-row program (DOUTA (0x0e850000, 0) to PA0, then the DOUTU,
    0x0a6c = 2) with 0x0a70 = 6;
  - the same with 0x0a70 = 8.

**Results:**

| Variant | 0x0a6c, 0x0a70 read | `BIF_INT_STAT` | `BIF_FAULT` |
|---|---|---|---|
| normal event program | 0x1, 0x6 | 0x4002 (b1) | **0x0e850000** |
| two-row, 0x0a70 = 6 | 0x2, 0x6 | 0x4004 (b2) | 0x0f400000 |
| two-row, 0x0a70 = 8 | 0x2, 0x8 | 0x4004 (b2) | 0x0f400000 |

- All recovered with the reset. -ETIMEDOUT, all five modules unloaded, the parent
  runtime-suspended.
- **The order of events on this boot:**
  - 10:17 UTC: the normal program's PA0 load faulted at 0x0f2d9000.
  - Then the two-row program ran its DOUTA, before its DOUTU started a task at code base 0.
  - The modules unloaded and the parent runtime-suspended.
  - 10:26: the normal program's PA0 load faulted at 0x0e850000.

**Facts (C):**
- **The PDS's DOUTA (value, ctrl 0) writes PA0:** 0x0e850000 appears in PA0 only after the
  DOUTA has run. No other program writes that value.
- **The task's load through PA0 reads what the PDS wrote.**
- **PA0 keeps its value through:**
  - the recovery resets;
  - the module unload;
  - the ti-sysc parent's runtime suspend;
  - the reload nine minutes later.
- **The two-row program's DOUTU still starts a task at code base 0 with 0x0a70 = 8.** So
  0x0a70 isn't what breaks it. The fortieth attempt's "0x0a70 is the data length" reading
  isn't supported.

**What it suggests (G):**
- **A primary attribute the PDS writes is visible to the task, where nothing the task
  writes to a register is.** That's the first fact behind carrying the SGX530
  microkernel's pointers in PDS-set attributes.
- **The register file keeps its contents across our resets and the power-down,** which also
  fits the stable leftovers (attempt 31).
- **The two-row program's DOUTU word comes out 0 for another reason,** such as how the
  SGX530 lays out a second data row. A one-row program with both the DOUTA and DOUTU words
  in it would avoid that.
