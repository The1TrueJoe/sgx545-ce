# Runtime PM works: a restart after a clean stop must not touch the gated core

Follows 0610 (the CE5310 board froze on the first runtime-PM run). CE5300 board (ce5300-v2, board) RAM
boots, 2026-11-03 ~06:30 UTC, DDK microkernel, nothing flashed. One freeze, recovered
with the remote power switch; the one-shot hook had already deleted itself, so the box came back
on its normal boot.

## The bisect

| step | build | result |
|---|---|---|
| `runtime_pm=0` | 37dca03 (ce5300-v2) | uAPI 33/33, 20/20 frames on 2 contexts, blits right, 3/3 forced hangs recovered, each with a devcoredump |
| `runtime_pm=1`, suspend | 37dca03 | suspended after 500 ms: power status 0x2c, `powered: 0` |
| `runtime_pm=1`, the first resume (one NULL job) | 37dca03 | **the SoC froze**; nothing more on serial after the device open |
| `runtime_pm=1`, the first resume | 1d170e9 | NULL job in 19.6 ms, suspended again 1 s later |

The SGX's interrupt (26) is not shared on the CE5300 board, so 0610's shared-IRQ suspect did not
apply here.

## Cause and fix

Resume is the restart a reset does. Before rebuilding the microkernel, that restart
quiesces the core: deinit script, `SOFT_RESET`, a read of `SOFT_RESET`, bus mastering
off and on. After a hang the clocks are on and that is needed. After a runtime suspend
`pvrsgx_fw_stop` has already done all of it, and the clocks gated seconds before. A
register read on that gated block froze the SoC.

The same read straight after the deinit, in `pvrsgx_fw_stop`, does not freeze, and
neither does a module reload (the same stop, then a first start, which writes
`CLKGATECTL` before any read). So a read is only safe while the clocks are still
running.

Fix: the restart quiesces only if the device was powered when the start began (a
reset). After a clean stop it goes straight to rebuilding the image and starting.

0610's CE5310 board freeze came on the same first-resume path, so it was very likely this. The
`powered` flag added then stays: it keeps register reads (IRQ handler, debugfs, the
devcoredump) away from a gated core.

## With the fix, `runtime_pm=1`

| run | result |
|---|---|
| 20 frames, each started from suspended | 20/20 right |
| uAPI suite | 33/33 |
| blits, 3 rounds; 20 frames on 2 contexts | all right |
| `powervr_sgx_hang -n 3`: render, mixed submit, idle (wait for suspend, then render, mixed submit and blit from suspended), forced hang | all right; render from suspended 13-16 ms; 3 resets, 3 devcoredumps, back to suspended afterwards |
| `rmmod` while suspended, reload, frames, `rmmod` | clean |

`runtime_pm` stays off by default until the CE5310 board has run it too.

The CE5310 board ran the same set on 1d170e9 (log `2026-11-03-1700-drm-runtime-pm-ce5310`), and
`runtime_pm` is now on by default.
