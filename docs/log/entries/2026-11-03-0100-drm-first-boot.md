# powervr_sgx boots the SGX545 from the kernel: probe, DDK microkernel, DEV_QUERY, NULL jobs with fences

M2 step 2 (`AGENTS.md` section 5): the first run of the new DRM render driver
(`drm/powervr_sgx/`, design in `docs/DRM-DRIVER.md`) on hardware. CE5310 board (CE5310, core rev
1.0.14), 2026-11-03 ~00:50 UTC, RAM-booted test kernel, nothing flashed.

## Set-up

- Kernel: kernel.org 7.1.8 with the boot image's CE5300 patches, drivers and config, the vendor driver
  (`pvrsrvkm`) left out and `powervr_sgx` built as a module (`7.1.8-m2drm`), built by the
  `powervr-sgx` workflow on GitHub-hosted runners.
- Boot: a one-shot `/etc/init.d/S00aramboot` on p1 kexec'd it from the bootstrap kernel,
  before anything had touched the GPU (`drm/ci/ea-ramboot/`), with `ohc.ramboot=1`. The
  hook deleted itself; the normal boot is unchanged.
- The test kernel came up clean: no HPET, DMA or EHCI symptoms, GPU unbound, no `/dev/dri`.
- The microkernel was cut from the box's own `libsrv_init.so.1.7.862890` into
  `/lib/firmware/powervr_sgx/` (sha256 `73dce088…`), as `srvinit/fetch-firmware.sh` does.
  It stays on the box.
- `/tmp/gpu.lock` held throughout; the panel web view stopped first.

## Result

```
powervr_sgx 0000:01:02.0: [drm] SGX core id 0x01150000 revision 0x0001000e
powervr_sgx 0000:01:02.0: [drm] microkernel started
powervr_sgx 0000:01:02.0: [drm] microkernel: core rev 0x1000e id 0x1150000, DDK 0x10711 build 862890, build options 0x60218
[drm] Initialized powervr_sgx 0.1.0 for 0000:01:02.0 on minor 0
```

- **The kernel started the microkernel** with no userspace involved: the init sequence of
  `docs/DRM-DRIVER.md` section 3 set `INIT_COMPLETE` within the 500 ms poll.
- **The first host command was serviced:** `GETMISCINFO` answered with the core identity, DDK
  build 862890 and build options 0x60218 (the value SRVINIT.md records), and all 13 struct
  sizes equal the ones this microkernel build was made with.
- **Translation as designed** (debugfs `status`): `BIF_BANK0` = 0xf (EDM on list 15), list 15
  = the firmware's directory, list 0 = the empty idle directory, `BIF_FAULT` 0, no
  microkernel lockups, no assert.
- **DEV_QUERY** returns core id 0x01150000, core revision 0x0001000e and
  `DRM_POWERVR_SGX_FW_IF_SGXMKIF_1_7`.
- **NULL jobs complete with fences:** a NULL job's out-syncobj signaled in 7.5 ms; 600 NULL
  jobs (more than the 256-slot kernel CCB) completed in 27 ms with the ring wrapping twice
  (`ccb wo 93 ro 93 issued 605 consumed 605`).
- **uAPI tests: 23 of 24 passed** on the first run (`drm/tests/powervr_sgx_test.c`): every
  DEV_QUERY, CREATE_BO, mmap, VM, VM_MAP/UNMAP, context and SUBMIT_JOBS case including all
  the negative ones. The failure was a real gap, below.
- **Back to normal:** after `rmmod` and a plain `reboot` the box came up on its own 7.1.8
  kernel with `pvrsrvkm` bound and no hand-off symptoms, `/boot/once` removed.
- **Unload and reload:** `rmmod` powered the microkernel off through the `POWER` command (no
  timeout), and left the cores held in soft reset (`EUR_CR_SOFT_RESET` 0x3f, as the boot image's
  quiesce expects). A second `insmod` started the microkernel again and the NULL-job tests
  passed on it.

Raw output: `docs/log/data/2026-11-03-0100-drm-first-boot.txt`.

## Found

1. **A wait on a syncobj that an earlier job of the same submit signals** was refused
   (`-EINVAL`, `submit-null-job-chain`): the syncobj has no fence until that job is armed.
   Fixed in 27b6501 as upstream pvr does it: such a wait becomes a dependency on the earlier
   job's finished fence, added just before the job is armed, in order. That build, loaded
   into the same boot (the third microkernel start of the boot): **24 of 24 passed**.
2. **The DDK microkernel raised no SW_EVENT interrupt** for any of the 605 commands (`irqs:
   0`). Completion of a NULL job comes from the poll that runs while jobs are out, which is
   what sets the ~7.5 ms single-job latency (one jiffy). Render jobs will complete on the
   3D's end-of-render event instead (UKERNEL.md 5); a NULL job has no such event.
