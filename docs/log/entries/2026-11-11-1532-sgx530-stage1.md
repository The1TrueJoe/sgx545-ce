# SGX530 stage 1: the first microkernel start doesn't reach init

**Board:** our OMAP3630 test board, mainline 7.1.8 (the board's own build, gcc 15.3), booted
by RAM kexec. GPU node `50000000.gpu` in ti-sysc `target-module@50000000`, unbound before.

**What ran:** one attempt, per [sgx530-stage1.md](../../porting/cores/sgx530-stage1.md).
- powervr_sgx from sgx530 c93e400, built by `powervr-sgx-omap3630` run 43007573058
  (7.1.8). `modver-check.py` found 0 differing CRCs against the board's modules.
- The open microkernel `powervr_sgx/sgx530_ukernel.bin`: image 2d79b7f2… (17088 B),
  file 34aa17c4…, crc 0x77f96757, features 0x4.
- Loaded with `allow_unisolated=1`. Before the load, `power/control` of `50000000.gpu` was
  set to `on`, so runtime PM couldn't autosuspend the GPU 500 ms after the probe (an
  autosuspend sends the CCB power command, which is stage 3). It was set back to `auto`
  afterwards.

```
SGX530 has one memory context: clients are not isolated from the firmware or from each other (allow_unisolated=1)
SGX core id 0x01120000 revision 0x00010205: TI OMAP3630 (SGX530 1.2.5)
powervr_sgx/sgx530_ukernel.bin: open microkernel dev, interface 1.0, features 0x4
event PDS registers before any write: enable 0x00000000 base 0x00000000 data 0x00000000 0x00000000
event PDS base 0x0a68: wrote 0x020042c0, read 0x020042c0
*ERROR* microkernel did not start (init status 0x0, event status 0x0; BIF int 0x0 fault 0x0 req 0x2)
probe with driver powervr_sgx failed with error -110
```

The failed start soft-reset the GPU. No oops, hang or interrupt storm followed. All five
modules unloaded, the ti-sysc parent runtime-suspended again, and the board kept answering.
The status words were never read twice: the probe failed first.

**Facts:**
- 0x0a68 is a backed read-write register on the SGX530: it reads 0 after reset and holds
  0x020042c0 (bits 6, 7, 14 and 25 at least) when written (C). This doesn't show that it is
  the event-program address.
- 0x0a58, 0x0a6c and 0x0a70 read 0 after reset, the same as an unbacked address would (no
  new fact).
- 500 ms after `EVENT_KICK`:
  - host control word 0 (`INIT_STATUS`) was still 0;
  - `EVENT_STATUS` (0x012c) read 0;
  - `BIF_INT_STAT` and `BIF_FAULT` read 0;
  - `BIF_MEM_REQ_STAT` (0x0ca8, the READS field: outstanding memory reads) read 2 (C).
- So the SGX issued memory reads that never completed, and the MMU raised no fault.

**Runbook row:** "the base reads back, init stays 0". The offsets stay G, and stage 1
hasn't passed.

**What the outstanding reads suggest** (hypotheses, not facts):
1. **The SGX's memory requests don't complete on the interconnect.** Candidates: its OCP
   initiator port in standby (ti-sysc's `midle` choice for this module), or an L3 issue.
   The kernel logged no L3 error.
2. **Two reads stuck in the MMU's table walk** for the event program's address in the
   kernel code heap (0x020042c0). The driver writes plain 4 KiB-aligned addresses and
   valid-only PDEs, which is the SGX530's encoding (K), so a wrong address encoding is
   unlikely.
3. **The PDS or USSE issuing reads through a path the SGX530 sets up differently**: the
   event-program enable value (0x2204b00f, the SGX545's), the entry program's data layout,
   or `USE_CODE_BASE`. Item 3 doesn't easily explain reads that never complete, against
   reads that complete and run the wrong code.

**For the next attempt** (each item needs the board owner's agreement and a new build):
- Read-only checks that touch no GPU register:
  - `/sys/kernel/debug/clk/clk_summary` for `sgx_fck`/`sgx_ick` (gap 14);
  - ti-sysc's own registers named in the DT (`rev` 0x5000fe00, `sysc` 0x5000fe10);
  - `OCP_DEBUG_CONFIG` bit 31 at module offset 0xff08 (gap 2).
- More logging on a failed start, from named registers only: `CLKGATESTATUS` (0x0004), and
  `BIF_MEM_REQ_STAT` and `EVENT_STATUS` sampled across the 500 ms, so a stuck count tells
  itself apart from a moving one.
