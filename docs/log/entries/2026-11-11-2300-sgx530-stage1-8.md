# SGX530 stage 1, eighth attempt: the kicker increment, and the PDS runs the event program

**Board:** our OMAP3630 test board, our kernel on the SD (7.3.3, the 02:16 build). 75 °C
before, 73.5 °C after.

**What ran:** powervr_sgx from sgx530 a308bf39 (CI: omap3630 43151044916, powervr-sgx and
upstream green), `allow_unisolated=1 stage1_sweep=1`, with the diagnostic image
(845463a3…).
- **The change from attempt 7:** the init kick increments the event-kicker word before
  writing `EVENT_KICK`, as the GPL DDK's `SGXInitialise` does on a core without
  `MULTI_EVENT_KICK` (7c8cb33e).
- **The normal start no longer writes `PDS_PC_BASE`.** Only sweep variants 10 and 11 do.
- **The rest is attempt 6's settings:** TI's layout, 0x0a68 as an offset from
  `PDS_EXEC_BASE`, the 24-temporary DOUTU.

The variant-12 line "starts the event program" was a **false positive** of the sweep's
check. `EVENT_TIMER` counts down once enabled (0x0102a9b3, 0x0102363a, …), so its value
leaves the host's write by itself. The timer event fired (`EVENT_STATUS` 0x20000000, b29).
Init, version, wait and heartbeat stayed 0, and the probe failed with -ETIMEDOUT. All five
modules unloaded and the ti-sysc parent runtime-suspended.

**Facts (C):**
- **With the kicker incremented, `PDS_PC_BASE` leaves 0 after the kick.** Attempts 5-7,
  without the increment, read 0 at every sample.
- **Variants 10 and 11 wrote `PDS_PC_BASE` and it read 0 afterwards.** So it doesn't hold a
  host write: it is a status register.
- **`EVENT_TIMER` is a live countdown when enabled.** Starting the timer raises the timer
  event (`EVENT_STATUS` b29).

**What it suggests (D/G):**
- **D:** `PDS_PC_BASE` is the PDS's current program counter.
- **G:** read as a dword address relative to `PDS_EXEC_BASE`, 0x005010d4 × 4 = 0x01404350.
  That is the event program's offset (0x01404340) plus 0x10, its first instruction after
  the 16-byte data segment, and 0x...d8 is the next one. So **the kick now reaches the PDS
  and the PDS runs our event program**. The kicker increment fixed the dispatch.
- **But no USSE task starts.** The ladder's first write (`EVENT_TIMER` = 0xa5a) never comes.
  The break has moved to **the PDS's DOUTU**: its operands under the SGX530's data layout,
  its words, or the task it starts.
- 0x0000f75c (variants 5-7) is unexplained. ×4 = 0x0003dd70.

**Next:**
- Fix the sweep's success check. Look for the ladder's own marker (`EVENT_TIMER` = 0xa5a,
  or the ctlblk wait word 0xd1a60001), not "changed".
- Keep the kicker increment.
- Work on the DOUTU with the microkernel session. Sweep variants 5-7 ran with the kicker
  fix, but each combined with nothing else; pairs are the next step.
