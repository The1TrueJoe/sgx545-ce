# SGX530 stage 1, twenty-eighth attempt: the load faults the same without [moe]

**Board:** our OMAP3630 test board, openHC on the SD (7.3.3, the 02:16 build), up 37 min,
the owner-confirmed host key, the board lock held. 77 °C before, 75 °C after. No hang, no
plug cycle.

**What ran:** powervr_sgx from sgx530 fd97aabe (the >> 8 code-base unit; modver-check 0
differ), `allow_unisolated=1` only.
- **The image:** the microkernel session's `cores/sgx530_usse_nomoe.py` (its branch,
  e8fb80e0): 96 bytes, sha256 410484bb…, crc 0x3e0a1c92. Packaged 911f1f0a…, both matching
  the microkernel session's.
- **What it does:** the twenty-seventh attempt's mirror probe, with one change: the
  heartbeat load `ld.a.d r3, r17, #42` no longer carries `[moe]`. The SGX545 image uses
  `[moe]` on many operations without ever setting the MOE state, and the SGX530's default
  state is untested (G).

**Results:**
- The event program sat at 0x01400060 above `PDS_EXEC_BASE` (read back).
- From 100 ms to 500 ms after the kick: `BIF_INT_STAT` 0x4002 (requestor b1), `BIF_FAULT`
  **0x0fd79000**, the clocks busy, `EVENT_TIMER` 0.
- Control block 0x28 = 0, INIT_STATUS 0.
- -ETIMEDOUT. The failed-start path held the cores in reset, then all five modules unloaded
  and the parent runtime-suspended.

**Facts (C):**
- **Without `[moe]` the heartbeat load faults exactly as with it:** b1 at 0x0fd79000.
- **So the MOE state isn't what puts the load at 0x0fd79000.**

**What it suggests (G):**
- **The SGX530 forms `ld.a.d`'s address from r17 (0x0f003000, the patched control block)
  and the offset differently from the SGX545 encoding,** or r17 doesn't hold the patched
  value when the load runs. 0x0fd79000 − 0x0f003000 = 0x00d76000.

**Next:** the microkernel session's offset sweep (varying `#42`) to read the load's
effective-address formula, as attempts 21-24 did for `USE_CODE_BASE`.
