# SGX530 stage 1, forty-second and forty-third attempts: eleven writable outputs, and the DOUTA's form isn't the problem

**Board:** our OMAP3630 test board, openHC on the SD (7.3.3, the 02:16 build), up 2 h 22 min
(the same boot as attempts 40-41), the owner-confirmed host key. the board lock was held for
each attempt. 77 °C before. No hang, no plug cycle.

## The forty-second attempt: how many output registers can the task write?

**What ran:** powervr_sgx from sgx530 f85c22d9 (modver-check 0 differ), `allow_unisolated=1`
only, loaded eleven times.
- **The images:** the microkernel session's `cores/sgx530_aluwr_o<n>.py` for n = 0-10 (its
  branch, ab364dec), built with `ukernel/build.py` and packaged by `drm/tools/mkukfw.py`. All
  22 image and package SHA-256s match the microkernel session's list in full.
- **What each does:** `or oN, r5, r17`, then `ld.a.d r3, oN, #0`. A fault at 0x0fd7d000 (r5's
  leftover | r17's) means oN took the write.
- **Not run:** the microkernel session's first version of this probe stored through r17. That
  register is set by a `limm`, which doesn't write on the SGX530, so it couldn't read out.
  It was replaced by this per-output form before any board time.

**Results:** every load faulted with `BIF_INT_STAT` 0x4002 (requestor b1) at **0x0fd7d000**,
for o0 through o10. -ETIMEDOUT each time, all five modules unloaded, the parent
runtime-suspended.

**Facts (C):** **o0-o10 each take an ALU write from the task, and a load through each reads
it.** That's eleven task-writable output registers.

**What it suggests (G):** **enough outputs for the microkernel session's restructure** (its
peak is 10). Each image wrote the same value, so this doesn't show the outputs are distinct
registers rather than aliases.

## The forty-third attempt: the DOUTA in its .x2.s27 form

**What ran:** powervr_sgx from sgx530 661edcb7 (CI: omap3630 43205423791, powervr-sgx
43205411856 and upstream 43205417407, all green; modver-check 0 differ), `allow_unisolated=1
stage1_sweep=1`, with the microkernel session's `sgx530_pa0` reader (packaged f59ce697…).
- **The variants:**
  - the normal event program;
  - the forty-first attempt's one-row program, `[0x0e860000, 0, 0, doutu]`, with a plain
    DOUTA (0x07…);
  - the same program with its DOUTA in the `.x2.s27` form seen on captured DOUTA pairs
    (word | 0x28000000 = 0x2f…, docs/PDS.md), writing 0x0e870000.

**Results:**

| Variant | `BIF_INT_STAT` | `BIF_FAULT` |
|---|---|---|
| normal event program | 0x4002 (b1) | 0x0e860000 |
| one-row, plain DOUTA | 0x4004 (b2) | 0x0f400000 |
| one-row, `.x2.s27` DOUTA | 0x4004 (b2) | 0x0f400000 |

All recovered. -ETIMEDOUT, all five modules unloaded, the parent runtime-suspended.

**Facts (C):**
- **PA0 still holds 0x0e860000** from the forty-first attempt's one-row DOUTA, half an hour and
  many loads later.
- **With the DOUTA in the `.x2.s27` form, the DOUTU after it still starts the task at code base
  0.** The DOUTA's form isn't what breaks the DOUTU.

**What it suggests (G):** **the next candidates are the DOUTU's data slots** (the microkernel's
own entry programs put DOUTU word 1 = 2 in a data word and word 0 in DS1), **or the order:** a
DOUTU first, then the DOUTA. Whether the `.x2` DOUTA wrote 0x0e870000 isn't known, since no PA0
read followed it.

**Next:** the microkernel session picks between those two.
