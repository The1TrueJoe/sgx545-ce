# SGX530 stage 1, forty-fourth attempt: ten distinct outputs, and a store to the control block faults

**Board:** our OMAP3630 test board, our kernel on the SD (7.3.3, the 02:16 build), up 2 h 35 min
(the same boot as attempts 40-43), the owner-confirmed host key, the board lock held for all
twelve loads. 77 °C before. No hang, no plug cycle.

**What ran:** powervr_sgx from sgx530 c105cac9 (CI: omap3630 43207325632, powervr-sgx
43207316461 and upstream 43207320951, all green; modver-check 0 differ). The images are the
microkernel session's (its branch, da5c4482), built with `ukernel/build.py` and packaged by
`drm/tools/mkukfw.py`. All 22 image and package SHA-256s match the microkernel session's
lists in full.
1. **Distinctness:** `cores/sgx530_odist<k>.py` for k = 0-9, without the sweep. Each image
   writes o0-o9 with ten different values (`or oK, rN, rN`, rN's leftover, no r17), then
   loads through ok. ok faulting at its own source's leftover means the outputs are distinct.
2. **Store from an output:** `cores/sgx530_stout_o0.py` (`or o0, r5, r17`;
   `st.a.d pa0, #0, o0`; a loop), twice.
   - First with `stage1_sweep=1`: the baseline, then a one-row DOUTA writing the address of
     the control block's version word (TA3DCTL + 0x60) to PA0.
   - Then without the sweep, so the task stores o0 through that PA0.

**Facts (C):**
- **o0-o9 are ten distinct, task-writable registers:** each keeps its own value through the
  other nine writes.
- **The forty-third attempt's `.x2.s27` DOUTA wrote PA0 = 0x0e870000.** The store test's first
  run stored through it.
- **The one-row DOUTA wrote PA0 = the control block's version word's address,** and the task's
  `st.a.d pa0, …` took PA0 as its base. The fault is on that page, 0x0f003000.
- **A store from the task to the kernel data arena faults, though the page is mapped.** The
  arena is mapped `CACHECONSISTENT | EDMPROTECT`, as the DDK maps the same buffers. These
  stores, like the kicker read and the code-base-0 fetches, show requestor b2 (0x4004). The
  loads show b1.
- **Whether `st` takes an output as its data can't be seen,** since the store didn't complete.

**What it suggests (G):**
- **EDMPROTECT pages may take writes only from the EDM data master.** If the SGX530 numbers its
  data masters differently from the SGX545's 3 (the value in code base 15's DM field), the task
  isn't the EDM there and its stores fault. That would block every microkernel store to its
  control block.
- **The tests:** code base 15's DM field at 0, 1 and 2, or the data arena mapped without
  EDMPROTECT. Both are new categories, so the coordinator's call.
