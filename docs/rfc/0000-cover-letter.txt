This RFC asks for design review of a render-only DRM driver for the
PowerVR SGX5xx (Series5) GPUs. It is not for merging yet: the Mesa
driver is a draft merge request, and the firmware is not yet in
linux-firmware.

The first platform is the SGX545 in the Intel Atom CE5300, a PCI
function of its own (8086:089b). Unlike the SGX ports of 2019-2020,
both the userspace and the GPU firmware are open, and the driver loads
no vendor binaries.

Design
- drm_sched (one job on the GPU at a time), drm_gpuvm with a page
  directory per VM, drm_exec, GEM shmem objects. The GPU addresses 32
  bits; imports are mapped through its 32-bit DMA mask.
- A table of supported cores (ID, revision, required features,
  firmware name). An unknown core is refused before any register
  write; other Series5 cores are new entries, not a new driver.
- The GPU runs a microkernel on its shader unit. I wrote my own (MIT,
  source public). The driver loads only an image that declares secure
  mode: no client page directory maps the firmware's memory.
- Each client has its own parameter buffer (the tiler's output). When
  consecutive jobs come from different clients, the microkernel saves
  the hardware's free-list state into the outgoing buffer and loads
  the incoming one.
- Client commands are plain structs with per-core extensions, which
  the kernel copies, checks field by field and builds the firmware
  commands from. Shader code is uploaded through an ioctl that checks
  every instruction.
- The GPU doesn't snoop the CPU's caches. A job lists the byte ranges
  of imported buffers it touches, and the kernel flushes them around
  the job. Kernel sync is explicit only; X on simpledrm syncs through
  the dma-buf sync-file ioctls.
- Completion comes from the microkernel's interrupt. Hang recovery
  blames only the context whose job hung, refuses that context's later
  submits, and sends a wedged uevent if the GPU can't be restarted.

Userspace
- A Gallium driver with a NIR compiler: draft Mesa merge request
  [link]. On the CE5300 it passes 16,638 of 17,165 dEQP-GLES2 tests
  with no resets.

Questions for reviewers
1. Placement. Imagination said in 2023 that SGX should have its own
   driver [1]. Alessio, Luigi: drivers/gpu/drm/powervr_sgx beside
   drivers/gpu/drm/imagination, or under it?
2. Cedarview and Poulsbo. Their SGX sits behind gma500. A follow-up
   has gma500 publish it as an auxiliary device that this driver binds
   to, as nova-drm and i915's GSC do; on four Cedarview machines it
   renders with the open firmware. Gabriel Gama is preparing gma500's
   own SGX535 (Poulsbo) code [2]. This driver is separate because it
   also runs hardware without gma500, the CE5300, and an SGX535 or
   SGX544 would be one more core-table entry in it. Is that the right
   split?
3. Cache maintenance for imports is part of SUBMIT_JOBS, as per-job
   byte ranges, rather than a separate BO_SYNC-style ioctl. Is cache
   work in the submit path acceptable?
4. x86 write-combining. Objects are map_wc, so on x86 the shmem helper
   costs three change_page_attr passes per object (two with a clflush
   of every page), per-page PAT calls, and a direct-map split that
   isn't collapsed. That was 10.6% of the X server's CPU in a
   window-drag profile before Mesa cached its objects. Is TTM, cached
   pages with explicit flushes, or a GFP_WC-style allocator the way?

MAINTAINERS lists me alone for now; I'd welcome a reviewer who wants to
share the work.

Not in this series, each a short series of its own: transfer jobs, the
gma500 auxiliary device, and the IGT port of the uAPI tests [link].

Testing: on the CE5300, RAM-booted 7.3.3 test kernels built from this
tree (plus board support outside this series): the uAPI, frame, hang,
PRIME and unbind tests, also under lockdep, KASAN, UBSAN, kmemleak and
DMA-API debug. System suspend is tested with pm_test only. CI builds
every patch on drm-misc-next with checkpatch --strict, sparse, smatch,
coccinelle, gcc and clang W=1, kernel-doc, KUnit, and an i386/x86_64
uAPI layout check.
