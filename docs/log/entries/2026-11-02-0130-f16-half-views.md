# F16 halves read as whole registers: three bugs behind two A/B differences

The EA-1 A/B found two mediump dependent-texture cases that differ from the DDK, and all three
bugs behind them are about 16-bit values that reach 32-bit code.

- `texture2D(t0, v.yx)` drew black. The 32-bit `mov` of the swizzled varying had no way to select
  a half, and `legalize()` let it through, so both coordinates read the whole of `pa0`. A 32-bit
  `mov` of halves is now an alias of them, like `f2f32`, so the coordinate stays F16 and
  takes one `pck.f16.f16` plus `smp .f16`. Where a half does reach a slot with no format select,
  it now goes through a register.
- `texture2DProj(t0, vec3(v, 1.5))` didn't compile ("16-bit constant in a 32-bit instruction"). A
  16-bit register assembled from a varying and a constant reaches the division as a half and an F16
  constant. The projective path and 32-bit ALU now read such a constant as its f32 bits.
- `texture2D(t0, vec2(v.y, 0.5))` crashed the compiler: `pair_reg_plain` and `pair_src` recursed
  forever on a half paired with a constant. The constant now comes from a register holding its half
  bits.

The same dropped half also broke mediump `a < b ? c : d` on varyings: `movc.f32` read
F16 registers as f32 (corpus c3 `fl_*_m/_l`). Those programs now widen each source first and go
from 8 to 16 instructions. They are correct but long; selecting F16 pairs directly would shorten them.

`tools/usc/tests/dep` holds these shapes. Offline, the rest of the corpora are byte-identical,
except for a dead `mov` gone from `tx_nd_*` and `dc_tex_m`. Pixels are for the EA-1 A/B.
