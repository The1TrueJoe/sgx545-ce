# SGX530 stage 1, thirty-eighth attempt: spacing the write and the read apart doesn't help

**Board:** our OMAP3630 test board, openHC on the SD (7.3.3, the 02:16 build), up 1 h 17 min,
the owner-confirmed host key, `hc250.lock` held. No hang, no plug cycle.

**What ran:** powervr_sgx from sgx530 fd97aabe (the >> 8 code-base unit; modver-check 0
differ), `allow_unisolated=1` only, loaded four times.
- **The images:** the microkernel session's `cores/sgx530_aluwr_nop<n>.py` for n = 1, 2, 4
  and 8 (its branch, f110c247), built with `ukernel/build.py` and packaged by
  `drm/tools/mkukfw.py`. All eight hashes match the microkernel session's list.
- **What each does:** `aluwr` (`or r5, r5, r17`; `ld.a.d r3, r5, #0`) with n `nop`s between
  the `or` and the `ld`.
- **Why:** the SGX530 lacks `SGX_FEATURE_USE_NO_INSTRUCTION_PAIRING`, which the SGX545 has
  (K, `sgxfeaturedefs.h`). If the SGX530 pairs a write with the next instruction, that
  instruction could read the old value (G).

**Results:** the same in all four runs. `BIF_INT_STAT` 0x4002 (requestor b1), `BIF_FAULT`
**0x0c004000** (r5's leftover), the USE busy (0x00110000), `EVENT_TIMER` 0, INIT_STATUS 0.
-ETIMEDOUT each time. All five modules unloaded and the parent runtime-suspended.

**Facts (C):**
- **With 1, 2, 4 or 8 `nop`s between the `or` and the `ld`, the load still reads r5's
  leftover.**
- **The thirty-second attempt had 23 `limm`s before its load through r5,** and it read the
  leftover too.

**What it suggests (G):**
- **A pairing or scheduling hazard of up to 8 instructions isn't what hides the writes.**
