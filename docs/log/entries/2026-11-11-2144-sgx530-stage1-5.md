# SGX530 stage 1, fifth attempt: the event-program address register holds 26 bits

**Board:** our OMAP3630 test board, now booting our kernel from its internal SD card (7.3.3,
the 02:16 build, `ohc.boot=sd`). 73.5 °C before and after, thermal zone enabled (105 °C
trip).

**What ran:** one attempt.
- powervr_sgx from sgx530 ffd84d70, built by `powervr-sgx-omap3630` run 43140769549.
  powervr-sgx and upstream were green on the same head. `modver-check.py`: 0 differing CRCs
  against this boot's modules.
- **The one change: the heap layout.** TI's SGX530 DDK bases from PDS pixel up: PDS pixel
  (`PDS_EXEC_BASE`) 0x0d800000, kernel code 0x0ec00000. That follows the GPL DDKs' rule
  that kernel code lie within 64 MiB above the PDS pixel heap on a core without
  `EDM_VERTEX_PDSADDR_FULL_RANGE`.
- The same diagnostic microkernel as attempt 3 (file 845463a3…). The event program now
  sits at 0x0ec04340. `allow_unisolated=1`, no probes.

```
clocks on: clock status 0x00010000 event status 0x00000000 BIF req 0x0 int 0x0 timer 0x00000000
clocks on: PDS PC base 0x00000000 PDS 0x00000000
clocks on: OCP revision 0x40000000 sysconfig 0x00000028 debug config 0x80000000 status 0x023c0707
event PDS registers before any write: enable 0x00000000 base 0x00000000 data 0x00000000 0x00000000
event PDS base 0x0a68: wrote 0x0ec04340, read 0x02c04340
*ERROR* event PDS base doesn't read back; not starting the microkernel
probe with driver powervr_sgx failed with error -5
```

The guard did its job: the start stopped before the events were enabled and before any
kick. All five modules unloaded and the ti-sysc parent runtime-suspended.

**Facts (C):**
- **0x0a68 doesn't hold bits 26 and 27.** 0x0ec04340 reads back as 0x02c04340. With the
  first four attempts' read-backs (bits 6, 7, 14 and 25 held), its field is at most bits
  0-25: a 26-bit value.
- **`PDS_PC_BASE` (0x0b2c) and `PDS` (0x0abc) read 0 after reset**, with the clocks on and
  before any write. Both are named in the SGX530's K header.

**What it suggests:**
- **D:** a 26-bit field is exactly the 64 MiB window of the DDK rule ("kernel code within
  64 MiB above PDS pixel").
- **G:** the likeliest reading is that the event program's address, on a core without
  `EDM_VERTEX_PDSADDR_FULL_RANGE`, is an *offset from `PDS_EXEC_BASE`*, not an absolute
  address. That would also explain attempts 1-4. They wrote the absolute 0x020042c0 or
  0x0200d020 with `PDS_EXEC_BASE` at 0x02c00000. As an offset, that points at about
  0x04c0xxxx, in the general heap, where nothing of ours is. Absolute low 26 bits fit
  attempts 1-4 less well: those addresses were below 2^26 and still didn't run.

**Next** (attempt 6): on a core without the feature, write 0x0a68 = event program −
`PDS_EXEC_BASE` (0x01404340 with this layout), and compare the guard's read-back against
that. Nothing else changes.
