# SGX530 stage 1, seventeenth attempt: a program in unmapped memory starts with no fault

**Board:** our OMAP3630 test board, openHC on the SD (7.3.3, the 02:16 build), up 6 min
after the Bench-plug swap's power cycle. 73.5 °C before and after. The host key was checked
against the owner's on-board reading.

**What ran:** powervr_sgx from sgx530 c7abad77 (CI: omap3630 43167487576, powervr-sgx
43167479877 and upstream 43167483857, all green; modver-check 0 differ),
`allow_unisolated=1 code_base_pads=1 stage1_sweep=1`, with the landing-pad image
`sgx530_bases` (f7de7b95…).

**The question:** after the sixteenth attempt, does the PDS fetch the program from memory at
all? Each variant puts a fetch where only it would fault. After each one the driver checks
`BIF_INT_STAT` and, on a fault, logs `BIF_FAULT` and runs the recovery reset.

| # | Variant | Change |
|---|---|---|
| 0 | baseline | the MOVS + HALT event program |
| 1 | P3 | `PDS_INV0`-`3` = 1 and `PDS_INV_CSC` = 1 after the reset, before the kick (offsets K: the GPL SGX530 header, cores/sgx530.md) |
| 2 | P3 + F1 | the same, with the sixteenth attempt's DOUTD from 0x0e840000 |
| 3 | P2 | 0x0a6c = 0x1000 rows: a code start 64 KiB past the program, unmapped (page 0x0ec14000) |
| 4 | P1 | 0x0a68 = 0x01040000: the program at 0x0e840000, in the unmapped hole past the PDS vertex heap |

Then the fault check.

**Results:**

| # | 0x0a68 read, 0x0a6c/0x0a70 read | `PDS_PC_BASE`, every 10 ms | BIF int |
|---|---|---|---|
| 0 | 0x01404aa0, 0x1/0x6 | 0 136500 0 136500 0 0 0 5012ac 0 5012ac | 0 (req 0x1) |
| 1 | 0x01404aa0, 0x1/0x6 | 5012ac 136500 0 5012ac 0 0 136500 136500 5012ac 0 | 0 (req 0x2) |
| 2 | 0x01404aa0, 0x1/0x6 | 5012ac 0 0 0 0 0 0 136500 0 0 | 0 |
| 3 | 0x01404aa0, **0x0**/0x6 | 0 0 0 0 0 0 136500 5012a8 0 0 | 0 (req 0x2) |
| 4 | **0x01040000**, 0x1/0x6 | **410004** 0 0 0 0 410004 0 410004 410004 136500 | 0 |

- No variant faulted, so no recovery ran between variants. `EVENT_TIMER` stayed 0.
- The third value is 0x136500 this boot. Earlier boots gave 0xf33c, 0xf35c, 0xf75c and
  0xf7dc.
- The fault check: 0x4004 at every sample, `BIF_FAULT` 0x0e800000, then "recovered, BIF int
  0x0".
- -ETIMEDOUT, all five modules unloaded, the parent runtime-suspended.

**Facts (C):**
- **With the event program's address in unmapped memory, the PDS logs that start and nothing
  faults.** 0x410004 × 4 = 0x01040010 is the hole's offset from `PDS_EXEC_BASE` + 16 bytes ×
  0x0a6c. On this core an unmapped read faults and stays faulted until the reset (the fault
  check).
- **So `PDS_PC_BASE` is a start address computed from 0x0a68 and 0x0a6c,** latched whether
  or not anything is at that address. It doesn't show that a fetch happened.
- **0x0a6c doesn't hold 0x1000:** it reads back 0, so it's at most 12 bits wide. With 0 the
  PDS started at row 0 (0x5012a8). P2 therefore didn't test a code fetch.
- **Invalidating the PDS caches before the kick changes nothing:** F1 still doesn't fault.
- **The third value moves between boots** (0x136500 now), with the same image and setup.

**What it suggests (G):**
- **The PDS doesn't fetch the event program from memory before it stops.** No fetch of the
  data row or the code row reached the BIF, at our address or in the hole. Either the
  dispatch stalls after the start address is formed (a resource, a data-store allocation, or
  an event-side condition), or the PDS's fetches take a path whose faults the BIF doesn't
  report the way it reports the kicker read.
- **That would explain attempts 8-16:** no change to the program's contents could matter if
  it's never read.
- **The third value may be another program start the PDS forms on its own,** in a different
  place on each boot. U.

**Next:** for the microkernel session to design. P2 needs a 0x0a6c value that latches and
lands past the mapped arena.
