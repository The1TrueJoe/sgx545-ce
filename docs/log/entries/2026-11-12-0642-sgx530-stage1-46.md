# SGX530 stage 1, forty-sixth attempt: the task's stores don't reach memory, and the pds3 layout doesn't launch

**Board:** our OMAP3630 test board, our kernel on the SD (7.3.3, the 02:16 build), up 2 h 58 min
(the same boot as attempts 40-45, so PA0 still held the control block's version-word address
from the forty-fourth attempt), the owner-confirmed host key, the board lock held. 77 °C
before. No hang, no plug cycle.

**What ran:** powervr_sgx from sgx530 8abc9c05 (CI: omap3630 43210458763, powervr-sgx
43210450680 and upstream 43210454761, all green; modver-check 0 differ). The SGX530 now maps
the kernel data arena without `EDMPROTECT` by default (d8160ba2). Three loads, each with
`allow_unisolated=1`:
1. **`sgx530_stout_r5`** (the microkernel session's control, packaged 486eff53…, matching).
   It runs `or r5, r5, r17` (no effect, since the write doesn't land), then
   `st.a.d pa0, #0, r5`, `idf`, `wdf`, a loop. It stores r5's leftover, 0x0c004000.
2. **`sgx530_stout_o0`** (packaged f9f4c09f…): the same, storing o0 = 0x0fd7d000. It also has
   `idf` and `wdf` after the `st`.
3. **The `pds3` layout:** `sgx530_pa0` with `stage1_sweep=1`.
   - The variants: the normal event program, then e0c4de9c's program.
   - That program's data, two rows: [2, 0, 0, 0, 0x0e880000, 0, 0, doutu], with 0x0a6c = 2 and
     0x0a70 = 8.
   - Its code: DOUTA 0x07040406 (ds0[2], ds1[0]), thirteen `tst ds0[0]` (0x87000000), DOUTU
     0x07003885 (ds1[3], ds0[0] = 2, ds0[1]), HALT.

**Results:**

| Load | `BIF_INT_STAT` | `BIF_FAULT` | Control-block word 0x18 |
|---|---|---|---|
| `stout_r5` | 0 | none | 0 |
| `stout_o0` | 0 | none | 0 |
| `pds3` layout: normal program | 0 | none | |
| `pds3` layout: DOUTA + DOUTU | 0x4004 | 0x0f400000 (code base 0) | |

- In both store loads the USE stayed busy through 500 ms: the task sat in its loop.
- -ETIMEDOUT for each load. All five modules unloaded and the parent runtime-suspended.

**Facts (C):**
- **With the arena mapped without `EDMPROTECT`, a store through PA0 to the control block
  doesn't fault.** That holds for a temporary and for an output.
- **Neither stored value shows in the control-block word at the end of the run,** although
  `idf` and `wdf` follow each `st`.
- **The `pds3` layout's DOUTU after a DOUTA still starts the task at code base 0,** as in the
  fortieth, forty-first and forty-third attempts.

**What it suggests (G):**
- **The task's stores don't reach memory the CPU can see.** That's whatever the source, so not
  a limit on storing an output. Candidates: the USSE's data cache isn't written back by
  `idf`/`wdf`; the store isn't committed; or it goes to another address without faulting.
- **The DOUTU-after-DOUTA problem isn't the data layout, the DOUTU word, DOUTU word 1 or the
  spacing.** What's left from the microkernel session's list: the DOUTA's value taken from an
  input, and the order.

**Next:** a data-cache flush the SGX530 honours, documented in docs/ and tested on hardware
first, not taken from DDK words. And the microkernel session's next DOUTA variant.
