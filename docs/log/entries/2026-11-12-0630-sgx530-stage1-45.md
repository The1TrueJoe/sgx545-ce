# SGX530 stage 1, forty-fifth attempt: EDMPROTECT blocks the task's stores, whatever the data master

**Board:** our OMAP3630 test board, our kernel on the SD (7.3.3, the 02:16 build), up 2 h 46 min
(the same boot as attempts 40-44, so PA0 still held the control block's version-word
address from the forty-fourth attempt's DOUTA), the owner-confirmed host key, the board lock
held. 77 °C before. No hang, no plug cycle.

**What ran:** powervr_sgx from sgx530 5ee84d86 (68a3a4f3 merged; CI: omap3630 43208887218,
powervr-sgx 43208878717 and upstream 43208882578, all green; modver-check 0 differ), with
the coordinator's approval of both parts. Each load uses `allow_unisolated=1`, plus the
parameter shown below.
1. **(a), the data master:** `sgx530_stout_o0` (`or o0, r5, r17`; `st.a.d pa0, #0, o0`; a
   loop; packaged f9f4c09f…) with `stage1_sweep=1`.
   - The variants: code base 15's data-master field at 3 (the baseline, the SGX545's EDM),
     then 0, 1 and 2, with the address field at kernel code >> 8.
   - Before each variant the driver cleared control-block word 0x18, then logged it after.
2. **The margin check:** `sgx530_odist10` (packaged 97f3c862…, matching the microkernel
   session's): it writes o0-o10 eleven distinct values, then loads through o10.
3. **(b), the mapping:** `sgx530_stout_o0` with `stage1_no_edmprotect=1`. The kernel data arena
   is then mapped `CACHECONSISTENT` only, without `EDMPROTECT`.

- In (b) the USE stayed busy (0x00110000) through 500 ms: the task sat in its loop.
- -ETIMEDOUT for each load. All five modules unloaded and the parent runtime-suspended.

**Facts (C):**
- **A store from the task into the kernel data arena faults while the arena is mapped
  `EDMPROTECT`,** with code base 15's data master at 0, 1, 2 or 3.
- **With the arena mapped without `EDMPROTECT`, the same store doesn't fault.**
- **o10 keeps its own value (r17's leftover) through the other ten writes:** eleven distinct
  task-writable outputs.
- **The stored value didn't show in control-block word 0x18 by the end of the run,** with
  `EDMPROTECT` off.

**What it suggests (G):**
- **On the SGX530, `EDMPROTECT` pages refuse the microkernel task's stores,** however code base
  15 is set. Either the SGX530 doesn't treat this task as the EDM, or `EDMPROTECT` means
  something else there. Without the flag, the SGX530 microkernel could store to its control
  block.
- **The value may still be in the USSE's data cache:** `stout_o0` has no `idf`/`wdf` after its
  `st`. A version with a flush would show whether it reaches memory.
- **This bears on the SGX530's normal start,** not only the sweep: its microkernel stores to its
  control block constantly. Mapping the arena without `EDMPROTECT` on the SGX530 is the
  coordinator's call.
