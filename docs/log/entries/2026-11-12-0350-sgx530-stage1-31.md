# SGX530 stage 1, thirty-first attempt: each register faults at its own leftover value

**Board:** our OMAP3630 test board, our kernel on the SD (7.3.3, the 02:16 build), up 5 min,
the owner-confirmed host key, the board lock held. 77 °C before, 75 °C after. No hang, no
plug cycle.
- A first try at 08:50 UTC stopped on a shell-script error (an unsplit list) after copying
  the modules, before any insmod. I released and retook the lock around it.

**What ran:** powervr_sgx from sgx530 fd97aabe (the >> 8 code-base unit; modver-check 0
differ), `allow_unisolated=1` only, loaded nine times.
- **The images:** the microkernel session's `cores/sgx530_ldreg_r<n>.py` for n = 0, 1, 2,
  3, 4, 6, 8, 16 and 31 (its branch, 1aa5d893), built with `ukernel/build.py` and packaged
  by `drm/tools/mkukfw.py`. All 18 image and package hashes match the microkernel
  session's list.
- **What each does:** `ld.a.d r3, rN, #0`, gated by a `str` to `EVENT_TIMER`. The probe
  doesn't write rN first.

**Results:** every load faulted with `BIF_INT_STAT` 0x4002 (requestor b1). `EVENT_TIMER`
stayed 0 and INIT_STATUS 0 in every run.

| Base register | `BIF_FAULT` |
|---|---|
| r0 | 0x0055d000 |
| r1 | 0x0722a000 |
| r2 | 0x003e1000 |
| r3 | 0x08439000 |
| r4 | 0x09e06000 |
| r5 (attempts 29-30, written by `limm` first) | 0x0c004000 |
| r6 | 0x0503f000 |
| r8 | 0x08779000 |
| r16 | 0x002ba000 |
| r17 (attempts 24-29, the patched `limm` first) | 0x0fd79000 |
| r31 | 0x0d04f000 |

- -ETIMEDOUT each time. The failed-start path held the cores in reset, then all five
  modules unloaded and the parent runtime-suspended.

**Facts (C):**
- **Every base register gives its own fault page,** with no pattern in the register
  number.
- **The pages for r5 and r17 were the same in every probe, across three boots,** whatever
  value a `limm` wrote to them before the load (thirtieth attempt for r5).

**What it suggests (G):**
- **The load reads the register it names, and each register holds a stable leftover value
  at task start.** These look like the registers' power-on or reset contents.
- **So the `limm` writes before the loads never reached r5 or r17.** The question is no
  longer the load or `limm`'s value bits, but `limm`'s destination or whether it executes
  at all on the SGX530. This replaces the twenty-ninth and thirtieth attempts' readings of
  where the load takes its base.

**Next:** for the microkernel session. A probe could write r5 with something other than
`limm` (a `mov` from a constant or another register) before the same load, to see whether
any write reaches it.
