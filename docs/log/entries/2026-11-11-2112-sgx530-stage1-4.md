# SGX530 stage 1, fourth attempt: not the temporaries, not the code-base unit

**Board:** our OMAP3630 test board, the same 7.3.3 boot as the third attempt (105 °C
critical trip, thermal zone enabled). 78.5 °C before, 77.0 °C right after, 78.5 °C after
the unload.

**What ran:** one attempt with two changes, agreed as a combined run.
- powervr_sgx from sgx530 64ac374c, built by `powervr-sgx-omap3630` run 43138623572.
  powervr-sgx, upstream and ukernel-sgxasm were green on the same head. `modver-check.py`:
  0 differing CRCs against this boot's modules.
- **The temporaries change** (a8a66544): the SGX530's entry DOUTU asks for 24 temporaries
  (bits 24-31 = 6), not 32.
- **The code-base unit probes** (54671f80, `code_base_probes=1`): for the first start,
  nine code-arena pages mapped read-only into the firmware MMU at 0x00040000, 0x00080000,
  0x00100000, 0x00200000, 0x00400000, 0x00800000, 0x01000000, 0x04000000 and 0x08000000.
  Those are where code base 15 (field 0x40000) would start if the field's unit were 1, 2,
  4, 8, 16, 32, 64, 256 or 512 bytes.
- **The microkernel** `sgx530_probe` (image 1356a4c5…, 53272 B, file fa39d633…, crc
  0xd6bbd623, event program at 0x0200d020):
  - offset 0 is the third attempt's diagnostic ladder (its first step writes
    `EVENT_TIMER` = 0xa5a);
  - each probe page holds `limm r0, #0xb00+k; str EVENT_TIMER`.

All five modules unloaded and the ti-sysc parent runtime-suspended.

**Result: the runbook's "0" row.** `EVENT_TIMER` stays 0 at every sample. No probe ran
(no 0xb0k), and the ladder at the 128-byte base didn't run either (no 0xa5a).

**What it rules out** (C, within what the probes cover):
- **The temporaries request.** Asking for 24 instead of 32 changes nothing.
- **The code-base unit, if it's a power of two from 1 to 512 bytes.** A task started at
  base 15 under any of those units would have found a probe, and none ran. (1 KiB and up
  start past the 28-bit space.)
- With the third attempt: **the DOUTU's code offset and base aren't what's wrong on their
  own.** Or no USSE task is being started at all.

**What's left**, in the runbook's order (all G):
1. `0xa6c`/`0xa70`, the event program's two data registers (1 and 6, a guess on the SGX545
   too).
2. DOUTU word 1 (2).
3. The entry program's MOVS selects under a one-word interleave.

The USE clocks still turn on at the kick and the BIF reads still come and go (2, 0, 2, 2,
2), so something in the USE clock domain is busy without starting our task. That's
consistent with the PDS running but never reaching, or never completing, its DOUTU.
