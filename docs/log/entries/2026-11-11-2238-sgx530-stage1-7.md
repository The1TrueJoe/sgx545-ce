# SGX530 stage 1, seventh attempt: the host-side sweep, and no SGX driver on stock

**First, the stock firmware read (option a), done by the board owner.** The board's stock
firmware (Linux 2.6.32-47.41, 2014) has **no SGX driver**: nothing in `/proc/devices` or
`/proc/modules`, no `/dev/pvrsrvkm`, nothing in dmesg. Its Flash UI renders in software.
The gate check, read twice with a one-word `/dev/mem` reader, read-only:
- `CM_FCLKEN_SGX` (0x48004b00) = 0, so `sgx_fck` is gated;
- `CM_IDLEST_SGX` (0x48004b20) = 1, so the module is idle.

The GPU window wasn't read. Stock never powers the SGX, so there's no vendor event-program
state on this board to read (C).

**Board for the sweep:** our kernel on the SD, 7.3.3 (the 02:16 build). 75 °C before and after.

**What ran:** powervr_sgx from sgx530 4ec4e22b (CI: omap3630 43145384064, powervr-sgx and
upstream green), `allow_unisolated=1 stage1_sweep=1`, with the diagnostic image
(845463a3…). The baseline is attempt 6's: TI's layout, 0x0a68 as an offset from
`PDS_EXEC_BASE`, and the 24-temporary DOUTU. After the baseline's kick, each variant:
- resets the cores;
- makes one change;
- kicks;
- polls `EVENT_TIMER` for 100 ms.

| # | Change | `EVENT_TIMER` | BIF req |
|---|---|---|---|
| 0 | none (baseline) | 0 | 2 |
| 1 | 0x0a6c/0x0a70 = 2, 6 | 0 | 0 |
| 2 | = 4, 6 | 0 | 2 |
| 3 | = 1, 2 | 0 | 2 |
| 4 | = 0, 0 | 0 | 1 |
| 5 | DOUTU word 1 = 0 | 0 | 2 |
| 6 | the entry data in the 2-dword interleave | 0 | 0 |
| 7 | `USE_CODE_BASE_15` data master 2 | 0 | 2 |
| 8 | `PDS` b6 (DOUT_TIMEOUT_DISABLE) | 0 | 0 |
| 9 | event-program enable 0x7fffffff | 0 | 2 |

`sweep: no variant starts the event program`. The normal 500 ms init wait then also stayed
at 0. All five modules unloaded and the ti-sysc parent runtime-suspended.

**Facts (C):**
- **No single change on the list starts the event program.**
- **Each variant started from an idle core.** After every reset `CLKGATESTATUS` was back to
  its pre-kick 0x00010000 (no "not independent" warning). So a stuck unit didn't carry
  over, and the variants are independent.
- **`USE_CLKS` (b20) turns on after every kick.**
- **`PDS` (0x0abc) b6 is writable.** It read 0x40 in variant 8 and 0 elsewhere.
  `PDS_PC_BASE` (0x0b2c) read 0 throughout.

**Next lead** (G, from the K header): `PDS_PC_BASE` (0x0b2c, the SGX530-only "PDS
program-counter base", a 30-bit address) has never been written, and reads 0. If it is
what the 26-bit event-program offset in 0x0a68 is added to, the PDS fetches from about
0x0140434x, where nothing is mapped. On the SGX545, 0x0b24-0x0b2c (unnamed there) are among
the registers a render loads from the 3D command (UKERNEL.md). On the SGX530 the vendor's
closed init would set it. The next attempt:
- `PDS_PC_BASE` = `PDS_EXEC_BASE` (0x0d800000) in the normal start;
- the sweep also tries `PDS_PC_BASE` = the event program's own address (variant 10) and =
  the kernel code base (variant 11).
