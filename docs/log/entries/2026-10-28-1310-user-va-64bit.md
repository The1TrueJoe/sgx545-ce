# Native 64-bit clients map above 4 GB

The first blob-free replay only worked because it asked for low memory. A
native x86_64 process gets its mmaps near `0x7f…`, and the kernel driver
still had two places that kept a user address in 32 bits:

- `DoMapToUser` (mmap.c) walked the VMA with an `IMG_UINT32 ulVMAPos`, so
  mapping device memory above 4 GB failed with `VM_INSERT_PAGE failed (-14)`;
- `OSAcquirePhysPageAddr` (osfunc.c) truncated the address of a buffer being
  wrapped, so `WRAP_EXT_MEMORY` of a high buffer failed with "Start address …
  is outside of the region returned by find_vma".

i386 clients through the compat layer never get such addresses, which is why
nobody had hit this. The replay worked around it with `MAP_32BIT`.

## The fix

User addresses are `unsigned long` from the mmap offset record
(`ulUserVAddr`) through the VMA walk to the page lookup (`CPUVAddrToPFN`). The
bridge's OUT fields stay `IMG_UINT32`, because they are part of the i386 ABI
the DDK was built against, and a native client gets its address from `mmap`
itself. On sgx545-ce `user-va-64bit` (4e5ceb4); in this tree it is already in
`kernel/`.

## How it was tested

`replay` has two switches for this: `-W` puts the wrapped back buffer above
4 GB, and `-H` also maps all device memory without `MAP_32BIT`. The same
captured frame ran in all three modes, then the i386 DDK probe ran, on the
EA3 before and after the fix. The new kernel came from openHC CI
(`sgx-user-va-64bit` a3f3667, which is PR #101 plus the submodule bump) and
was booted once from RAM through `/boot/bzImage.once`, never flashed.

| Kernel | Mode | Device memory CPU span | Wrap | Result |

| Oct 26 (before) | `-W` | | high | `WRAP_EXT_MEMORY` failed (find_vma) |

The i386 probe read back md5 `232e4930…` (= `ref.rgba`) on both kernels, so
the compat path is unchanged. No `DoMapToUser`, `VM_INSERT_PAGE` or
find_vma message appeared on the new kernel. Data:
`data/2026-10-28-1310-user-va-64bit.csv`.

## What was not checked

Each mode ran once on the new kernel. The repeats were spoiled: a gl4es ctest
started by another session put the GPU into a failing recovery loop about a
minute later (see `2026-10-28-1230-hwr-sleep-in-timer.md`), and every repeat
produced no dump.

`libpvr` can now drop `MAP_32BIT` for native clients on a kernel with this
fix; the replay keeps it as the default so it still runs on older kernels.
