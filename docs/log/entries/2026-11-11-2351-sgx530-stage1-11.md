# SGX530 stage 1, eleventh attempt: the event program's MOVS fields

**Board:** our OMAP3630 test board, our kernel on the SD (7.3.3, the 02:16 build). 75 °C
before, 73.5 °C after.

**What ran:** powervr_sgx from sgx530 923207c0 (CI: omap3630 43156660164, powervr-sgx and
upstream green), `allow_unisolated=1 code_base_pads=1 stage1_sweep=1`, with the
landing-pad image `sgx530_bases` (f7de7b95…).
- **The baseline:** the tenth attempt's, with the pads on code bases 0-14 at their usual
  data masters.
- **Each variant changes the event program's MOVS only:**
  - its DOUT destination (b0-4): 4, 6, 7, 1, 0, 2, against the SGX545's 5; 3 (the DMA) is
    left out;
  - its condition (b24-26): 3, then 0, against 7;
  - or an all-slots row: every data word the DOUTU word, every select at it.
- **The fault check last.**

| # | Variant | `PDS_PC_BASE`, every 10 ms |
|---|---|---|
| 0 | baseline (dest 5, cc 7) | 0 5012ac 0 0 0 0 0 0 0 0 |
| 1 | dest 4 | f75c 0 0 f75c 0 0 f75c 5012ac f75c f75c |
| 2 | dest 6 | 0 0 0 5012ac f75c 0 0 f75c 0 f75c |
| 3 | dest 7 | 5012ac 0 f75c 0 0 5012ac 5012ac 5012ac 5012ac 5012ac |
| 4 | dest 1 | f75c 0 5012ac 0 f75c 0 f75c 5012ac 0 0 |
| 5 | dest 0 | 0 5012ac 0 0 5012ac f75c 5012ac 0 5012ac 0 |
| 6 | dest 2 | 5012ac 0 0 0 0 0 0 5012ac f75c 5012ac |
| 7 | cc 3 | 5012ac 0 f75c 0 0 0 5012ac f75c 0 0 |
| 8 | cc 0 | 5012ac 0 0 0 0 0 f75c f75c 0 0 |
| 9 | all four slots the DOUTU word | 0 0 0 0 5012ac f75c 0 f75c 0 f75c |

- `EVENT_TIMER` stayed 0 in every variant: no ladder value and no pad value.
- No "not independent" warning.
- The fault check reported the fault as in the tenth attempt (`BIF_INT_STAT` 0x4004,
  `BIF_FAULT` 0x0e800000) and recovered (BIF int 0).
- -ETIMEDOUT, all modules unloaded, the parent runtime-suspended.

**Facts (C):**
- **None of the MOVS destinations, conditions or the all-slots row starts a task.** No
  pad fires, so no task went through code bases 0-14 either.
- **The PC pattern doesn't change with the MOVS's destination or condition.** Even with
  cc 0 it still visits 0x5012ac, the event program's first instruction, and the third
  value.
- **The third value is 0xf75c with the same image that gave 0xf33c in the tenth attempt.**
  So it doesn't follow the image. It may not be one of our addresses at all (U).

**What it suggests (G):**
- A MOVS whose fields make no difference, with a PC that keeps reaching the program's
  first instruction, suggests the PDS reaches that instruction and goes no further: it
  restarts or idles.
- In that case the fields after the first instruction never mattered. The first
  instruction itself, or what the PDS needs before it can execute (its data segment, the
  program's attribute or size words: 0xa6c/0xa70 or the enable value), is what's wrong.
