# SGX530 (TI OMAP3630)

The fact sheet for the second core: the PowerVR SGX530 in TI's OMAP3630 / DM3730 family
(ARMv7 Cortex-A8). It collects what public sources say, compares it with the SGX545 we
know from hardware, and lists what a hardware test must confirm before any of it goes into
the driver tables. The first facts read from an SGX530 are the core ID and revision
(2026-11-11); everything else still waits for hardware.

The method is [state.md](../state.md)'s: every fact carries a tag. A fact stays below
**C** until our own hardware read confirms it, however good its source.

| Tag | Meaning |
|---|---|
| **L** | Mainline Linux 7.3.3: the device tree, its binding, or a driver. The text is in the tree. |
| **K** | The GPL kernel side of an SGX DDK: its register, feature, errata and MMU headers. They describe what that DDK programs, not the silicon itself. |
| **D** | Derived from L or K facts, often with an SGX545 result we confirmed on hardware. |
| **C** | Confirmed on SGX530 hardware: our OMAP3630 test board. |
| **G** | A guess. |
| **U** | Unknown. |

  `sgx530defs.h`, `sgxfeaturedefs.h`, `sgxerrata.h`, `sgxmmu.h`.
- **K, both cores:** the GPL kernel drop the SGX545 work started from: its `sgx545defs.h`,
  `sgxfeaturedefs.h`, `sgxerrata.h`, `sgxmmu.h`, and the host-side workaround code in
  `sgxutils.c`.
- **K, TI's OMAP3 services:** the GPL-2 kernel side of TI's OMAP3 graphics services (PVR
  services 1.4 for OMAP3430/3630, as carried in a 2.6.35 DM3730 board kernel,
  `drivers/gpu/pvr/`): `ocpdefs.h`, `sysconfig.c`, `sysutils.c`, `sgxreset.c`,
  `sgxinit.c`. Read 2026-11-11 for the OCP wrapper ("The OCP wrapper" below).
- No closed userspace, firmware or non-GPL vendor file was used.

The DDK's register headers list only the registers the host kernel touches. The TA, 3D,
DPM, ISP, TSP, PBE and PDS state registers that the microkernel and the command streams
program aren't in them, for either core. Everything about those is **U** for the SGX530.

| `EUR_CR_CORE_ID` | offset 0x0010; config b0-15, id b16-31 | K |

The expected revision is derived two ways:
- The DDK writes revisions as decimal digits, major.minor.maintenance. The SGX545's "1014"
  is the 1.0.14 our CE5300 reads as `0x0001000e`, and "1013" is Cedarview's `0x0001000d`
  (hardware). So 125 is 1.2.5.
- `ti-sysc.c` matches an OMAP34xx GPU by reading offset 0x14 of the module and expecting
  `0x00010201`: rev 121 in that encoding, at the 0x14 `sgx530defs.h` gives for
  `CORE_REVISION` (L).

Offsets are from the start of the GPU's register window. The SGX545 column is from its K
header; where we confirmed an SGX545 register on hardware, the hardware agrees with it.

| `CLKGATECTLOVR` | 0x0008 | 0x000c | K |

## Clock gating

| | SGX530 | SGX545 | Tag |
|---|---|---|---|
| Gated units | 2D, ISP, TSP, TA, DPM, USE: one 2-bit control each | ISP, ISP2, TSP, TE, MTE, DPM, VDM, PDS0 and more | K |
| `CLKGATECTL` | 2D b0-1, ISP b4-5, TSP b8-9, TA b12-13, DPM b16-17, USE b20-21, auto/manual b24 | ISP b0-1, ISP2 b2-3, TSP b4-5, TE b6-7, MTE b8-9, DPM b10-11, VDM b12-13, PDS0 b14-15; auto/manual b24 | K |
| `CLKGATESTATUS` | 2D b0, ISP b4, TSP b8, TA b12, DPM b16, USE b20 | 20 units, one bit each (ISP b0, DPM b5, ...) | K |
| `CLKGATECTLOVR` | the `CLKGATECTL` layout | the SGX545's own layout | K |
| Automatic clock gating | yes (`SGX_FEATURE_AUTOCLOCKGATING`) | yes | K |

The SGX545's status bits match what we measured with regsample (b0-1 the 3D side, b5 the
DPM). The SGX530's coarser status means its busy split works per unit: TA (b12), ISP and
TSP (the 3D side), DPM, USE and 2D, with no separate texture, PBE or PDS bits. The
`tools/state/busysplit.py` groups need an SGX530 table (D).

## Reset

`SOFT_RESET` at 0x0080 (K):

| Bit | SGX530 | SGX545 |
|---|---|---|
| 0 | BIF | BIF |
| 1 | 2D | DPM |
| 2 | DPM | TA |
| 3 | TA | USE |
| 4 | USE | ISP |
| 5 | ISP | TSP |
| 6 | TSP | (more units above) |

Every unit above the BIF moves up a bit, because the 2D reset takes bit 1.

## Events and kicks

- `EVENT_STATUS` keeps the SGX545's bit positions for every event the two share: master
  interrupt b31, timer b29, TA DPM fault b28, the DPM out-of-memory events (global b2,
  macrotile b1, ZLS b25), DPM state and control store/load/clear (b4-9), DPM memory free
  (TA b24, 3D b0), memory threshold b3, TA finished b13, TA terminate b12, TPC flush b10,
  TPC clear b11, ISP end tile b23, pixel BE end render b18, visibility fail b16, software
  event b14, breakpoint b15 (K).
- Only on the SGX530: 2D complete b27, OTPM loaded b21 (on the SGX545, b21 is the ISP2 ZLS
  context-switch finish), ISP halt b17 (K).
- `EVENT_STATUS2` has only the DPM TA and 3D free-load events (b0, b1). The SGX545's
  triggers, VDM context, GSG, MTE, DCU and OTPM events there are absent (K).
- The SGX545's event-program enable value, 0x2204b00f (measured), sets b0-3, b12, b13,
  b15, b18, b25 and b29: 3D memory free, the three out-of-memory events and the threshold,
  TA terminate and finished, breakpoint, pixel BE end render, ZLS out-of-memory and the
  timer. If the enable register's bits follow `EVENT_STATUS` (as the SGX545 value
  suggests), every one of them sits at the same position on the SGX530, so the same value
  enables the same events. It leaves the SGX530's own b17, b21 and b27 off (D; the
  register's offset is G until stage 1).
- `EVENT_KICKER` takes a 28-bit address (b4-27); the SGX545's takes 32 bits (K).
- **One kick register.** The SGX530 has no `SGX_FEATURE_MULTI_EVENT_KICK`, and
  `FIX_HW_BRN_22934` removes it from any core whose errata list it (K). Only `EVENT_KICK`
  at 0x0ac8 exists (`NOW` b0).

## The BIF and the MMU

| Fact | SGX530 | SGX545 | Tag |
|---|---|---|---|
| Device address space | 28 bits (256 MiB) | 32 bits | K |
| Memory contexts | one: `DIR_LIST_BASE0` only, no bank registers | 16 directory lists, per-requestor banks | K |
| `DIR_LIST_BASE0` address | b12-31, page-aligned | b8-31, with a 4-bit shift for 36-bit physical addresses | K |
| Page size | 4 KiB; no variable page sizes | 4 KiB to 4 MiB per directory entry | K |
| PDE, PTE address | b12-31: 4 KiB frames anywhere in 32-bit physical memory | b8-31 with the shift | K |
| PTE flags | valid b0, write-only b1, read-only b2, cache-consistent b3, EDM-protect b4 | the same | K |
| PDE flags | valid b0, write-only b1, read-only b2, cache-consistent b3, EDM-protect b4 | valid b0, page size b1-3 | K |
| `BIF_FAULT` address | b12-27 | b12-31 | K |
| Requestor bases (`TA`, `3D`, `ZLS`, `TWOD_REQ_BASE`) | b20-27: a 1 MiB-aligned base in the 28-bit space | b20-31 | K |
| `BIF_CTRL` bypass bits | cache b8, VDM b9, TE b10, 2D b11, PBE b12, TSPP b13, ISP b14, USE b15 | cache b8, VDM b9, TE b10, PBE b11, TSPP b12, ISP b13, USE b14, host b15 | K |
| `BIF_CTRL` low bits | no-reorder b0, pause b1, flush b2, `INVALDC` b3, clear fault b4 | the same | K |
| `BIF_INT_STAT` | fault b0-13, page-fault read/write b14 | other fields | K |
| `BIF_MEM_REQ_STAT` reads | b0-7 | b0-10 | K |

The PDE flags come from a DDK 1.4 header and differ from the later one we used for the
SGX545. The page-size bits of the later layout sit where the 1.4 header puts write-only and
read-only. Which layout the SGX530 silicon decodes is **U**; the safe first mapping sets
only the valid bit in the PDE, which both read the same.

**`FIX_HW_BRN_28889`** (K): when a command needs a data-cache invalidate and a BIF page
table or page directory invalidate together, the host first sends the microkernel a
command that does only the BIF invalidate, waits for it to report completion, and only then
sends the command with the data invalidate. The two must not be issued together.

## The USSE and its code base

- The SGX530 runs the USSE (first generation) instruction set, the same family as the
  SGX545 ([the porting README](../README.md); D).
- **2 USE pipes** (`SGX_FEATURE_NUM_USE_PIPES`), against the SGX545's 4 (K).
- The SGX545-only features `USE_NO_INSTRUCTION_PAIRING` and `USE_UNLIMITED_PHASES` aren't
  set for the SGX530 (K). What that means for encodings and scheduling is **U**: the
  feature names suggest that the SGX530 pairs instructions and limits the phases of a
  program, but nothing in the K sources defines either (G).
- `USE_CODE_BASE(n)`: the address field is b0-23 (24 bits) and the data master b24-25. On
  the SGX545 they're b0-24 and b25-26 (K). The header gives no unit for the address
  field (`ADDR_SHIFT` 0, no `ADDR_ALIGNSHIFT`).
- **The address field counts 256-byte units on the SGX530: the EDM task's code fetch is at
  (field << 8) & 0x0fffffff (C).** The SGX545's unit is 128 bytes. Stage 1 measured it by
  the fault page (logs 2026-11-12-0300 and -0311): 0x1d8000 → 0x0d800000, 0 → 0, 0x100000
  → 0 (0x10000000, beyond 28 bits), 0x1b0000 → 0x0b000000. With the SGX545's unit, code
  base 15 named `PDS_EXEC_BASE` instead of the kernel code heap. The driver keeps the unit
  per core (`use_code_base_addr_shift`).
- F16 arithmetic, the C10 fixed-point format and the `efo` instruction are SGX545 facts in
  [ISA.md](../../ISA.md). Whether the SGX530 has each is **U**. No public source we may use
  says.

**What needs the ISA first.** The open microkernel needs only the SGX545 microkernel's own
forms: integer and bitwise ops, `limm`, `mov`, `test`, the loads and stores, `ldr`/`str`,
the branches, link, `phas`, `idf`/`wdf`. It uses no float, F16, C10 or `efo`. The compiler
needs the rest. Mesa's 530 entry compiles F32 only (`f16` off) and encodes with the SGX545's
description until `sgx.xml` has an SGX530 range.

**The test order** (gap 10). `hwt_open.py` with `sgx_hwt` from `mesa/build.sh armv7`. It
draws through the open stack, so it needs the 530 to render a frame first (the
microkernel's stage 5), not only the driver loading. Then, one suite at a time, with each
result recorded in ISA.md as a per-core note:
1. `hwt_sanity` (the readout path), `hwt_ba`;
2. the microkernel's forms: `hwt_p2` (test, predicated moves, branches), `hwt_gaps`
   (loads and stores, `ima32`);
3. float: `hwt_p1`, `hwt_p3` to `hwt_p5`, then `hwt_p13` (`pck`);
4. F16 and C10: `hwt_p6`, `hwt_p7`, `hwt_p10`, `hwt_p11`. A core without them reads back
   the clear color or an F32 result: record which;
5. `efo` and `fdual`: `hwt_p12`.

## Other features

From `sgxfeaturedefs.h` (K). Set for the SGX545 and not for the SGX530:
- volume textures;
- the texture-stride extension;
- host allocation from the DPM;
- `PDS_DATA_INTERLEAVE_2DWORDS`, and 2 PDS pipes. [PDS.md](../../PDS.md)'s data
  layout (DS0 and DS1 interleaved two words at a time) is the SGX545's. How the SGX530
  lays out a PDS program's data is **U**; one word at a time is a guess (G). Every PDS
  program depends on it: the kernel's microkernel entry and event programs and Mesa's
  vertex and pixel programs. An entry program that reads only memory words 0 and 3 of a
  row, plus words 1 and 2 set to the same value, runs the same under both layouts;
- the monolithic microkernel;
- external Z for the ZLS;
- native backward blits;
- 512 TA render targets (`MAX_TA_RENDER_TARGETS`);
- secondary programs requiring a USE kick;
- the write-back DCU;
- `BIF_WIDE_TILING_AND_4K_ADDRESS`;
- the full-range vertex PDS address in the EDM.

Set for the SGX530: the 28-bit address space, automatic clock gating, an MP core count of
1, and the 2D unit's registers and events above. `SGX_FEATURE_2D_HARDWARE` is the name the
later cores use for their 2D unit; the SGX530's feature block doesn't set it, though its
register header has a 2D block. Whether its 2D unit is useful to us is **U**.

The `50000000.gpu` platform device exists on our OMAP3630 test board with no driver bound, so its SoC
isn't one of the variants without the GPU (D).

The SGX545 is a PCI function: BAR registers, MSI, PCI power states. The SGX530 is a
platform device behind ti-sysc, so the driver's runtime PM goes through the parent module
(pm_runtime on the GPU device powers the module up and applies the quirk). When
`sgx_pwrdm` turns off, the GPU loses all state (D): the driver must reload the microkernel
and the BIF setup on every power-up, as it does after recovery.

## The PDS address range and the heap order

**The kernel code heap must lie above the PDS pixel heap, within 64 MiB (K).** Both GPL
DDK kernels we have check this at build time for a core without
`SGX_FEATURE_EDM_VERTEX_PDSADDR_FULL_RANGE`, and the SGX530 lacks that feature ("Other
features" above). The check, from `sgxconfig.h` (Intel's DDK 1.7, in this repo under
`kernel/src`):

    #if !defined (SGX_FEATURE_EDM_VERTEX_PDSADDR_FULL_RANGE)
        #if ((SGX_KERNEL_CODE_HEAP_BASE + SGX_KERNEL_CODE_HEAP_SIZE - SGX_PDSPIXEL_CODEDATA_HEAP_BASE) >  0x4000000)
            #error "sgxconfig.h: ERROR: SGX_KERNEL_CODE_HEAP_BASE out of range of SGX_PDSPIXEL_CODEDATA_HEAP_BASE"

The same check applies to the PDS vertex heap. The subtraction is unsigned, so a kernel
code heap *below* the PDS pixel heap fails it too.

**The DDKs' 28-bit layouts both comply:**

| Heap | Intel DDK 1.7 | TI DDK 1.4 (OMAP3) |
|---|---|---|
| PDS pixel | 0x0DC00000 | 0x0D800000 |
| Kernel code | 0x0E400000 | 0x0EC00000 |
| PDS vertex | 0x0E800000 | 0x0E000000 |
| Kernel data | 0x0F000000 | 0x0F000000 |

**powervr_sgx's SGX530 layout (stage 1, attempts 1-4) breaks it:** kernel code at
0x02000000 sits below the PDS pixel heap at 0x02c00000, which is what `PDS_EXEC_BASE`
points at. The SGX545's layout (kernel code 0x30000000 above PDS pixel 0x2e000000)
complies, as the SGX545 would need to without the feature.

**From stage 1's fifth attempt on**, the SGX530 layout uses TI's bases from PDS pixel
up (kernel code at 0x0EC00000), and `pvrsgx_core_family_usable()` refuses a layout that
breaks the rule on a core without the feature (`PVRSGX_FEATURE_EDM_VERTEX_PDSADDR_FULL_RANGE`,
set for the SGX545).

The event-program address register (0x0a68) holds only bits 0-25 on the SGX530 (C, stage 1
attempt 5: 0x0ec04340 reads back as 0x02c04340). That is the same 64 MiB, which makes it
likely (G) that the address it takes is an offset from `PDS_EXEC_BASE`. powervr_sgx writes
it that way on a core without the feature (`event_pds_addr()`).

**For later stages (G):** 0x0a5c, the pixel-event (end-of-tile) PDS program, sits in the
same register block as 0x0a68 and is almost certainly the same kind of address. The
microkernel copies it raw from the 3D command (render data +0x5c), and the uAPI's
`pixel_event_pds_addr` is an absolute VA. So on the SGX530 the kernel's 3D command builder
(`pvrsgx_render.c`) should write it relative to `PDS_EXEC_BASE`, like `event_pds_addr()`,
before stage 5. 0x0aa0, loaded from the TA command (+0x270), is unnamed in every source:
if it turns out to be a PDS address, the same applies. The DOUTU words (code-base
relative), `EVENT_KICKER` (a BIF memory address) and 0x0a6c/0x0a70 (not addresses) stay as
they are.

What the hardware does with an address outside the range is U. One reading that fits
attempts 1-4 is that PDS code addresses are taken relative to `PDS_EXEC_BASE` in a 26-bit
window, so the event program at 0x0200xxxx is fetched from somewhere else.

## The OCP wrapper

The SGX's OCP (interconnect) wrapper sits at 0xfe00 to 0xff10 in the GPU window, inside the
32 MiB the DT gives the GPU node. Mainline names two of its registers (`rev` and `sysc`)
and writes a third. TI's OMAP3 services name the rest.

| Register | Offset | Fields | Tag |
|---|---|---|---|
| `OCP_REVISION` | 0xfe00 | the whole word; ti-sysc matches 0x40000000 | K, L |
| `OCP_HWINFO` | 0xfe04 | system bus width b0-1, memory bus width b2 | K |
| `OCP_SYSCONFIG` | 0xfe10 | idle mode b2-3, standby mode b4-5 | K, L |
| `OCP_PAGE_CONFIG` | 0xff00 | memory page size b0, page check enable b2, size b3-4 | K |
| `OCP_INTERRUPT_EVENT` | 0xff04 | initiator: unexpected response b0, unused tag b1, response error b2, page cross b3, read-tag FIFO overrun b4, request FIFO overrun b5; target: response FIFO full b8, command FIFO full b9, invalid command b10 | K |
| `OCP_DEBUG_CONFIG` | 0xff08 | force target idle b0-1, force initiator idle b2-3, force pass data b4, select initiator idle b5, `THALIA_INT_BYPASS` b31 | K, L |
| `OCP_DEBUG_STATUS` | 0xff0c | target: MConnect b0-1, SConnect b2, SIdleReq b3, SDiscAck b4-5, SIdleAck b6-7; initiator: MConnect0 b8-9, SConnect0-2 b10-12, MDiscAck b13-14, MDiscReq b15, MWait b16, MStandby b17; target command out b18-20, which target register b21-25, response error b26, command FIFO full b27, response FIFO full b28, target idle b29, command-response and command debug states b30, b31 | K |

What the published host code does with it:
- **TI's services** write one OCP register: `OCP_DEBUG_CONFIG` = `THALIA_INT_BYPASS`, on the
  OMAP3630 only, right after enabling `sgx_fck` and `sgx_ick` (`sysutils.c`,
  `setup_int_bypass`). They never write `OCP_SYSCONFIG`; that was left to the platform
  code (K).
- **Mainline** makes the same write from ti-sysc's SGX quirk on every module enable, if
  `rev` reads 0x40000000. It also sets smart idle and smart standby in `sysc` (L).
- **The OMAP34xx's wrapper isn't accessible**, so its DT matches the SGX's own revision
  register and configures no `sysc` (L: `omap34xx.dtsi` and commit 3b72fc895a2e). The
  community PVR driver later dropped its OCP accesses on the 34xx because the reads hung.
  Our board is a 36xx, where the wrapper reads back. With the module idled, a read of
  0x5000fe00 gives a bus error (L: the same commit message). It also reads 0x00010205
  at 0x50000014 on a 36xx, our `CORE_REVISION`. So powervr_sgx reads the wrapper only
  with the ti-sysc parent awake.
- **TI's reset** (`sgxreset.c`) pulses `BIF_CTRL.INVALDC`, then waits for
  `BIF_MEM_REQ_STAT.READS` to reach 0 before going on (K). Our reset doesn't wait.

So there's no published OCP write that mainline leaves out. The open question after stage
1 (gap 18) is whether the wrapper is in the state mainline intends: the quirk applied
(`rev` = 0x40000000, b31 set), `sysc` 0x28, and what `OCP_DEBUG_STATUS` shows while reads
are outstanding (MWait, MStandby, the FIFO-full bits). powervr_sgx logs all four registers
on the 36xx during a guessed-core start (`bringup_diag()` in `pvrsgx_fw.c`).

## What this means for the stack

The kernel driver's core check (`pvrsgx_core.c`) requires `MULTIPLE_MEM_CONTEXTS`,
`MULTI_EVENT_KICK`, a 32-bit address space and at least two directory lists. The SGX530
meets none of them (D from K). An SGX530 entry is therefore more than a table row:
- **One memory context.** Each job's page directory goes into `DIR_LIST_BASE0`, with a BIF
  flush and `INVALDC` on every switch between VMs, following BRN_28889's ordering. Our
  per-requestor bank scheme ([UKERNEL.md](../../UKERNEL.md)) doesn't apply.
- **One kick.** The microkernel start that uses the SGX545's second kick needs another path
  through `EVENT_KICK` and the host-control words.
- **256 MiB of device address space.** The fixed layout in `pvrsgx_fw.h` assumes 32 bits;
  the SGX530 needs its own, smaller one.
- **The register offsets above** go into the family's `regs` table: clock status, core ID,
  revision, `PDS_INV3`, and the field shifts of `BIF_CTRL`, `SOFT_RESET` and
  `USE_CODE_BASE`.
- **The microkernel**: the open microkernel's register tables, the reset bits, the clock
  status and the PDS and USE code bases change. Whether it runs on the SGX530's USSE
  without changes is the ISA question.

## The open microkernel's SGX530 build

`ukernel/build.py sgx530` builds it from [`cores/sgx530.py`](../../../ukernel/cores/sgx530.py),
which overrides the SGX545 config with the K facts above and turns on the per-core
features below. `ukernel/test_sgx530.py` checks those paths in the emulator, and
`ukernel/golden/sgx530.sha256` is its golden. The SGX545 image is unchanged. The kernel
side of the same design is `docs/porting/single-context.md` (the kernel session's note,
pending approval).

| Feature | SGX530 | What the microkernel does |
|---|---|---|
| `MULTI_MEM_CONTEXTS` | off | The EDM, TA and 3D all use list 0. A scene's first TA kick, and a transfer, load `DIR_LIST_BASE0` from the **PD table** and pulse `INVALDC`. Before a render's or a transfer's first completion write, and on the idle path, the microkernel loads slot 0 (the firmware PD) again. No `DIR_LIST_BASE1` or bank access; the EDM's background-block pulse is dropped; overlap is refused. |
| `FIX_HW_BRN_28889` | on | After a PD switch's `INVALDC`, the microkernel reads `BIF_CTRL` back and spins (bounded) until `BIF_MEM_REQ_STAT` b0-7 read 0, before the MADD invalidate. A kernel CCB command whose cache control asks for a BIF and a data invalidate gets only the BIF one in that event; it stays queued with only its data bit, and the next event does the rest. |
| `WAIT_BOUND` | 65535 | Every status wait gives up after 65535 polls, writes its id to control block word 0x28 (+0xa0), counts in word 0x29 (+0xa4) and goes on. The manifest's `waits` maps each id to its register, bits and whether it waits for them set or clear. A bit the SGX530 lacks shows in the dump instead of freezing the EDM. |
| `HEARTBEAT` | word 0x2a | The event entry adds 1 to control block word 0x2a (+0xa8) on every event: a progress word for the host watchdog, since the SGX545's EDM task registers (0xb14/0xb20) aren't named for the SGX530. |
| `INIT_DPM_CLEAR` | none | Init doesn't zero the SGX545's DPM load-select (0x65c) and slot select (0x630). Neither is named for the SGX530 (gap 13), and stage 1 must touch only named registers. They come back when the DPM is mapped. |
| `MULTI_EVENT_KICK` | off | Nothing: the event entry tells init from a kick by `ui32InitStatus`. |

**The PD table.** The host's directory table, read-only to the GPU: 1024 words in one
4 KiB page, each a value for `DIR_LIST_BASE0`. Slot 0 is the firmware PD; a slot no VM
holds also holds the firmware PD. Its device address reaches the microkernel through a
second loader patch, `pdtable` (a `limm r14` in the event entry). The code is read-only in
every PD, so a client can't redirect it. On this core a HW render or transfer context's
word 2 (`CTX_PD`) holds a **slot**, not an address. The microkernel masks it to the table
(`& 1023`), so any value names a host-written entry.

Also from K: `CORE_ID`/`CORE_REVISION` at 0x10/0x14 (get-misc-info reports core 530),
`CLKGATESTATUS` at 0x004 with the ISP at b4 and the ISP gate field at b4-5, the TA soft
reset at b3 (the 2D bit, b1, is the host's), no `EVENT_STATUS2` DCU acknowledge, and no
wait on the SGX545's `EVENT_STATUS2` b12 after the OTPM clear. The manifest declares
feature bit 2, `PVRSGX_UKFW_SINGLE_CONTEXT` (the number is proposed), and not `SECURE`.

What the host does for it:
1. Puts the firmware PD in `DIR_LIST_BASE0` before every microkernel start (boot, recovery,
   power-up).
2. Shares the kernel code, kernel data and sync heaps into every VM's directory, at the
   firmware PD's addresses. The EDM runs on the job's PD.
3. Fills the PD table, patches `pdtable`, and writes a context's slot into its word 2.
4. Runs one VM's jobs at a time (credit 1; same-VM TA/3D overlap only under `overlap`,
   which this image refuses).
5. Kicks init with `EVENT_KICK`, after writing `ui32InitStatus` = 0, and gives
   `EVENT_KICKER` a 28-bit address.
6. Splits BRN_28889 cache control itself too, through `PROCESS_QUEUES`. That is harmless
   with the microkernel's own split.
7. Reads control block words 0x28, 0x29 and 0x2a into its dump.

Still the SGX545's values, unknown on the SGX530 (gap 13): every TA, 3D, DPM, ISP, TSP,
PBE and PDS register and table in `cores/sgx545.py`, the `0x138`/`0x140` invalidate
handshake, `EVENT_STATUS` b20 and b26 (the OTPM and MADD waits), `0x804` and `0xa74`.
The event-program registers the host programs (on the SGX545: `EVENT_PDS_ENABLE` 0xa58,
`EVENT_PDS_BASE` 0xa68, `EVENT_PDS_DATA0`/`1` 0xa6c/0xa70) and the EDM task registers
(0xb14/0xb20) aren't in either core's GPL header. The SGX545's were measured. The
SGX530's are **G**: its `USE_CODE_BASE` block below them (0xa0c to 0xa48) and its
`PDS_EXEC_BASE`, `EVENT_KICKER`, `EVENT_KICK`, `EVENT_TIMER` and `PDS_INV0`/`1` above
them sit at the SGX545's offsets, so the event-program registers likely do too. They
become **C** at stage 1, the first boot: one read of each after reset, the event PDS
address written to 0xa68 and read back, then the init kick, which counts only if
`ui32InitStatus` reaches 1 and the heartbeat moves.

**Stage 1, first attempt (2026-11-11, log `2026-11-11-1532-sgx530-stage1`):**
- 0xa68 is a backed read-write register: it reads 0 after reset and holds 0x020042c0 when
  written (C).
- The init kick didn't reach init. 500 ms later, `INIT_STATUS`, `EVENT_STATUS`,
  `BIF_INT_STAT` and `BIF_FAULT` were all 0, and `BIF_MEM_REQ_STAT` showed 2 outstanding
  reads (C).
- The event-program offsets stay G.

**Second attempt (2026-11-11, log `2026-11-11-1946-sgx530-stage1-2`):**
- The OCP wrapper reads revision 0x40000000, `sysc` 0x28 and `OCP_DEBUG_CONFIG` 0x80000000,
  as mainline sets it. `OCP_DEBUG_STATUS` stays 0x023c0707: initiator connected, MWait and
  MStandby clear (C).
- The kick turns on `CLKGATESTATUS.USE_CLKS` (b20) for the whole 500 ms (C), so the event
  reaches the USE, or the PDS in its clock domain.
- `BIF_MEM_REQ_STAT.READS` goes between 2 and 0: the reads complete (C).
- The heartbeat stays 0 (C).
- So 0xa68 holding the event program's address is likely (D). It stays G until the
  microkernel writes.

**What stage 1 runs** (microkernel.md stages 1 and 2, the first boot; the runbook is
[sgx530-stage1.md](sgx530-stage1.md)). The init kick, a
timer event and a get-misc-info touch only registers the SGX530's K header names:
`CORE_ID`, `CORE_REVISION`, `EVENT_STATUS`, `EVENT_HOST_CLEAR`, `EVENT_TIMER`, `BIF_CTRL`
and `DIR_LIST_BASE0`. `test_sgx530.py` (`stage 1`) fails if any other register shows up
on those paths. They execute 18 instruction forms, all on the SGX545's encodings:

    and  ba  idf  imae  ld.a.d  ldr  limm  mov  nop  or  phas.i  st.a.d  str  wdf
    test.and.eq  test.and.ne  test.xor.eq  test.xor.ne

Stage 1 passing (`ui32InitStatus` = 1, the heartbeat moving, get-misc-info's words
filled) is coarse evidence that these forms behave on the SGX530 as on the SGX545. It is
not a per-field test: an encoding that differs only in a field these paths don't exercise
goes unseen. The instruction-level tests (gap 10) still decide.

## Stage-1 bring-up: confirmed findings and the register-file split (through attempt 41)

The bring-up got the open microkernel's USSE code **executing** on the SGX530, then found a
register-write blocker that is still open. Three SGX530-vs-SGX545 differences were confirmed
and two fixed:

- **`USE_CODE_BASE` is `addr >> 8` (256 B units), not `>> 7` (C, attempt 24).** The fetch is
  `(field << 8) & 0x0fffffff`. Code base 15 = `kernel_code >> 8`. The driver uses a per-core
  `use_code_base_addr_shift` (7 on the SGX545, 8 on the SGX530). Fixed.
- **`phas.i` must be the first instruction of a task (C, attempt 26).** The SGX530 lacks
  `USE_UNLIMITED_PHASES`; a task that starts with other work (the marker-first diagnostics)
  faults with an image-dependent garbage fetch. The real entry has `phas.i` first and was
  never the problem. Fixed; diagnostic builds emit `phas.i` first too (lesson 26).
- **Instruction pairing: the SGX530 lacks `SGX_FEATURE_USE_NO_INSTRUCTION_PAIRING`** (K,
  sgxfeaturedefs.h; the SGX545 has it), so it schedules/pairs adjacent instructions. This
  was tested as the write blocker and **ruled out** (attempt 38: up to 8 nops and
  attempt 32's 23-instruction separation both flat). Noted for later code generation.

**The open blocker (C, attempts 31-38): the USSE executes but no register write retires.**
With the two fixes, the task runs — `ld.a.d` generates addresses and faults, an unconditional
`ba` self-loops, instruction fetch works — but no write by `limm`, an ALU `or`, `str`, or an
`ld` destination is ever visible to a later read. Reads return each register's **stable
power-on leftover**, the same across boots: r0 0x0055d000, r1 0x0722a000, r2 0x003e1000,
r3 0x08439000, r4 0x09e06000, r5 0x0c004000, r6 0x0503f000, r8 0x08779000, r16 0x002ba000,
r17 0x0fd79000, r31 0x0d04f000 (all C). `ld.a.d rN` reads register N correctly (source decode
works); the fault address follows the register named, not its value or the offset.

Ruled out as the cause: the DOUTU word-0 temp field (attempt 35), `phas.i`'s temps4
(36), the host-side init-regs setup (37; 0x810/0x814/0x818/0x800/0x4e8/0xaac don't even
latch — unimplemented), and instruction pairing (38). It is a register-file / write-back
difference, not a single misplaced field.

**The blocker is specific to the temporary file; other register files work (C, attempts
40-41).** Two task-visible writes have now landed where temporaries do not:

- **PDS-set primary attributes are task-readable and persist (C, attempt 40).** A PDS `DOUTA`
  wrote PA0 = 0x0e850000; the task read it through `ld.a.d r3, pa0`, and it held across
  recovery resets, a module unload and a reload ~19 minutes later. Attributes carry pointers
  and constants *into* the task, but they are inputs — the task cannot write them for scratch.
- **Output registers are task-writable (C, attempts 41-42).** `or o0, r5, r17` followed by
  `ld.a.d r3, o0, #0` faulted at exactly 0x0fd7d000 = r5's leftover 0x0c004000 | r17's
  0x0fd79000, so the `or` wrote `o0` and the dependent `ld` read it back — the first task-side
  register write to retire on the SGX530. Attempt 42 extended it: **all of o0 through o10 are
  writable** (each faults at 0x0fd7d000), covering the restructure's measured peak output
  pressure of 10. The output bank is usable scratch; the temporary bank is not. Why the two
  differ is still open (the EDM-task temp allocation is the suspected cause — a vendor capture of
  TI's working SGX530 EDM task setup would show it). **Caveat (G):** every probe wrote the same
  value, so the outputs are not yet shown to be *distinct* physical registers rather than aliases
  — a distinctness probe (`sgx530_odist0/9`) is pending. See
  [sgx530-attr-restructure.md](sgx530-attr-restructure.md) for the restructure this enables.

Open leads: confirm how many output registers are usable as scratch (only `o0` is tested) and
measure the microkernel's peak register pressure against that; the vendor capture, which could
make temporaries work directly and avoid the restructure. Full chronology:
[sgx530-stage1.md](sgx530-stage1.md).
