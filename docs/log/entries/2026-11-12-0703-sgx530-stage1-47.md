# SGX530 stage 1, forty-seventh attempt: the task's stores land nowhere, and it can't write pa

**Board:** our OMAP3630 test board, openHC on the SD (7.3.3, the 02:16 build), up 3 h 18 min
(the same boot as attempts 40-46), the owner-confirmed host key, the board lock held. 75 °C
before and after. No hang, no plug cycle.

**What ran:** powervr_sgx from sgx530 50367971 (CI: omap3630 43213176156 green, upstream
43213172269 green; powervr-sgx 43213168493 failed on the out-of-tree compat patch, fixed in
4c17f77c, which doesn't change the OMAP modules). modver-check: 0 differ against the board's
own module tree. Four loads, each with `allow_unisolated=1`. The images are the microkernel
session's, and every SHA-256 matches its list.
1. **`sgx530_pa0`** (it loads through PA0, so a mapped PA0 doesn't fault and an unmapped one
   faults at its value) with `stage1_sweep=1`. The variants:
   - The baseline.
   - The `pds3` layout with pds3's own DOUTA form, 0x07800406 (value from in0, control word
     ds1[0]), then DOUTU 0x07003885.
   - The baseline.
   - The one-row DOUTA writing the control block's version-word address (TA3DCTL + 0x60) to
     PA0.
   - The baseline.
2. **`sgx530_stout_o0`** with `stage1_scan=0x0fd7d000`. After the failed start the driver
   reads the whole data arena and the whole code arena (0xe000 bytes each) through its
   write-combined mapping, after an `rmb()`, and logs every word equal to the value.
3. **`sgx530_stout_r5`** with `stage1_scan=0x0c004000`.
4. **`sgx530_aluwr_pa0w`** (packaged 599a93a6…): `or pa0, r5, r17`, then a load through PA0.
   It runs last, since a write that lands changes PA0.

- In every load without a fault the USE stayed busy (0x00110000) through 500 ms: the task sat
  in its loop.
- The sweep's fault check: BIF_FAULT 0x0e800000, recovered.
- -ETIMEDOUT for each load. All five modules unloaded and the parent runtime-suspended.

**Facts (C):**
- **The forty-sixth attempt's `pds3`-layout DOUTA didn't set PA0.** It was the last program
  run before this one, and the first baseline doesn't fault at its value, 0x0e880000.
- **The one-row DOUTA does set PA0**, here as in the forty-third and forty-fourth attempts.
- **The task's stores from a temporary and from an output appear nowhere in either firmware
  arena,** though they don't fault.
- **With PA0 at a mapped address, `or pa0, r5, r17` followed by a load through PA0 doesn't
  fault:** the ALU write to pa doesn't land.

**What it suggests (G):**
- **Either the stores aren't committed, or they land outside both arenas without faulting.**
- **The task can't write the pa bank.**
- **The task now has no register a load can land in.** Temporaries don't take writes,
  outputs can't be a load's destination (the microkernel session's assembler finding), and pa
  doesn't take an ALU write. That blocks the microkernel's restructure for the SGX530.
- **The in0 DOUTA either didn't set PA0 or in0 holds a mapped address.** Together with the
  forty-sixth attempt, the `pds3` layout's DOUTA doesn't take effect.
