# SGX530 stage 1, nineteenth attempt: the DOUTU's fetch runs linearly from PDS_EXEC_BASE

**Board:** our OMAP3630 test board, openHC on the SD (7.3.3, the 02:16 build), up 30 min,
the owner-confirmed host key. 75 °C before and after. No hang, no plug cycle.

**What ran:** powervr_sgx from sgx530 f2abceb8 (CI: omap3630 43171607635, powervr-sgx
43171600487 and upstream 43171603877, all green; modver-check 0 differ),
`allow_unisolated=1 code_base_pads=1 stage1_sweep=1`, with the landing-pad image
`sgx530_bases` (f7de7b95…). Part 2 now writes 0xa74 = 0x208200 in every start (43831efb).
With the pads, code bases 0-15 all point at mapped code.

**The question:** with 0xa74 set, the entry program (MOVS → DOUTU, HALT) faults at
0x0d800000, `PDS_EXEC_BASE` + 0, requestor b2 (eighteenth attempt). What fetches there?

| # | Variant |
|---|---|
| 0 | the control: the entry program |
| 1 | the event program as its data row and a HALT, with no DOUT |
| 2 | one read-only page mapped at 0x0d800000, holding a copy of the entry program (data row, MOVS → DOUTU, HALT) |
| 3 | the same page holding the data row and a HALT |

The page was mapped for variants 2 and 3 only and unmapped before the fault check. The
recovery reset ran after each fault.

**Results:**

| # | Clock status at 100 ms | `BIF_INT_STAT` | `BIF_FAULT` |
|---|---|---|---|
| 0 | 0x00110000 | 0x4004 | 0x0d800000 |
| 1 | **0x00010000** (idle) | **0** | none |
| 2 | 0x00110000 | 0x4004 | **0x0d801000** |
| 3 | 0x00110000 | 0x4004 | **0x0d801000** |

- `PDS_PC_BASE` read 0 at every sample in every variant. `EVENT_TIMER` stayed 0: no ladder
  and no pad.
- Every fault recovered with the reset. The fault check: 0x4004 at 0x0e800000, recovered.
- -ETIMEDOUT, all five modules unloaded, the parent runtime-suspended.

**Facts (C):**
- **The fault at `PDS_EXEC_BASE` + 0 comes from the DOUTU.** With no DOUT the program ends
  cleanly: no fault, and the clocks go idle, which no variant since attempt 8 had shown.
- **With a page mapped at 0x0d800000, the fault moves to the next page, 0x0d801000, whatever
  the page holds:** a copy of the entry program or a HALT. The same requestor, b2.
- **So whatever the DOUTU starts reads linearly from `PDS_EXEC_BASE` + 0 through at least
  4 KiB,** and a HALT at the start doesn't stop it.

**What it suggests (G):**
- **The DOUTU starts a USSE task whose instruction fetch begins at 0x0d800000**, not at code
  base 15 + the entry offset. A PDS program would have stopped at V3's HALT. A USSE task
  would run through a page of zeros and fetch the next page. Requestor b2 would then be the
  USSE's code fetch.
- **The SGX530 reads the DOUTU's code address differently from the SGX545:** its code-base
  selection, or the offset field, comes out as 0 relative to some base that resolves to
  `PDS_EXEC_BASE`. Which fields of DOUTU word 0 the SGX530 uses is the next question.
- **The pads didn't fire**, so the fetch doesn't go through any of code bases 0-15 as we
  program them.

**Next:** for the microkernel session. A page at 0x0d800000 holding USSE code (a marker
write to `EVENT_TIMER`) would confirm a USSE fetch from there.
