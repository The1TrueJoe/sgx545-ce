# SGX530 stage 1, thirty-second attempt: limm preloads don't change what the load reads

**Board:** our OMAP3630 test board, openHC on the SD (7.3.3, the 02:16 build), up 8 min,
the owner-confirmed host key, the board lock held. No hang, no plug cycle.

**What ran:** powervr_sgx from sgx530 fd97aabe (the >> 8 code-base unit; modver-check 0
differ), `allow_unisolated=1` only, loaded six times.
- **The images:** the microkernel session's `cores/sgx530_ldpre_r<k>.py` for k = 0, 1, 2,
  4, 5 and 17 (its branch, dc0217a3), built with `ukernel/build.py` and packaged by
  `drm/tools/mkukfw.py`. All 12 image and package hashes match the microkernel session's
  list.
- **What each does:** `limm` r0-r22 with distinct values, rN = (N + 1) << 16 (all below
  2 MiB, all unmapped). Then `ld.a.d r3, rK, #0`, gated by a `str` to `EVENT_TIMER`. A
  fault at (M + 1) << 16 would name the register M the load read.

**Results:** every load faulted with `BIF_INT_STAT` 0x4002 (requestor b1). `EVENT_TIMER`
stayed 0 and INIT_STATUS 0 in every run.

| Probe | Preload of rK | `BIF_FAULT` | Thirty-first attempt (rK not written) |
|---|---|---|---|
| ldpre_r0 | 0x00010000 | 0x0055d000 | 0x0055d000 |
| ldpre_r1 | 0x00020000 | 0x0722a000 | 0x0722a000 |
| ldpre_r2 | 0x00030000 | 0x003e1000 | 0x003e1000 |
| ldpre_r4 | 0x00050000 | 0x09e06000 | 0x09e06000 |
| ldpre_r5 | 0x00060000 | 0x0c004000 | 0x0c004000 |
| ldpre_r17 | 0x00120000 | 0x0fd79000 | 0x0fd79000 |

- -ETIMEDOUT each time. The failed-start path held the cores in reset, then all five
  modules unloaded and the parent runtime-suspended.

**Facts (C):**
- **`limm` writes to r0-r22 don't change what `ld.a.d` reads through any of them.** Each
  fault equals that register's value without the preload (thirty-first attempt), and none
  is a preloaded (M + 1) << 16.
- **The load reads the register it names:** each register gives its own value, the same
  with and without preloads.

**What it suggests (G):**
- **On the SGX530, the SGX545 encoding of `limm` doesn't write the named register.** It
  writes another place (a different bank or field), or doesn't execute. That's also why
  the patched r17 never held the control block (attempts 24-29).

**Next:** for the microkernel session: write a register another way and load through it,
and `limm` followed by a `str` of the same register, to see where `limm`'s result goes.
