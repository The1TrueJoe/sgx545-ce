# powervr_sgx: the DDK microkernel's cleanup commands don't complete; a quiesced restart works twice

The second render context hangs on its third frame (`2026-11-03-0310-drm-second-context`).
The first thing tried is what the DDK does before freeing: the cleanup commands
(UKERNEL.md 3, type 5). The same build also quiesces the GPU before an in-place restart.
EA1, RAM boot of `7.1.8-m2drm` (cf50aae), 2026-11-03 ~02:57-03:00 UTC, DDK microkernel,
nothing flashed, no power-cycle.

## Cleanup

At teardown the driver sends RT (type 1, the HW RT dataset), then RC (2, the HW render
context), then PB (5, the PB descriptor), as the DDK's kernel module does. Each one
polls `ui32CleanupStatus` for 5 s. Four `powervr_sgx_frame -k 2 -n 10 -s 720x480`
processes in a row:

```
== process 1   10/10 frames right
== process 2    0/10 frames right
cleanup 1 of 0x32029000 did not complete
cleanup 5 of 0x32010000 did not complete
job timed out (ccb 26, consumed 23); resetting
```

- **RT cleanup:** consumed, never completed.
- **RC cleanup:** reported no timeout. It may have read a late RT completion, because all
  three share one status bit.
- **PB cleanup:** never consumed. The kernel CCB's read offset stopped on it (23 of 26:
  21 commands for process 1, then RT and RC). Process 2's first render waited behind it
  until the job timeout.

So once the first context's last render has signalled render-done, the microkernel still
treats its RT dataset and PB as busy. After ten frames the PB descriptor is left at
0x14 = 5, 0x18 = `04210005`, 0x20 = 5, 0x24 = 1 (data
`2026-11-03-0215-drm-10-frames-render.txt`), which looks like the last render's pages
still accounted as in use. That is the leading candidate for the second-context hang:
the next context runs on DPM and PB state the first never gave back. Not shown yet.

The GEN.md replay saw the same RT cleanup timeout on a srvinit-started EA3. The driver
now leaves cleanup off by default (`cleanup=1` turns it on), since a stuck PB cleanup
blocks every later command. What the open microkernel has to do instead is listed in
UKERNEL.md 3 ("What a kernel driver needs from it").

## Restart

Before restarting, the driver now does what an unload does: the deinit script, the cores
held in reset, bus mastering dropped (`restart_quiesce`). For the first time an in-place
restart worked: **two restarts in a row came back** ("microkernel started again", the
`GETMISCINFO` check passing). But each next render hung again (`ccb 3, consumed 3`), and
the third restart failed. After that the TA stayed triggered: `EVENT_STATUS2` 0x480,
`BIF_INT_STAT` 0xd0004, `BIF_FAULT` 0x10000040, the PB base. Even an unload and reload
(with `cleanup=0`) gave 0/10 in the first process. So a module reload does not always
recover. The quiesce is kept; it is not yet reliable.

A plain reboot brought the box back to its normal boot (7.1.8, pvrsrvkm bound).
