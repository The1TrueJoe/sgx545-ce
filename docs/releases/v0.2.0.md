The second release of the open graphics stack for the PowerVR SGX545 in Intel's Cedarview
Atoms (N2600, N2800, D2500, D2550, D2700) and the Intel Atom CE5300. It adds a 32-bit Mesa
package for 32-bit programs and a new kernel interface, and fixes games that came out
wrong in 0.1.x.

**Upgrade the kernel, the firmware and Mesa together, then restart.** The interface between
the kernel driver and Mesa changed, so the 0.2.0 Mesa doesn't work with a 0.1.x kernel, and
the other way around. See "Upgrading" below.

## What's new

- **32-bit Mesa, `mesa-sgx:i386`.** 32-bit programs, such as Counter-Strike 1.6, older Steam
  games and 32-bit Wine, can use the GPU now. Before, they fell back to Debian's software
  renderer (`llvmpipe`). It installs beside the 64-bit package. docs/INSTALL.md, "32-bit
  games".
- **A new kernel interface (uAPI 1.0).** Mesa now checks the kernel's interface version. Against an older kernel,
  it leaves the GPU alone instead of misbehaving, so programs fall back to `llvmpipe` until
  you restart into the new kernel.
- **Desktop speed.** Three changes target the slow desktop on Cedarview. None of them has
  been measured on a Cedarview machine yet.
  - The shader compiler keeps the `if`s of X's drawing programs (glamor) as branches. In
    0.1.x it flattened them, so each pixel ran 105 to 210 instructions instead of 0 to 5.
  - The kernel flushes only the part of a shared buffer a job touches from the CPU caches,
    not the whole screen buffer (2.4 MB at 1024x600) before and after every X job.
  - Mesa reuses freed GPU buffers instead of allocating new ones for each of X's
    temporary images.
- **Games and GL 2.1:**
  - Multitexturing as GL1 game renderers draw lightmaps: a new test of it passes on a
    CE5300 board.
  - QuakeSpasm's models and particles, which were missing, and flat shading of vertex
    colors.
  - GLSL flat varyings, user clip planes, 3D textures, and sampling depth textures with
    shadow comparison.
  - Integer division in shaders.
- **From the OpenGL 3 work** (the driver still reports OpenGL 2.1): multiple render
  targets, instanced drawing, primitive restart, 4x MSAA, depth and stencil textures as
  render targets, and `gl_FragDepth`. Integer varyings and uniform buffers are in too,
  but off by default (`SGX_DEBUG=glsl130`, `SGX_DEBUG=ubo`).
- **Fewer stalls.** A texture that a game updates while the GPU still reads it, such as a
  lightmap with dynamic lights, gets a spare copy, up to 1 MiB per texture. Before, the
  program waited for the GPU on each update.
- **A GPU reset every 65,536 renders, fixed.** The microkernel's completion counters were
  16 bits wide, so one render in 65,536 was never seen to finish, and the GPU was reset.
- **Kernel driver.** Fixes from a full review: submission and reset locking, unbinding with programs still open, memory
  lifetimes, and the gma500 handover.
  - Runtime power management is per job now, so the GPU can power down while programs keep
    a context open. 0.1.x kept it awake for them.
  - `fdinfo` reports each program's GPU time and memory, which tools such as `nvtop` and
    `gputop` read.
- **Firmware.** The microkernel is now licensed MIT OR Apache-2.0.
- **"heap 14 has no room".** 0.1.x printed this line for every texture once the texture
  heap was full, as in SuperTuxKart. The allocation then succeeded from the general heap,
  so nothing was wrong. Mesa now says so once per program.
- **Source cleanup.** Material derived from the vendor's closed drivers is gone from the
  tree: vendor-compiled shaders, listings of vendor programs, tools that read or drove the
  closed stack, and a pixel-event program and blend tables that had been copied from it,
  now replaced by our own (same rendering; dEQP and piglit identical). The firmware is
  built only with the clean-room assembler. Mesa no longer builds anything against the
  vendor's GPL kernel headers.
- **DKMS:** `drm/dkms/mkdkms.sh --cedarview` builds the Cedarview binding, and the build
  works with DKMS 3.4 (Arch).
- **Packaging.**
  - apt keeps the three packages in step. The 0.2.0 Mesa and firmware refuse the older
    kernels, so upgrading them upgrades the kernel too.
  - Test builds from GitHub Actions now number themselves below the next release.

## Upgrading

**From 0.1.0 or 0.1.1, with the apt repository:**

```bash
sudo apt update && sudo apt upgrade
```

Restart right away. Until then, the old kernel runs with the new Mesa, and programs use
`llvmpipe`. For 32-bit programs, add the package afterwards:

```bash
sudo dpkg --add-architecture i386 && sudo apt update && sudo apt install mesa-sgx:i386
```

**From packages downloaded from GitHub Actions.** Several testers installed test builds
from GitHub Actions. Their version numbers sort above this release, so `apt upgrade` keeps
them. That caused two problems:
- After installing a newer test-build Mesa with a 0.1.x kernel, every program used
  `llvmpipe`.
- After installing the 32-bit test-build Mesa, the 0.1.x Mesa would no longer install
  (`not co-installable with mesa-sgx which has multiple installed instances`).

Check what you have:

```bash
dpkg -l 'linux-image-7.3.3-sgx' sgx545-firmware 'mesa-sgx*' | grep '^ii'
```

If a version looks like `26.2.5+sgx20261112.694a777`, `7.3.3-sgx1` or `0~git…`, install the
release over it. This needs the apt repository from docs/INSTALL.md. Leave out
`mesa-sgx:i386=…` if you don't have the 32-bit package:

```bash
sudo apt update && sudo apt install --allow-downgrades linux-image-7.3.3-sgx=7.3.3-sgx0.2.0 sgx545-firmware=0.2.0 mesa-sgx:amd64=26.2.5+sgx0.2.0 mesa-sgx:i386=26.2.5+sgx0.2.0
```

Then restart. From now on, test builds number themselves below the next release, so this
is needed only once.

**Checking it worked:** `glxinfo -B` should name the **PowerVR SGX545**. If it says
`llvmpipe`, run a GL program from a terminal. A line such as
`sgx: powervr_sgx uAPI 0.x, this Mesa speaks 1.x` means the running kernel is older
than Mesa. Restart, and check that the boot menu picked `7.3.3-sgx`.

**CE5300 (DKMS):** rebuild the driver from this release's source as in docs/INSTALL.md,
section 2.

## Tested

On a CE5300 board with this release's kernel and microkernel and the cleaned Mesa
(2026-11-13):

- **dEQP-GLES2 sample** (all of `fragment_ops`, every 20th case of the rest; 2,685 cases):
  2,657 pass, 3 expected failures, 25 skipped, no new failures.
- **piglit**, every blend and fragment test of the gpu profile (387): the same results
  as before the pixel-event program and the blend tables were replaced.

## Known issues

- **No OpenGL 3.x or OpenGL ES 3.0 yet.** The driver offers OpenGL 2.1 and OpenGL ES 2.0.
  Renderers that need GL 3.x don't start, and some fall back to GLES2.
- **Minecraft 1.15 and newer** render into a depth texture, which 0.1.x refused
  (`GL_FRAMEBUFFER_UNSUPPORTED`). This release renders into depth textures (from the
  OpenGL 3 work), but those versions haven't been tried with it yet.
- **ioquake3's `opengl1` renderer** can leave a map's world undrawn on a CE5300 board;
  this is being investigated.
- **sRGB textures** are decoded in the shader. Filtering across mipmap levels and sRGB
  border colors aren't right yet.
- **Cedarview desktop speed and flicker.** The desktop is still slower than it should
  be. On some machines, a band of the screen shows shifted sideways for one frame. The
  flicker looks like a display-side problem (gma500) rather than the GPU's, and it is
  being investigated.
- **The same as 0.1.x:**
  - `perf record` with precise events (PEBS) can corrupt memory on these Atoms; use
    `perf record -e cpu-clock`.
  - Some Cedarview panels stay dark with `gma500`, with Debian's kernel too.
  - CE5300 boards have no kernel package (DKMS only).
  - Speed work on the GPU itself is still ahead.

## Installing

New installs: docs/INSTALL.md. Check the downloads with `sha256sum -c SHA256SUMS`.

Please report problems on the issue tracker, with your computer model and the output of
`sudo dmesg | grep -i -E 'powervr|gma500|drm'` and `glxinfo -B`.
