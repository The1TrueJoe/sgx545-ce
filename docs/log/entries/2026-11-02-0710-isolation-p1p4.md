# Isolation premises P1-P4 on hardware: three of the four fail

`docs/UAPI.md` section 7.2 named four hardware premises the DRM uAPI's isolation
design rests on, none of them established. They are established now, on the EA3
(core rev 1.0.14), and **P1, P2 and P3 fail**: an ordinary render-node client's
USSE task can read the hardware registers, read kernel memory, and run from the
kernel code base. P4 (the microkernel's secondary-attribute state leaking into a
client task) did not reproduce, but P2 exposes the same secret it protected.

This decides D9 (UAPI.md section 7.2, "what to do if P1, P2 or P3 fails") in the
affirmative: the design in sections 7.1-7.4 does not deliver isolation on its own.
Written up here before any M2 kernel code exists, which was the point.

## How it was tested

`tools/iso/iso.c` is an ordinary services client (no DDK code; the same frame
path as `tools/gen/sgxgen.c`). It draws one triangle whose fragment and vertex
programs, their placement in the shader heaps and their DOUTU word 0 come from a
spec file, so a client controls exactly what a client controls: its own USSE and
PDS code and its own GPU VAs. It reads named `EUR_CR_*` registers from the host
(BAR0 of `01:02.0`) just before and after the frame, and dumps client buffers
after. The triangle's pixels are the fragment's `o0`, which the PBE stores
unchanged, so a value a shader moves to `o0` is read straight out of the back
buffer (the `tools/isa/hwt` trick). `tools/iso/iso.py` runs a suite on the box
under `flock /tmp/gpu.lock`, one process per test, 15 s watchdog, and stops the
batch at the first lockup or fault, because the wedge is the result.

Suites `tools/iso/suite_p1.py` .. `suite_p4.py`, `suite_p3_wedge.py`. The GPU was
brought up first with the blob `sgxinit` (the services/microkernel model the
premises are about). Raw output: `docs/log/data/2026-11-02-0710-iso-*.txt`.

## P1 — a client USSE task reads `EUR_CR_*` registers. **Fails (reads).**

`ldr` of a register into a temporary, from an ordinary fragment task:

| test | register | host read (before/after) | value the shader got (pixel) |
|---|---|---|---|
| `p1_fs_ldr_core_id` | `CORE_ID` 0x1c | 0x01150000 | **0x01150000** |
| `p1_fs_ldr_core_rev` | `CORE_REVISION` 0x20 | 0x0001000e | **0x0001000e** |
| `p1_fs_ldr_timer` | `TIMER` 0x144 | 0xa5a47b29 / 0xa5f1b9f3 | **0xa5f12219** (and every one of the 32 sampled pixels differed: `uniform=0`) |

The shader read the true register contents. The `TIMER` case is the sharpest: the
value lies between the host's before and after reads, and it differs per pixel,
so each pixel's task executed the `ldr` at its own time. Register reads from a
client shader are real and unprivileged. A shader that can read `BIF_FAULT`,
`TIMER` and the like has side channels; one that can also *write*
`BIF_DIR_LIST_BASE0` could repoint all translation and defeat any page-directory
design (see below).

The one write tried, `str` of a test value to the unused `USE_CODE_BASE_14`
(0xa44), left the register unchanged in the host's reads and in the shader's own
read-back, so that write had no effect (the register may ignore writes, or the
value did not fit its field). **A write to an *effective* register was not tried**
(`BIF_DIR_LIST_BASE0` would redirect translation; writing it live risks
corrupting or wedging the box). Since reads already fail P1, the design
conclusion holds regardless; but the register-write capability is the most
dangerous open question and must be assumed possible until shown otherwise.

## P2 — a client task reaches kernel memory through its page directory. **Fails.**

`ld` from a kernel VA into a temporary, from a fragment task (and a vertex task):

| test | kernel VA | what came back |
|---|---|---|
| `p2_ld_hostctl` | 0x32003100 host control block | its live fields (power/status words, e.g. +0x14 = 0x0a, +0x18 = 0x00061a80) |
| `p2_ld_ta3dctl` | 0x32003000 TA3D control block | word 0x01 host-ctl 0x32003100, 0x02 CCB-ctl 0x32002000, **0x16 kernel-CCB base 0x32000000, 0x17 page-directory physical address** |
| `p2_ld_kccb` | 0x32000000 kernel CCB | its contents (misc-info addr 0x32003160, counters) |
| `p2_ld_ukcode` | 0x30000000 microkernel code | microkernel instruction words (`fc22b080` limm, `f9200000` wdf, ...) |
| `p2_vs_ld_ta3dctl` | 0x32003000, from a vertex task | the same as the fragment read |

Both the TA (vertex) and 3D (pixel) data masters translate through a directory
that maps the kernel heaps, so a client reads the host control block, the TA3D
control block — including the page-directory physical address and the CCB
addresses — and the microkernel's own code. The page-directory physical address
is exactly the secret P4 was about; a client reads it directly here.

`p2_wr_tasig` stored a sentinel into the kernel region (0x3200a420, the TA
signature buffer) and **wedged the GPU**: `SGXOSTimer() detected SGX lockup`,
`HWRecoveryResetSGX: SGX Hardware Recovery triggered`. Whether the write landed
or faulted, a client write aimed at kernel memory takes the GPU down (and the
reads already show kernel memory is in reach).

`p2_alloc_kdata` also shows the services layer let an ordinary client
**allocate in the kernel-data heap** (returned 0x32042000), so the heap is not
even reserved against clients in this stack.

The note in GEN.md "Layout" — that the microkernel reads the previous client's
structures — and section 7.1's reliance on the per-VM page directory as "the real
boundary" are both contradicted by the DDK's mapping: kernel memory is in every
client's translation. A new kernel driver that owns the page directory can
*stop* mapping the kernel heaps and code into client PDs (this is within our
control, unlike P1), which is the fix.

## P3 — a client PDS selects code base 15 (the kernel code heap). **Fails.**

`p3_base15` set the pixel task's DOUTU word 0 to name code base 15 (the kernel
code heap, `USE_CODE_BASE_15`) with the program's own offset. The task did not
produce its color (pixel 0, not the green uniform) and the **GPU wedged**:
`SGX lockup`, `HWRecoveryResetSGX`. So a client PDS program is not stopped from
pointing the USSE at the kernel code base; here it was a denial of service, and a
chosen offset into base 15 runs real microkernel code. The kernel driver must not
leave base 15 (or the kernel code heap) reachable from client PDS/DOUTU.

The b27 flag in DOUTU word 0 (PDS.md G4), tested on an ordinary base-0 task
(`p3_b27_ldr_core_id`, `p3_b27_plain`), changed nothing: the register read still
returned `CORE_ID` and the frame still rendered. b27 grants a task nothing extra
that these tests can see; P1's register access does not depend on it.

## P4 — the microkernel's secondary attributes in a client task. **Did not reproduce.**

`p4_sa11_42`, `p4_sa43_63` and the vertex `p4_vs_sa10_41` read `sa11`..`sa63`
(the registers the fragment/vertex secondary DMA does not overwrite) into client
memory. They hold the task's own secondary-update results (`sa9`/`sa10` were the
DMA'd uniform, 0xff00ff00 and 0x3c000000), per-task coefficient/iterator data
that differs per pixel (`uniform=0`), and a prior same-client draw's clear color
(0xcc336699 recurs) — but **not** the microkernel's named pointers: no TA3D-ctl
address, no page-directory physical address, no CCB addresses. The secondary
attributes look reloaded per task, so the microkernel's live `sa` state (UKERNEL.md
section 1) did not survive into a client task here.

**Correction (later the same night).** An earlier version of this entry took the
microkernel bring-up as showing that a USSE task cannot write its own secondary
attributes. That was withdrawn in `docs/log/entries/2026-11-02-0630-ukernel-ea3-bringup.md`:
the DDK microkernel writes `sa` in its PDS-DMA-entered context, and the stall was a
write in the bare-`DOUTU` context before any DMA. So the write-then-observe half of P4
is **untested**. Since f672198 the open microkernel keeps its control-block base in a
temporary and reads no `sa`, so P4 holds for our microkernel by construction; for the
DDK microkernel it rests on the per-task reload above.

So the specific P4 read did not work — but it protects the page-directory physical
address, which **P2 hands to a client anyway**. The cross-client case (one
client's leftovers visible to another, G6) needs two simultaneous clients and was
not tested. The clear-color recurrence is a within-client cross-draw leak, minor.

## What this means for the uAPI (D9)

P1, P2 and P3 each break section 7.1. The kernel driver can close P2 and P3 by
owning the page directory and never mapping the kernel heaps, kernel code or base
15 into a client PD — these are the driver's to control. **P1 it cannot:** `ldr`/
`str` reach the register file from any USSE task regardless of the page directory,
so a client shader can read registers, and possibly write an effective one
(untested, dangerous). Closing P1 needs either kernel-side validation of every
client USSE and PDS program (D9 option 1, as `vc4_validate_shaders.c` does for a
GPU with no MMU — costly, Mesa generates PDS per draw, and it needs the full ISA
in the kernel), or a hardware privilege mode that blocks register access from
client tasks (not found in the registers or docs; a gap). One client at a time
with a scrub (option 3) is not useful on a desktop. This is the decision that
"could end the upstream plan as written", and it now rests on hardware, not doubt.

Recommended, for Joseph: treat shader validation as required for M2, and before
committing to it, test the one thing left open — whether a client `str` to
`BIF_DIR_LIST_BASE0` is effective (it needs a careful rig: set the EDM/3D/TA bank
to a client-built page directory, or expect a wedge). If register writes are
effective, validation must cover every `ldr`/`str`, i.e. forbid them in client
code outright.

## Box

EA3, handed over by open-ukernel on a clean cold boot, blob `sgxinit` run once
(SGX revision 1.0.14). Two deliberate wedges (`p2_wr_tasig`, `p3_base15`), each
recovered by the driver's HW recovery; the GPU rendered correctly again after the
first. Power-cycled through the Bench plug at the end, so the next session gets a
clean cold boot. `/root/srvinit`, `S00kexec` and the switch setting untouched.
