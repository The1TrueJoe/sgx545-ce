# SGX530 stage 1, thirty-fourth attempt: an ALU result doesn't reach the register either

**Board:** our OMAP3630 test board, openHC on the SD (7.3.3, the 02:16 build), up 13 min,
the owner-confirmed host key, the board lock held. 77 °C before. No hang, no plug cycle.

**What ran:** powervr_sgx from sgx530 fd97aabe (the >> 8 code-base unit; modver-check 0
differ), `allow_unisolated=1` only.
- **The image:** the microkernel session's `cores/sgx530_aluwr.py` (its branch, 80acaf00),
  built with `ukernel/build.py` and packaged by `drm/tools/mkukfw.py`. 72 bytes, sha256
  81dd5785…, crc 0x1dd7e9fa, packaged 18ce50ba…, both matching the microkernel session's.
- **What it does:** `phas.i`; `or r5, r5, r17`; `ld.a.d r3, r5, #0`. There's no `limm`.
  With the leftovers (attempt 31), the `or` would give 0x0c004000 | 0x0fd79000 =
  0x0fd7d000.

**Results:**
- The event program sat at 0x01400050 (read back).
- `BIF_INT_STAT` 0x4002 (requestor b1), `BIF_FAULT` **0x0c004000**, from 100 ms to 500 ms.
- `EVENT_TIMER` 0, INIT_STATUS 0.
- -ETIMEDOUT. The failed-start path held the cores in reset, then all five modules unloaded
  and the parent runtime-suspended.

**Facts (C):**
- **The load through r5 faults at r5's leftover (0x0c004000), not at 0x0fd7d000.** The
  `or`'s result didn't reach the r5 the load reads.
- **With the thirty-second attempt (`limm`) and this one, no register write we've tried
  reaches the register a following load reads.**

**What it suggests (G):**
- **The SGX530 takes the SGX545 encoding's destination operand somewhere else:** another
  register bank, or another numbering, than the source operand `ld.a.d` reads as rN.
  `limm` failing to write was one case of this.
- **The thirty-third attempt's `str` result can't be read either way** until a write is
  shown to land.

**Next:** for the microkernel session: where a write's destination lands, by bank or field.
