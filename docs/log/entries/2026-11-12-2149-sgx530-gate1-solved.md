# SGX530 gate 1 SOLVED: the temporary write retires under the §9 vendor launch

**Board:** our OMAP3630 test board, up 13 h 05 min (the same boot as attempts 40-47, T1, T2,
§9 and the gate-1 probes), the owner-reread pinned ED25519 host key, the board lock held
21:49:26-21:50:01 UTC. 77 °C. No hang, no plug cycle.

**What ran:** powervr_sgx from claude/sgx530-gap19-tests (omap3630 CI 43309942028, green), one
load, `allow_unisolated=1 stage1_vlaunch=1`. Image `sgx530_xorr5` (matching the microkernel
session's hashes, img e6480943…, pkg 6349db08…): `aluwr` with the `or` replaced by an **`xor`**
— `xor r5, r5, r17` then `ld.a.d r3, r5`. Unlike `or`, `xor` is non-identity even when r17's
bits are a subset of r5's, so it distinguishes a retired write from an untouched register.

**Result: `BIF_FAULT` 0x00a90000.**

- The predicted value if the write retires is `r5 ^ r17` = 0x0fa93000 ^ 0x0f003000 =
  **0x00a90000**. If it did not retire, r5 would be untouched (0x0fa93000).
- The fault is **0x00a90000**. The `xor` changed r5.

**Facts (C):**
- **The temporary write retires under the §9 vendor launch.** `sgx530_xorr5` faults at exactly
  the XOR result, so `xor r5, r5, r17` wrote r5 and the dependent `ld` read it back.
- **r17 (ctlblk) = 0x0f003000** (kernel_data.base 0x0f000000 + TA3DCTL offset 0x3000), as in
  the gate-1 probes.

**Why the earlier probes were inconclusive (resolved):**
- `aluwr` (`or`) and `ldr5_ctl` (`nop`) both gave 0x0fa93000 because r17 = 0x0f003000 is a
  subset of r5's leftover 0x0fa93000, so `r5 | r17 = r5` — the OR couldn't change r5 whether or
  not it retired (logs 2026-11-12-2131, 2026-11-12-2143). `xor` has no such degeneracy.

**What this settles:**
- **Both SGX530 write-retire gates now pass under §9:** gate 2 (the task launches and runs)
  and gate 1 (a temporary write retires). The write-retire blocker that held stage 1 (attempts
  31-47: "no register write retires") is **solved** by the vendor launch — the 8-word data
  interleave, the DOUTU words (0x0020000f, 0x04000000, 1), `0xa6c` = 3, `0xa70` = 0x00013d01,
  and the kernel data arena mapped with EDMPROTECT.
- **The open microkernel can run on the SGX530** with these launch words: the EDM-mediated path
  is viable, not only host-kick.

**Next:** the microkernel session brings up the full microkernel on the 530 with the §9 launch
words; the launch words fold into the SGX530's real init (not only `stage1_vlaunch`). The
bisect (which word grants the write context — word 2 is inert; word 1 and word-0 bit 21 remain)
is now optimization, not a blocker, run as `xorr5` with each word reverted via the `vl_*`
params.
