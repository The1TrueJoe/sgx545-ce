# The shader compiler: upstream readiness (audit, 2026-11-01)

This checks `mesa/src/sgx/compiler` against AGENTS.md §3.5-§3.7: licensing,
clean-room provenance and Mesa's expectations. It covers what the compiler
contains today (`um-re` 96d60cd plus the compiler commits after it). It also says
what has to change before the code is offered to Mesa.

The compiler is 8 files, 8.8k lines: `sgx_nir.c` (NIR lowering),
`sgx_compile.c` (instruction selection, register allocation, encoding),
`sgx_usp.c` (the DDK's USP container; moved to `tools/usc` since, see §3), `usse.c`/`usse.h` (the encoder),
the generated `usse_forms.h`, plus `sgx_compiler.h` and `sgx_priv.h`. The tools
that test it (`tools/usc`, `tools/isa`) stay in this repo and are not part of
what goes to Mesa.

## 1. Licensing (§3.5): clean

- **Includes:** only Mesa (`nir*.h`, `util/*`, `compiler/*`) and the compiler's
  own headers. Nothing from `kernel/src`, `libpvr` or `libpvr/abi`. I checked
  every `#include` in the eight files.
- **No GPL material:** the compiler knows nothing about services, bridge
  ioctls or kernel structs. Its inputs are NIR and its outputs are instruction
  words, a constant map and an iteration list. No struct layout, table or text
  from `kernel/src` appears in it.
- **No proprietary binaries or decompiler output** are in `mesa/`. The DDK
  corpus USPs (`tools/isa/corpus`, compiler output from the DDK) and the hwt
  logs stay in `tools/` and must not go to Mesa.
- **Headers:** every file carries `Copyright © 2026 Joseph Telaak` and
  `SPDX-License-Identifier: MIT` (Joseph's choice, 2026-11-01).
  `gen_forms.py` writes them into `usse_forms.h`.

## 2. Provenance (§3.6)

The compiler depends on three kinds of knowledge.

### 2.1 Instruction encodings: `usse_forms.h`

**Since 2026-11-03** the compiler encodes through the isaspec encoder generated
from `mesa/src/sgx/isa/sgx.xml` (written from docs/ISA.md alone), via
`sgx_forms.c`. `usse_forms.h`, `usse.c`, `usse.h` and `gen_forms.py` are
deleted; the output was byte-identical on the whole corpus before they went.
The rest of this section describes the encoder as audited.

`usse_forms.h` is generated by `tools/usc/gen_forms.py` from the form tables in
`tools/isa/hw.py` + `hw_*.py`, which is mechanical and complete (all 174 forms).
`usse.c` is a C port of `hw.encode()` over those tables.

How the tables were established (ISA.md "How each fact was established"):

- The forms were **written while reading libusc's USE assembler (useasm.c) in
  Ghidra decompiles**. Each form's `src=` names the libusc function it was
  read from. This is static analysis of a proprietary binary.
- Every form was then **checked black-box**. `oracle.py` runs libusc's own
  encoder in an i386 emulator, and `check_<area>.py` sweeps every field value
  of every form through it. `hw.py` must decode each result with no
  unexplained bit and re-encode it from text. 5045 instruction words logged
  from real DDK compiles round-trip.
- **Hardware experiments** (`hwt_*`, 11 suites, 76 tests on a CE5300 board) fixed the
  *meaning* of fields the encoder alone can't give: F16 numbering, rounding,
  C10, setfc, repeats, swizzles, and so on.

Under §3.6, a fact found by static analysis must carry its provenance (ISA.md
does: the **encoder** tag) and be confirmed by experiment before code depends
on it. For the forms the compiler uses, that confirmation exists. Every word
the compiler emits in the A/B suites ran on the GPU and gave the DDK's pixels:
c1 (106 shaders, F32 and F16), tests/f16, sys, ix, gl4es's Minecraft shaders,
and mesa-gallium's driver A/B set. A wrong field value would have shown up as
a wrong pixel or a GPU fault.

**Gaps:** these forms can be emitted, but none of the A/B suites runs them yet.

- `fcos`: hwt_p3 confirms its value on hardware. No A/B shader uses cos yet.
- `fadm`, `fmsa`: hwt_p1/p5 confirm them. Selected only for some fmad shapes.
- `fdsx`, `fdsy` (derivatives): ours match the DDK's words for corpus c3
  dsx/dsy. piglit on a CE5300 board showed that their sources must run on helper
  instances (skipinv clear) and that the destination must not share the
  source's register. Retest after the register fix; they also need an hwt
  test before upstream.
- `depthf` (gl_FragDepth): the driver writes it at the feedback point; what
  it does with our depth is a guess until a hardware test.
- `pck.f32.f16`: the conversion is hwt_p4. No A/B shader takes this path.

### 2.2 Conventions and behaviour: the DDK as an oracle

What to emit for each GLSL feature (iteration layout, discard, sample
blocks, C10 for lowp, F16 for mediump, rounding choices) comes from the DDK
used as a **behavioural oracle**. That covers the USPs its compiler produces for
one-feature shaders (`gen*.py` corpora), and pixel A/B on the same draws. §3.6
allows this: the DDK is an oracle, and nothing is translated from it.

Comments in the compiler name libusc and the DDK as the behaviour being
matched ("as libusc fuses a mediump a*b+c"), with ISA.md references. One
comment cited a libusc function address (`FUN_00029ff0`). It's removed, and no
`FUN_` address is left in `mesa/`. For upstream, these comments should cite the
docs/ section and the hardware test that fixed the behaviour, not libusc.
Reviewers will read "as libusc does" as "copied from libusc", even though it
means "matched against it".

### 2.3 Hardware semantics

F16 numbering, rounding, C10 range and rounding, setfc state, repeat
stepping, the internal registers' loss on a deschedule (found by the A/B
runs, now `nosched` as libusc marks it): all from `hwt_*` and A/B runs, logged
in `docs/log/`.

### 2.4 What to do before upstream (provenance)

The encodings are hardware-confirmed for everything the compiler emits, but
the *tables* were typed while reading decompiled code. The defensible path is
to write the Mesa-side ISA description again **from docs/ISA.md only**, not
from `hw.py`, and validate it black-box:

1. Describe the 42 forms the compiler uses (not all 174) from ISA.md's field
   tables.
2. Validate without looking at decompiles: round-trip the DDK corpus words,
   use the encoder oracle as an A/B (an oracle, allowed), and run the
   A/B and hwt suites.
3. Keep `hw.py`, the Ghidra function names and the "read from the decompile"
   notes in `tools/` and `docs/`, where the provenance belongs. None of it goes
   to Mesa.
4. Close the gaps in 2.1 with hwt tests (derivatives first).

## 3. DDK-compatibility code that doesn't go upstream

Some of the compiler exists so the DDK's GLES driver can run our programs,
which is what makes the A/B harness possible. An upstream driver doesn't need it:

- **`sgx_usp.c`, the USP container. Done (2026-11-01):** the compiler now
  publishes the program's structure in `struct sgx_shader` (flat code, blocks:
  code runs, labels, branches, the discard feedback point, samples; dependent
  samples with their smp template; SA slots). `tools/usc/sgx_usp.c` builds the
  USP from that for sgxc, and the gallium driver reads the fields instead of
  parsing a USP (`SGX_DUMP_USP` became `SGX_DUMP_CODE`). Every corpus
  and test set compiles to byte-identical USPs and code before and after
  (6841 files, F32 and F16).
- **glslcompiler's numbering.** This covers the pins, the varying-to-set
  allocation in `sgx_assign_varyings`, sampler numbering by first use, the
  constant numbers measured by `calib.py`, and the USP label numbers 3/4/5.
  All of it matches glslcompiler so that our USPs drop into the DDK's driver.
  Upstream, the driver decides layouts. **The pins are done (2026-11-01):** the
  compiler takes a `struct sgx_layout` (place a name, first free number) from
  its caller; the name tables and glslcompiler's numbers live in sgxc, and the
  gallium driver answers with st's `driver_location` for attributes. Still in
  the compiler: the varying-set allocation and first-use sampler order (the
  compiler's defaults, which match glslcompiler), and the n_pa count of the
  DDK driver's placeholder colour iteration.
- **The list A dummy colour iteration** is USP-only (written by
  `tools/usc/sgx_usp.c`).
- **Ours, and staying:** the driver-only constant kinds 0x10 (F16 of a C10
  value) and 0x11 (literals) are our own interface, not the DDK's. Express them
  in `sgx_const_map`; the list C records exist only for the harness.

## 4. ISA definitions as XML (evaluated)

The candidate is **Mesa's `isaspec`** (`src/compiler/isaspec`, used by
freedreno's ir3 and etnaviv), not genxml or csbgen. isaspec describes
instruction encodings and generates the encoder and the decoder, so Mesa also
gets a disassembler. genxml and csbgen describe state packets, the right tool
for the driver's PDS and control-stream words (STATE.md, PDS.md), not for
USSE.

Size and fit:

- 174 forms (42 used), 1611 field instances, 520 operand slots.
- **60 fields are split** across non-adjacent bits: the sop2/sop3 colour and
  alpha selects, sopwm's write mask (`h12,h13,h14,h11`), fmad16's swizzles
  (`h13,h18`), the movc and ima8 condition bits. isaspec fields are contiguous
  ranges. A split field becomes one `<field>` per range, an `<encode><map>`
  expression for each part, and a `<derived>` field that reassembles the value
  for display. That's mechanical.
- **Operands** (bank + extension bit + number, the format bit that makes
  numbers 6-bit under format control, F16 halves) map to isaspec types per
  slot kind.
- **Modal state:** format control (`setfc`) changes how numbers are read. The
  encoder can take it as a parameter, as `usse_encode(…, fc, …)` does now. The
  decoder needs it as decode state; `dis.py` tracks it per block. How isaspec's
  decoder takes such a hint needs a look before committing to it.

Recommendation (all four done, see §2.1): do it, in this order:

1. Write the 42 forms in isaspec XML from docs/ISA.md (§2.4).
2. Generate the encoder at build time (meson `custom_target`). No generated
   file is committed, which is Mesa's convention.
3. Keep the backend's `usse_inst`/`usse_encode` API, so `sgx_compile.c`
   doesn't change.
4. Check that the generated encoder and today's tables give the same words on
   every word the compiler emits in the suites, and on the corpus.

## 5. Other Mesa expectations (§3.7)

Status: docs/UPSTREAM-READINESS.md, "Compiler" (C1-C9), tracks these now.

- **Style:** C11, Mesa formatting, no global state (`hw_const`'s static table
  should become a const table).
- **Debug options:** `opts.verbose`, `SGX_PRINT_PRE_I2F` and sgxc's `-v`
  belong in the driver's debug-option table (`SGX_DEBUG=nir,...`), not in
  environment variables read by the compiler.
- **Tests in Mesa:** an encoder round-trip unit test (meson `test`) over
  programs the compiler itself emits (not DDK corpus words), plus dEQP-GLES2
  through the driver. The DDK corpus and libusc oracle stay here.
- **Placement and naming:** `src/gallium/drivers/sgx` with the compiler in
  it, or `src/imagination/sgx/...`. This is AGENTS.md §7.2, for the Rogue
  maintainers. The compiler has no dependency on that choice.
