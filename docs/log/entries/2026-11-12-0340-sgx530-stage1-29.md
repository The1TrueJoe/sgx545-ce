# SGX530 stage 1, twenty-ninth attempt: the load's base register is read, but not as the SGX545 writes it

**Correction (2026-11-12, after the thirtieth attempt).** The reading below, that r5's value
came through with bits 24-25 lost, is wrong. In the thirtieth attempt seven probes loaded
r5 with seven different single-bit `limm` values. All seven faulted at the same 0x0c004000.
So the fault doesn't follow r5's value: it follows **which register the load names** (r17
→ 0x0fd79000, r5 → 0x0c004000). The match with 0x0f004000's low bits was a coincidence. The
facts table stands. The "base register does" fact and the `limm` suggestion don't.

**Board:** our OMAP3630 test board, openHC on the SD (7.3.3, the 02:16 build), up 40 min,
the owner-confirmed host key, the board lock held for both loads. 77 °C before, 75 °C after.
No hang, no plug cycle.

**What ran:** powervr_sgx from sgx530 fd97aabe (the >> 8 code-base unit; modver-check 0
differ), `allow_unisolated=1` only, loaded twice. The microkernel session's probes are from
its branch, e345a3b1, built with `ukernel/build.py` and packaged by `drm/tools/mkukfw.py`.
All four hashes match the microkernel session's. Each probe isolates one `ld.a.d`, gated
by a `str` to `EVENT_TIMER` after it.
- **ld0** (`cores/sgx530_usse_ld0.py`): `ld.a.d r3, r17, #0`, with r17 = the patched
  control block (0x0f003000 by the driver's layout). Image 72 bytes, sha256 675b7843…, crc
  0xc7a8e64a, packaged 7013b5a6…
- **ld0nb** (`cores/sgx530_usse_ld0nb.py`): `ld.a.d r3, r5, #0`, with r5 = `limm`
  0x0f004000. Image 80 bytes, sha256 d0ce59a3…, crc 0xd7ce33b4, packaged e1d819da…

**Results:**

| Probe | Base | Offset | `BIF_INT_STAT` | `BIF_FAULT` | `EVENT_TIMER` |
|---|---|---|---|---|---|
| ld0 | r17 (patched 0x0f003000) | 0 | 0x4002 | **0x0fd79000** | 0 |
| ld0nb | r5 = `limm` 0x0f004000 | 0 | 0x4002 | **0x0c004000** | 0 |

- Both faults held from 100 ms to 500 ms. INIT_STATUS 0 in both.
- -ETIMEDOUT each time. The failed-start path held the cores in reset, then all five
  modules unloaded and the parent runtime-suspended.

**Facts (C):**
- **The offset doesn't place the fault:** with r17 and offset 0 the load faults at
  0x0fd79000, as with offset 42 (attempts 27 and 28).
- **The base register does:** with r5 = `limm` 0x0f004000 the fault moves to 0x0c004000.
  The low bits come through (0x4000), and the address is 0x03000000 below the value
  written.

**What it suggests (G):**
- **The register doesn't hold the value the SGX545 encoding of `limm` writes.** The
  microkernel's `limm` puts value bits 0-20 in word 0, bits 21-25 in word 1 bits 4-8 and
  bits 26-31 in word 1 bits 12-17 (`fw_limm`, pvrsgx_fw.c). For 0x0f004000, bits 21-25 are
  0x18, and the fault page would fit them reading as 0. The patched r17 (0x0f003000) gives
  0x0fd79000, which doesn't fit that simply, so the SGX530's `limm` field layout is for the
  microkernel session to decode.

**Next:** the microkernel session decodes the SGX530's `limm`. That's the ISA, so it
documents it and hands it to the clean-room ISA work.
