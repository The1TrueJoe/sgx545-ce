# SGX530 stage 1, twelfth attempt: 0x0a6c is where the PDS starts executing, in 16-byte rows

**Board:** our OMAP3630 test board, openHC on the SD (7.3.3, the 02:16 build). 75 °C
before, 73.5 °C after.

**What ran:** powervr_sgx from sgx530 1e33da62 (CI: omap3630 43157838085, powervr-sgx and
upstream green), `allow_unisolated=1 code_base_pads=1 stage1_sweep=1`, with the
landing-pad image `sgx530_bases` (f7de7b95…). The event program is at code offset 0x4aa0,
so it sits 0x01404aa0 above `PDS_EXEC_BASE`: a 16-byte data segment, then a MOVS at +0x10
and a HALT at +0x14.
- **The grid:** event data 0 (0x0a6c) ∈ {0, 1, 2, 4} × event data 1 (0x0a70) ∈ {0, 1, 2,
  4, 6, 8}, with the kicker fix and the pads.
- **Then:** an event-program enable of 0x7fffffff, and of 0.
- **The fault check last.**

**Results:** no variant ran the ladder or reached a pad (`EVENT_TIMER` 0 throughout), and
no variant depended on the one before it. The fault check reported its fault and
recovered. The probe ended with -ETIMEDOUT. But `PDS_PC_BASE`'s non-zero value, apart from
the other value (0xf75c), was set by 0x0a6c alone:

| 0x0a6c | `PDS_PC_BASE` (any 0x0a70) | where that is (corrected) |
|---|---|---|
| 0 | 0x5012a8 | row 0, the event program's data segment |
| 1 (the value used since attempt 1) | 0x5012ac | row 1, byte 0x10: our MOVS and HALT |
| 2 | 0x5012b0 | row 2, byte 0x20, past our program |
| 4 | 0x5012b8 | row 4, byte 0x40, in PDS1's slot |

- The enable variants: 0x7fffffff gives 0x5012ac as the baseline does. With 0, only 0xf75c
  appears.

**Correction (2026-11-12, after the thirteenth attempt).** The first reading of this table
below, "0x0a6c counts dwords", was wrong. `PDS_PC_BASE` counts dwords (× 4 gives the
address), and each step of 0x0a6c moves it by 4: **0x0a6c counts 16-byte rows.**
- **0x0a6c = 1, the SGX545's value, starts the PDS at byte 0x10:** our MOVS, right after the
  one-row data segment. So it was right all along.
- **0x0a6c = 4 starts it at byte 0x40,** past our 0x18-byte program and into PDS1's slot.
- **Read this way, attempts 8-11's PC cycling between …ac (row 1: the MOVS and HALT) and
  …b0 (row 2) suggests the PDS did execute the event program,** sent its DOUT, and no task
  started.

The facts below are restated in rows.

**Facts (C):**
- **The PDS starts at the event program's address plus 16 bytes × 0x0a6c.** `PDS_PC_BASE`
  (dwords) = the program's address / 4 + 4 × 0x0a6c, for 0, 1, 2 and 4, under every 0x0a70.
- **0x0a6c = 1 starts it on our code; 4 starts it in PDS1's bytes.**
- **The third value (0xf75c) appears whenever the event program is enabled**, and alone
  when the enable is 0. So it isn't ours: another PDS activity.

**What it suggests (D):**
- **0x0a6c is the code offset in 16-byte rows,** the same on both cores. For our program
  that's 1.
