# SGX530 stage 1, thirtieth attempt: the load's fault follows the register it names, not its value

**Board:** our OMAP3630 test board, our kernel on the SD (7.3.3, the 02:16 build), up 1 min
after the owner's last Wi-Fi test, with the owner-confirmed host key. the board lock was held
for all seven loads. 77 °C before, 75 °C after. No hang, no plug cycle.

**What ran:** powervr_sgx from sgx530 fd97aabe (the >> 8 code-base unit; modver-check 0
differ), `allow_unisolated=1` only, loaded seven times.
- **The images:** the microkernel session's `cores/sgx530_limm_b21.py` … `_b27.py` (its
  branch, 679ca90c), built with `ukernel/build.py` and packaged by `drm/tools/mkukfw.py`.
  All 14 image and package hashes match the microkernel session's list. Each image is 80
  bytes.
- **What each does:** it sets r5 = `limm` of one bit (b21 = 0x00200000 … b27 =
  0x08000000), then runs `ld.a.d r3, r5, #0`, gated by a `str` to `EVENT_TIMER`. The
  images differ in the `limm` word (offset 0x18): b21 `00 00 a0 00 10 00 20 fc`, b26
  `00 00 a0 00 00 10 20 fc`.
- **The run:** each run copied its own image to `/lib/firmware/powervr_sgx` before the
  insmod. Every run's event program sat at 0x01400050 (read back).

**Results:**

| Probe | r5 (`limm`) | `BIF_INT_STAT` | `BIF_FAULT` | `EVENT_TIMER` |
|---|---|---|---|---|
| b21 | 0x00200000 | 0x4002 | 0x0c004000 | 0 |
| b22 | 0x00400000 | 0x4002 | 0x0c004000 | 0 |
| b23 | 0x00800000 | 0x4002 | 0x0c004000 | 0 |
| b24 | 0x01000000 | 0x4002 | 0x0c004000 | 0 |
| b25 | 0x02000000 | 0x4002 | 0x0c004000 | 0 |
| b26 | 0x04000000 | 0x4002 | 0x0c004000 | 0 |
| b27 | 0x08000000 | 0x4002 | 0x0c004000 | 0 |

- -ETIMEDOUT each time. The failed-start path held the cores in reset, then all five
  modules unloaded and the parent runtime-suspended.

**Facts (C):**
- **The load faults at 0x0c004000 whatever r5's `limm` value is.** That's the page of the
  twenty-ninth attempt's ld0nb, where r5 was `limm` 0x0f004000.
- **Loads naming r17 fault at 0x0fd79000 and loads naming r5 at 0x0c004000,** in every
  probe and the real image so far. The offset doesn't move it either (twenty-ninth
  attempt).
- **So the fault address follows the source register the load names, not that register's
  value.** This corrects the twenty-ninth attempt's reading (see the correction there).

**What it suggests (G):**
- **The SGX530 decodes `ld.a.d`'s source operand differently from the SGX545 encoding.** It
  reads a register other than the one named, or from another bank, or takes the base from
  another field. The values at 0x0fd79000 and 0x0c004000 would then be whatever that other
  register holds.
- **The `limm` encoding isn't shown to be wrong by any result so far.**

**Next:** for the microkernel session. A load naming r0-r7 in turn, each preloaded with a
distinct `limm` value below 2 MiB, would map the operand field to the register read.
